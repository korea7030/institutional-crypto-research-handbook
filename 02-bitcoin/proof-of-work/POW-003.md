## 3. Executive Summary
SHA-256 is a standardized cryptographic hash algorithm that maps an input message to a fixed 256-bit digest.
It is deterministic:
```text
same input
↓
same digest
```
Small input changes are expected to produce substantially different outputs:
```text
message A
↓
SHA-256
↓
digest A
```
```text
message A with one changed bit
↓
SHA-256
↓
apparently unrelated digest B
```
Bitcoin uses SHA-256 as a cryptographic commitment and search function.
For Proof of Work, miners serialize an 80-byte block header and compute:
```text
SHA256(SHA256(block_header))
```
The resulting 256-bit value is interpreted as an integer and compared with the block's consensus target:
```text
block_hash ≤ target
```
A valid result is difficult to find because miners cannot predict which candidate header will produce a sufficiently small hash. Verification is inexpensive because a node can hash the submitted header and compare the result to the target.
Bitcoin does not use SHA-256 for every cryptographic purpose. Depending on the protocol context, Bitcoin also uses:
- RIPEMD-160,
- HMAC-SHA512,
- tagged single SHA-256,
- SipHash,
- other specialized constructions.
The phrase "Bitcoin uses SHA-256" is therefore correct but incomplete.

## 4. What Is a Cryptographic Hash Function?
A cryptographic hash function accepts a message of variable length and produces a fixed-length digest.
Conceptually:
```text
H(message) = digest
```
For SHA-256:
```text
input:
message shorter than 2^64 bits
output:
256-bit digest
```
NIST specifies SHA-256 as one of the Secure Hash Standard algorithms. It processes messages in 512-bit blocks, operates on 32-bit words, and produces a 256-bit digest. ([NIST 기술 시리즈 출판물](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.180-4.pdf))
### Example
```text
SHA256("Bitcoin")
```
produces one 256-bit result.
```text
SHA256("bitcoin")
```
produces a different result because uppercase and lowercase characters have different byte encodings.
The hash function operates on bytes and bits, not human semantic meaning.
---
## 5. Hashing Is Not Encryption
Hashing and encryption solve different problems.
| Property | Hash Function | Encryption |
|---|---|---|
| Primary purpose | Produce a digest | Preserve confidentiality |
| Reversible with a key | No | Yes |
| Typical input size | Variable | Variable |
| Typical output | Fixed-length digest | Ciphertext |
| Secret required | No | Usually |
| Bitcoin use | Commitments, identifiers, Proof of Work | Bitcoin does not encrypt the public blockchain |
A hash is not an encrypted copy of the original message.
There is no decryption key that converts a SHA-256 digest back into the source message.
However, this does not mean the original message is always impossible to discover.
If the input comes from a small or predictable search space, an attacker may hash likely candidates until one matches.
Example:
```text
SHA256("0000")
SHA256("0001")
SHA256("0002")
...
```
This is why passwords should not be stored using raw SHA-256 alone.

## 6. Core Security Properties
NIST describes secure hash algorithms as functions intended to make it computationally infeasible to recover a message corresponding to a digest or to find two different messages producing the same digest. ([NIST 기술 시리즈 출판물](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.180-4.pdf))
The standard cryptographic properties should be separated carefully.
---
### 6.1 Preimage Resistance
Given a digest:
```text
y = H(x)
```
it should be computationally infeasible to find any input `x` such that:
```text
H(x) = y
```
For an ideal 256-bit hash, generic preimage search requires approximately:
```text
2^256
```
trials in the worst-case security model.
Bitcoin mining is not a full preimage attack.
Miners are not trying to reproduce one exact 256-bit digest.
They are trying to find any digest inside a target range.
---
### 6.2 Second-Preimage Resistance
Given a specific message `x₁`, it should be computationally infeasible to find a different message `x₂` such that:
```text
H(x₁) = H(x₂)
```
with:
```text
x₁ ≠ x₂
```
This property matters for cryptographic commitments.
If a block header or transaction could be replaced by another object with the same digest, references to that digest could become ambiguous.
---
### 6.3 Collision Resistance
It should be computationally infeasible to find any pair of distinct messages:
```text
x₁ ≠ x₂
```
such that:
```text
H(x₁) = H(x₂)
```
For an ideal 256-bit hash, generic collision resistance is approximately:
```text
2^128
```
because of the birthday bound.
This does not mean SHA-256 has only 128-bit preimage security.
Collision and preimage attacks are different problems with different generic complexity.
---
## 7. Avalanche Behavior
A desirable hash-function behavior is that a small input change produces a substantially different output.
This is commonly called the avalanche effect.
Example:
```text
Input A:
block header with nonce = 100
```
```text
Input B:
block header with nonce = 101
```
The resulting hashes should appear unrelated.
This unpredictability is essential to mining.
A miner cannot gradually "move closer" to a valid hash using ordinary optimization.
Each candidate behaves approximately like a new random trial under the standard cryptographic model.
### Important Limitation
The avalanche effect is an observed and designed diffusion property.
It should not be treated as a complete proof of:
- preimage resistance,
- collision resistance,
- overall protocol security.

## 8. SHA-256 Standard Parameters
According to FIPS 180-4, SHA-256 has the following parameters. ([NIST 기술 시리즈 출판물](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.180-4.pdf))
| Parameter | SHA-256 |
|---|---:|
| Maximum message length | Less than `2^64` bits |
| Message block size | 512 bits |
| Word size | 32 bits |
| Digest size | 256 bits |
| Digest size in bytes | 32 bytes |
| Digest size in hexadecimal | 64 hex characters |
| Compression rounds per block | 64 |
| Internal state words | 8 × 32-bit words |
One hexadecimal character represents four bits:
```text
256 bits / 4 = 64 hexadecimal characters
```
---
## 9. High-Level SHA-256 Processing
SHA-256 can be understood as two broad phases:
```text
1. Preprocessing
2. Hash computation
```
NIST explicitly describes secure hash processing in these two stages. ([NIST 기술 시리즈 출판물](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.180-4.pdf))
---
### 9.1 Preprocessing
Preprocessing includes:
1. appending padding,
2. appending the original message length,
3. dividing the padded message into 512-bit blocks,
4. setting the initial hash state.
Conceptually:
```text
Original Message
↓
Append 1 bit
↓
Append enough 0 bits
↓
Append 64-bit message length
↓
512-bit aligned message
```
The padding is deterministic.
The same message always receives the same padding and digest.
---
### 9.2 Parsing Into Blocks
The padded message is divided into blocks:
```text
M(1), M(2), ..., M(N)
```
Each block contains:
```text
512 bits
```
or:
```text
16 × 32-bit words
```
SHA-256 processes the blocks sequentially.
The output state from one block becomes the input state for the next.
---
### 9.3 Message Schedule
Each 512-bit block begins as sixteen 32-bit words.
These are expanded into sixty-four 32-bit schedule words:
```text
W0 ... W63
```
The message schedule ensures that each round incorporates transformed information derived from the original block.
---
### 9.4 Compression Function
SHA-256 maintains eight working variables:
```text
a, b, c, d, e, f, g, h
```
Each of the 64 rounds combines:
- message-schedule data,
- fixed constants,
- bitwise choice and majority functions,
- rotations,
- shifts,
- addition modulo `2^32`.
After processing a block, the working variables are added to the current hash state.
After the final block, the eight state words form the 256-bit digest.
---
## 10. SHA-256 Is Deterministic but Its Output Is Modeled as Unpredictable
SHA-256 is completely deterministic.
There is no randomness inside the algorithm.
```text
same bytes
↓
same digest
```
Yet mining analysis models SHA-256 outputs as if candidate hashes were uniformly distributed across:
```text
0 to 2^256 - 1
```
This is a cryptographic modeling assumption.
The algorithm is deterministic, but without an exploitable shortcut, the result for a changed candidate header is computationally unpredictable before hashing it.
That distinction is central to Proof of Work.
---
## 11. SHA-256 in the Bitcoin Whitepaper
Section 4 of the Bitcoin Whitepaper describes Proof of Work as scanning for a value whose hash, using an algorithm such as SHA-256, begins with a required number of zero bits. It states that average work grows exponentially with the number of required zero bits while verification requires one hash evaluation. ([Bitcoin](https://bitcoin.org/bitcoin.pdf))
The Whitepaper presents the conceptual model:
```text
increment nonce
↓
hash block
↓
check zero-bit condition
```
Modern Bitcoin consensus expresses the condition more precisely as a numeric comparison:
```text
hash ≤ target
```
The visual appearance of leading zeros follows from the hash being numerically small.

## 12. Bitcoin's 80-Byte Block Header
Bitcoin does not repeatedly hash the entire serialized block during mining.
It hashes the serialized block header.
The header has six fields:
| Field | Size |
|---|---:|
| Version | 4 bytes |
| Previous block hash | 32 bytes |
| Merkle root | 32 bytes |
| Timestamp | 4 bytes |
| `nBits` | 4 bytes |
| Nonce | 4 bytes |
| **Total** | **80 bytes** |
The Bitcoin developer reference identifies this 80-byte serialized header as the object hashed by Bitcoin's Proof-of-Work algorithm. ([Bitcoin Developer](https://developer.bitcoin.org/reference/block_chain.html))
Conceptually:
```text
version
||
previous_block_hash
||
merkle_root
||
time
||
nBits
||
nonce
```
is serialized and then hashed.
---
## 13. Why Hash the Header Instead of the Entire Block?
The header commits to the important block contents indirectly.
### Previous Block Hash
The header includes the double-SHA-256 hash of the previous block header.
This links the block to a specific predecessor.
### Merkle Root
The header includes a Merkle root derived from the block's transactions.
Changing a transaction changes:
```text
transaction identifier
↓
Merkle tree
↓
Merkle root
↓
block header hash
```
### Consensus Metadata
The header also includes:
- version,
- timestamp,
- encoded target,
- nonce.
Therefore, the 80-byte header acts as a compact commitment to:
- the previous chain history,
- the included transaction set and ordering,
- the block's Proof-of-Work parameters.
---
## 14. Double SHA-256
Bitcoin commonly uses the construction:
```text
SHA256(SHA256(data))
```
This is often abbreviated as:
```text
SHA256d
```
or:
```text
double SHA-256
```
Bitcoin Core's `CHash256` class performs a first SHA-256 finalization, resets the SHA-256 state, writes the 32-byte intermediate digest, and hashes it again. ([GitHub](https://github.com/bitcoin/bitcoin/blob/master/src/hash.h?utm_source=chatgpt.com))
Conceptually:
```text
first_digest = SHA256(data)
final_digest = SHA256(first_digest)
```
---
## 15. Where Bitcoin Uses Double SHA-256
Important uses include:
### 15.1 Block Header Hashes
```text
block_hash = SHA256(SHA256(serialized_block_header))
```
This value is used in Proof-of-Work validation and block identification.
### 15.2 Legacy Transaction IDs
The traditional transaction ID is derived from double SHA-256 of the serialized non-witness transaction form.
### 15.3 Merkle Tree Nodes
Bitcoin's traditional transaction Merkle tree combines adjacent 32-byte hashes and applies double SHA-256 to each pair. The Bitcoin developer reference documents this repeated `SHA256(SHA256())` construction. ([Bitcoin Developer](https://developer.bitcoin.org/reference/block_chain.html))
### 15.4 Previous-Block References
The next block header stores the prior block header's double-SHA-256 hash.
---
## 16. Bitcoin Does Not Always Use Double SHA-256
It is incorrect to assume every Bitcoin hash uses SHA256d.
Examples of other constructions include:
| Context | Construction |
|---|---|
| P2PKH key hash | SHA-256 followed by RIPEMD-160 |
| P2WSH witness program | Single SHA-256 of the witness script |
| BIP32 key derivation | HMAC-SHA512 |
| Taproot and Schnorr-related hashes | Tagged single SHA-256 |
| Compact block short IDs | SipHash-based construction |
| Script `OP_SHA256` | Single SHA-256 |
| Script `OP_HASH256` | Double SHA-256 |
The hash construction must always be identified by protocol context.
---
## 17. Why Does Bitcoin Use Double SHA-256?
### FACT
Bitcoin consensus uses double SHA-256 in several foundational structures.
### UNKNOWN
The Bitcoin Whitepaper and original public design materials do not provide a complete, authoritative explanation for every reason Satoshi selected double SHA-256 rather than single SHA-256.
Common explanations include:
- reducing exposure to Merkle–Damgård length-extension behavior in contexts where raw hashes are reused,
- defensive engineering,
- consistency with earlier constructions,
- reducing dependence on one compression pass.
These explanations should not be presented as established historical fact without direct primary evidence.
### Institutional Standard
The accurate statement is:
> Bitcoin uses double SHA-256 in several consensus-critical contexts; the complete original design rationale is not explicitly documented.
---
## 18. Length Extension: Important but Frequently Overstated
SHA-256 follows a Merkle–Damgård-style iterative construction.
For certain insecure constructions, knowing:
```text
SHA256(secret || message)
```
may allow an attacker to compute the hash of:
```text
secret || message || padding || extension
```
without knowing the secret.
This is called a length-extension attack.
However:
- Bitcoin block hashing does not use SHA-256 as a naive secret-prefix MAC.
- A length-extension property does not directly allow an attacker to produce a lower Proof-of-Work hash.
- Double SHA-256 prevents straightforward reuse of the first digest as an exposed internal state.
It is reasonable to discuss this as a security property of the construction.
It is not justified to claim with certainty that length-extension resistance was the sole or documented reason Bitcoin adopted double SHA-256.
---
## 19. Mining as Targeted Hash Search
Mining searches for an 80-byte header whose double-SHA-256 digest is less than or equal to a target:
```text
SHA256d(header) ≤ target
```
Mining hardware repeatedly varies header-related data.
The direct header nonce is 32 bits:
```text
0 to 4,294,967,295
```
If the nonce range is exhausted, miners can modify other data, such as:
- coinbase extra nonce,
- transaction selection,
- transaction ordering,
- timestamp,
- version bits where permitted.
Changing the coinbase transaction changes its transaction identifier, which changes the Merkle root and creates a new block-header search space. The official mining guide describes this workflow. ([Bitcoin Developer](https://developer.bitcoin.org/devguide/mining.html))
---
## 20. Probability of a Valid Hash
Assume SHA-256d outputs are uniformly distributed over the 256-bit range.
There are:
```text
2^256
```
possible hash values.
If valid values are:
```text
0 through target
```
then the probability of success for one candidate is approximately:
```text
P(success) = (target + 1) / 2^256
```
For very small targets, this is usually simplified to:
```text
P(success) ≈ target / 2^256
```
Expected trials are:
```text
E[trials] ≈ 2^256 / (target + 1)
```
A lower target means:
- lower probability per hash,
- more expected work,
- higher network difficulty.
---
## 21. A Valid Hash Does Not Reveal the Number of Attempts
Suppose a valid block hash is found.
The hash proves that:
```text
one valid header exists
```
It does not prove exactly how many candidate headers were tested.
A miner may find a block:
- on the first attempt,
- near the expected number of attempts,
- after many times the expected number.
Mining is probabilistic.
The network estimates work statistically from the target, not from a direct count of the miner's computations.
---
## 22. Block Hashes and Byte Order
Bitcoin hash presentation frequently causes confusion.
The block header stores hash fields using Bitcoin's internal byte-order conventions, while block explorers usually display block hashes in the reverse byte order familiar to users.
The developer reference notes that block-header hash fields are stored in internal byte order, while other scalar header fields are serialized in little-endian order. ([Bitcoin Developer](https://developer.bitcoin.org/reference/block_chain.html))
### Practical Consequence
A developer may:
1. serialize an 80-byte header,
2. compute SHA256d,
3. obtain 32 raw bytes,
4. reverse those bytes for the conventional displayed block-hash string.
The reversal is a representation issue.
It does not create a different cryptographic digest.
---
## 23. SHA-256 Internal Endianness vs Bitcoin Serialization
Two separate layers must not be confused.
### SHA-256 Standard
FIPS 180-4 expresses SHA-256 words using big-endian convention. ([NIST 기술 시리즈 출판물](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.180-4.pdf))
### Bitcoin Serialization
Bitcoin serializes many integer fields in little-endian format.
Hash fields have their own internal and display conventions.
Therefore, a correct implementation must distinguish:
- byte serialization before hashing,
- SHA-256's internal word processing,
- raw digest bytes,
- human-readable hash display.
Many incorrect block-hash calculations arise from mixing these layers.
---
## 24. Bitcoin Core SHA-256 Implementation
Bitcoin Core implements SHA-256 in:
```text
src/crypto/sha256.cpp
src/crypto/sha256.h
```
The implementation includes:
- a standard portable SHA-256 transformation,
- architecture-specific optimized implementations,
- runtime CPU-feature detection,
- specialized multiway double-SHA-256 processing.
Bitcoin Core's `CSHA256::Write` processes complete 64-byte blocks and buffers remaining bytes. `Finalize` applies SHA-256 padding, appends the bit length, and writes eight 32-bit state words as the final 32-byte digest. ([GitHub](https://github.com/bitcoin/bitcoin/blob/master/src/crypto/sha256.cpp))
### Important Architectural Point
Consensus depends on the resulting digest, not on which optimized implementation produced it.
Different implementations must produce exactly the same SHA-256 result.
---
## 25. Hardware Optimization
SHA-256's deterministic structure allows optimization in:
- CPUs,
- GPUs,
- FPGAs,
- ASICs.
Bitcoin Core includes CPU-specific SHA-256 paths for software hashing, but industrial Bitcoin mining is primarily performed by specialized ASIC hardware.
Optimization changes:
- hashes per second,
- energy efficiency,
- implementation throughput.
It does not change:
- the SHA-256 algorithm,
- the valid target,
- the block-header serialization,
- node verification rules.
---
## 26. Midstate Optimization
An 80-byte Bitcoin block header requires SHA-256 processing across more than one 64-byte block after padding.
Because much of a candidate header remains constant while miners vary selected fields, mining hardware can reuse intermediate SHA-256 state for unchanged portions.
This is commonly described as midstate optimization.
Conceptually:
```text
Mostly fixed header prefix
↓
precompute intermediate SHA-256 state
↓
vary mutable fields
↓
complete remaining rounds
```
This reduces redundant work.
It does not bypass SHA-256 or reduce the statistical difficulty of finding a valid digest.
---
## 27. Hash Security vs Consensus Security
SHA-256 security is one component of Bitcoin security.
Bitcoin consensus also depends on:
- valid transaction rules,
- valid block rules,
- chain selection,
- accumulated work,
- network propagation,
- miner incentives,
- node diversity,
- private-key security,
- software correctness.
A strong hash function does not make an invalid transaction valid.
A valid Proof of Work does not make an invalid block acceptable.
Nodes must verify both:
```text
Proof-of-Work condition
AND
all consensus rules
```
---
## 28. What If SHA-256 Were Weakened?
The effect depends on the type of weakness.
### 28.1 Faster Generic Hashing
If all participants gain proportionally faster SHA-256 hardware:
- blocks temporarily arrive faster,
- difficulty later adjusts,
- relative mining power may remain similar.
### 28.2 One-Sided Hardware Advantage
If one actor obtains a large private efficiency advantage:
- mining concentration risk increases,
- that actor gains a larger share of expected block production.
### 28.3 Preimage Shortcut
A practical shortcut for finding target-range hashes faster than brute force could undermine mining assumptions.
### 28.4 Collision Attack
A collision attack would be serious, but its effect must be analyzed by context.
Finding any two SHA-256 inputs with the same digest does not automatically provide:
- a valid alternate block,
- a chosen transaction replacement,
- a lower-than-target block hash,
- a private key,
- control of accumulated chainwork.
A usable Bitcoin attack may require stronger properties, such as:
- chosen-prefix control,
- second-preimage capability,
- preimage capability,
- consensus-specific exploitability.
"SHA-256 collision breaks Bitcoin" is therefore too imprecise for institutional research.
---
## 29. Quantum Computing Context
A sufficiently capable fault-tolerant quantum computer could theoretically apply Grover's algorithm to unstructured search.
For a 256-bit preimage-style search, Grover's algorithm provides a square-root reduction in query complexity:
```text
classical:
approximately 2^256
quantum:
approximately 2^128 queries
```
For Bitcoin mining, the practical effect is more complex because:
- mining is already massively parallel,
- quantum computation has substantial overhead,
- Grover search is sequential within one search instance,
- difficulty adjusts to effective network hash production,
- practical fault-tolerant hardware does not currently exist at the necessary scale.
Quantum implications should not be summarized as "SHA-256 becomes useless."
---
## 30. On-Chain Implications
SHA-256 and SHA256d appear directly in observable Bitcoin structures.
### 30.1 Block Hash
Every block has a header hash satisfying the target.
### 30.2 Previous Block Hash
Each block header commits to its predecessor.
### 30.3 Transaction IDs
Traditional TXIDs are hash-derived identifiers.
### 30.4 Merkle Root
The header commits to the transaction set through a double-SHA-256 Merkle tree.
### 30.5 Mining Difficulty
The probability of an acceptable hash is governed by the target.
### 30.6 Hash Rate Estimation
Network hash rate is inferred from:
- observed block intervals,
- current difficulty.
It is not directly counted from miners.
### 30.7 Chainwork
Nodes estimate accumulated work from each block's target rather than counting electrical energy.
---
## 31. Institutional Thinking
### Observation
Bitcoin uses SHA-256 extensively.
### Weak Conclusion
> SHA-256 makes Bitcoin secure.
### Institutional Decomposition
Ask which security property is relevant.
| Question | Relevant Property |
|---|---|
| Can a miner predict a successful nonce? | Preimage-like search hardness |
| Can historical headers be substituted? | Second-preimage resistance |
| Can two arbitrary objects share a digest? | Collision resistance |
| Can a node verify a block cheaply? | Deterministic computation |
| Can a miner search efficiently? | Hardware throughput |
| Can a valid high-work block contain invalid transactions? | Separate consensus validation |
### Conclusion
SHA-256 supports Bitcoin's commitments and Proof-of-Work mechanism.
Bitcoin's security emerges from the interaction of cryptography, validation, networking, economics, and accumulated work.

## 32. Analyst Notes
When reviewing a blockchain's hash-function model, verify:
### Algorithm
- Which hash function is used?
- Is it standardized?
- What output length does it have?
- Are known practical attacks relevant?
### Construction
- Single hash or double hash?
- Tagged hash?
- HMAC?
- Hash-then-truncate?
- Multiple algorithms combined?
### Serialization
- What exact bytes are hashed?
- In what byte order?
- Are witness or metadata fields included?
- Is the serialization consensus-critical?
### Proof of Work
- What constitutes a valid output?
- Numeric target or prefix rule?
- How is target encoded?
- Which fields can miners vary?
- Can intermediate state be reused?
### Identifiers
- Is the digest used as an identifier or as a security proof?
- Is the displayed byte order different from internal order?
- Could malleability change the identifier?
### Security
- Which attack property matters: collision, preimage, or second preimage?
- Would a theoretical cryptographic result create a practical protocol attack?
- Is specialized hardware an intended feature or a risk?

## 33. Common Misinterpretations
### Misinterpretation 1
> SHA-256 encrypts Bitcoin transactions.
Incorrect.
Bitcoin transactions are publicly visible. SHA-256 creates digests and commitments; it does not encrypt public blockchain data.
---
### Misinterpretation 2
> Miners decrypt blocks.
Incorrect.
Miners search for a block header whose double-SHA-256 digest satisfies the target.
---
### Misinterpretation 3
> A block hash contains hidden transaction data.
Incorrect.
A digest commits to data but does not encode a reversible copy of the data.
---
### Misinterpretation 4
> Bitcoin always uses double SHA-256.
Incorrect.
Bitcoin uses several hash constructions depending on context.
---
### Misinterpretation 5
> The nonce is the only field miners can change.
Incorrect.
Miners can alter coinbase extra nonce, transaction selection, transaction ordering, timestamp, and other permitted data, thereby changing the Merkle root or header.
---
### Misinterpretation 6
> More leading zeros cause the hash function to perform more work.
Incorrect.
SHA-256 performs the same algorithm for every header. More required leading zeros reduce the proportion of acceptable outputs, forcing miners to test more candidates on average.
---
### Misinterpretation 7
> The network can see exactly how many hashes a miner performed.
Incorrect.
The network sees the successful header and infers expected work from the target.
---
### Misinterpretation 8
> A SHA-256 collision would immediately allow arbitrary double spending.
Incorrect.
The practical consequence depends on the exact cryptographic capability and its applicability to Bitcoin's serialized structures and consensus rules.
---
## 34. Counter Evidence and Limitations
SHA-256 is not the only viable Proof-of-Work hash function.
Other protocols use algorithms designed around different goals, including:
- memory hardness,
- resistance to specialized hardware,
- efficient commodity-hardware participation,
- combined hash functions.
Bitcoin's use of SHA-256 has encouraged highly specialized ASIC development.
This has produced:
- extremely high hash throughput,
- substantial hardware specialization,
- industrial mining infrastructure,
- barriers to competitive entry.
Whether ASIC specialization strengthens or weakens decentralization depends on the analytical dimension:
- hardware efficiency,
- manufacturer concentration,
- pool concentration,
- geographic distribution,
- energy access,
- operational scale.
The hash function should therefore be evaluated as part of a mining ecosystem, not in isolation.
