## 3. Executive Summary

Bitcoin's Proof-of-Work target is a 256-bit unsigned integer.

A block header, however, allocates only four bytes to the target field:

```text
nBits: uint32_t
```

Bitcoin therefore stores the target using a compact representation resembling base-256 scientific notation. The official developer reference describes the target as a 256-bit threshold encoded into the 32-bit `nBits` field using a less precise compact format. ([Bitcoin Developer](https://developer.bitcoin.org/reference/block_chain.html))

The four bytes are conceptually divided into:

```text
[ exponent ][ coefficient/significand ]
   1 byte             3 bytes
```

Ignoring the historical sign-bit behavior, decoding follows:

```text
target = coefficient × 256^(exponent - 3)
```

For example:

```text
nBits = 0x1d00ffff
```

contains:

```text
exponent    = 0x1d = 29
coefficient = 0x00ffff
```

and represents:

```text
target = 0x00ffff × 256^(29 - 3)
```

Compact encoding is not a general lossless serialization of every 256-bit integer. It preserves only the most significant bytes needed by the format and may discard lower-order precision when a large target is encoded.

Bitcoin Core also inherits a sign-bit convention from an older signed-number representation. If the coefficient's high bit is set, the compact value may be interpreted as negative. Because Proof-of-Work targets are unsigned, negative, zero, overflowing, and above-limit targets are rejected before hash comparison. ([Bitcoin Developer](https://developer.bitcoin.org/reference/block_chain.html))

## 4. Position Inside the Block Header

The Bitcoin block header is 80 bytes.

| Field | Size |
|---|---:|
| Version | 4 bytes |
| Previous block hash | 32 bytes |
| Merkle root | 32 bytes |
| Timestamp | 4 bytes |
| `nBits` | 4 bytes |
| Nonce | 4 bytes |
| **Total** | **80 bytes** |

The `nBits` field is an encoded version of the target that the block-header hash must be less than or equal to. ([Bitcoin Developer](https://developer.bitcoin.org/reference/block_chain.html))

Conceptually:

```text
Block Header

├── version
├── previous block hash
├── Merkle root
├── timestamp
├── nBits
└── nonce
```

The validation flow is:

```text
nBits

↓

decode full target

↓

validate target

↓

calculate block-header hash

↓

accept Proof of Work only when:

hash ≤ target
```

## 5. Why Compact Encoding Exists

A complete Proof-of-Work target can require up to:

```text
256 bits = 32 bytes
```

The block header reserves:

```text
32 bits = 4 bytes
```

Bitcoin therefore uses a floating-point-like compact representation.

The format prioritizes:

- small header size,
- easy target transmission,
- deterministic decoding,
- sufficient precision for difficulty control.

It does not preserve every possible 256-bit target exactly.

This is an intentional encoding trade-off.

---

## 6. Compact Format Layout

A compact value can be separated as:

```text
0xEECCCCCC
```

where:

```text
EE     = exponent
CCCCCC = coefficient region
```

More precisely:

```text
exponent = nBits >> 24
```

```text
coefficient_with_sign = nBits & 0x00ffffff
```

The coefficient magnitude is normally taken from:

```text
nBits & 0x007fffff
```

because:

```text
0x00800000
```

acts as the historical sign bit.

Layout:

```text
31                      24 23                    0
+-------------------------+-----------------------+
|        exponent         | sign + coefficient    |
+-------------------------+-----------------------+
          8 bits                    24 bits
```

---

## 7. Base-256 Scientific Notation

Decimal scientific notation may represent a number as:

```text
1.23 × 10^8
```

Bitcoin compact format operates conceptually in base 256:

```text
coefficient × 256^(exponent - 3)
```

The exponent describes the target's byte length.

The coefficient stores its most significant bytes.

The official developer documentation characterizes `nBits` as a base-256 counterpart to scientific notation. ([Bitcoin Developer](https://developer.bitcoin.org/reference/block_chain.html))

---

## 8. Decoding Formula

Let:

```text
nSize = nBits >> 24
```

and:

```text
nWord = nBits & 0x007fffff
```

Bitcoin Core's `SetCompact` logic follows two cases.

### Case A — Exponent at Most 3

When:

```text
nSize ≤ 3
```

the coefficient is shifted right:

```text
target = nWord >> (8 × (3 - nSize))
```

### Case B — Exponent Greater Than 3

When:

```text
nSize > 3
```

the coefficient is shifted left:

```text
target = nWord << (8 × (nSize - 3))
```

Equivalent conceptual formula:

```text
target = coefficient × 256^(exponent - 3)
```

The source implementation uses bit shifts instead of floating-point arithmetic so decoding remains exact and deterministic within the represented precision. ([GitHub](https://github.com/bitcoin/bitcoin/blob/master/src/arith_uint256.cpp))

## 12. The Historical Sign Bit

The compact format inherits behavior from a signed-number representation.

The bit:

```text
0x00800000
```

acts as a sign indicator.

Conceptually:

```text
negative =
(coefficient != 0)
AND
(nBits & 0x00800000 != 0)
```

Example:

```text
nBits = 0x04923456
```

The coefficient region begins with:

```text
0x92
```

whose high bit is set.

This is interpreted as a negative compact number:

```text
-0x12345600
```

The developer reference explicitly notes that this signed-data-class inheritance allows a target to be represented as negative even though the Proof-of-Work threshold is conceptually unsigned. ([Bitcoin Developer](https://developer.bitcoin.org/reference/block_chain.html))

---

## 13. Negative Targets Are Invalid

A block-header hash is treated as an unsigned integer.

It can never meaningfully satisfy a negative target.

Bitcoin Core therefore rejects a compact target when the decoded value is marked negative.

Conceptually:

```text
if negative:
    reject
```

This check is performed before comparing the block hash with the target. ([GitHub](https://github.com/bitcoin/bitcoin/blob/master/src/pow.cpp))

### Important Distinction

Decoding a compact value and accepting it as a valid Bitcoin target are separate operations.

A parser may derive:

- magnitude,
- negative flag,
- overflow flag.

Consensus validation then decides whether the result is permissible.

---

## 14. Zero Targets Are Invalid

Some compact values decode to zero.

Examples from the documented test vectors include:

```text
0x01003456 → 0x00
```

A zero target would permit only the impossible-to-expect special case:

```text
hash = 0
```

Bitcoin Core explicitly rejects zero targets rather than treating them as valid extreme difficulty. ([Bitcoin Developer](https://developer.bitcoin.org/reference/block_chain.html))

Validation:

```text
if target == 0:
    reject
```

---

## 15. Overflow Detection

Compact values can represent magnitudes outside the supported 256-bit unsigned range.

Bitcoin Core records an overflow flag using conditions based on:

- coefficient size,
- exponent size,
- resulting shifted bit length.

Conceptually, overflow occurs when the compact representation would require more than 256 bits.

A simplified interpretation is:

```text
if decoded target > 2^256 - 1:
    overflow = true
```

Bitcoin Core rejects overflowing targets before Proof-of-Work comparison. ([GitHub](https://github.com/bitcoin/bitcoin/blob/master/src/arith_uint256.cpp))

---

## 16. `powLimit` Validation

Even a positive, non-zero, non-overflowing target may still be invalid.

Each network defines a maximum allowed target:

```text
powLimit
```

Because a larger target is easier, this value establishes the easiest permissible Proof of Work.

Validation requires:

```text
target ≤ powLimit
```

If:

```text
target > powLimit
```

the block is rejected.

The miner cannot declare an arbitrarily easy target merely by placing a large compact value in `nBits`. ([GitHub](https://github.com/bitcoin/bitcoin/blob/master/src/pow.cpp))

---

## 17. Compact Validity vs Required Difficulty

Two separate checks are required.

### Check 1 — Is the Compact Target Structurally Valid?

Reject if:

- negative,
- zero,
- overflowing,
- above `powLimit`.

### Check 2 — Is This the Target Required by Consensus?

The block's `nBits` must match the target determined from:

- previous blocks,
- block height,
- retarget rules,
- timestamps,
- network-specific exceptions.

A miner could encode a structurally valid but easier target.

The block remains invalid if that target is not the one consensus requires.

---

## 18. Proof-of-Work Comparison

Once the compact target passes validation:

```text
target = decode(nBits)
```

the node computes:

```text
hash = SHA256d(serialized_block_header)
```

It then applies:

```text
if hash > target:
    reject
```

Therefore, valid:

```text
hash ≤ target
```

Equality is accepted.

The `nBits` value is part of the hashed header, so altering it also changes the header hash.

---

## 19. Encoding a Target Into Compact Form

Bitcoin Core's `GetCompact` performs the reverse operation.

At a high level:

1. Determine how many bytes are required to represent the target.
2. Extract the most significant three bytes.
3. Store the byte length as the exponent.
4. If the coefficient's high bit would be interpreted as a sign bit:
   - shift the coefficient right by one byte,
   - increase the exponent by one.
5. Add the sign bit only when encoding a negative arithmetic value.

Proof-of-Work targets are expected to be unsigned and non-negative, but the arithmetic helper supports the inherited sign convention. ([GitHub](https://github.com/bitcoin/bitcoin/blob/master/src/arith_uint256.cpp))

---

## 20. Encoding Formula

Let:

```text
size = ceil(bit_length(target) / 8)
```

### If `size ≤ 3`

Shift the target left so it occupies the coefficient region:

```text
compact =
target << (8 × (3 - size))
```

### If `size > 3`

Extract the most significant three bytes:

```text
compact =
target >> (8 × (size - 3))
```

Then append the exponent:

```text
compact =
compact | (size << 24)
```

The coefficient is later normalized if its sign bit is set.

---

## 21. Sign-Bit Normalization

Suppose the extracted coefficient begins with a byte whose high bit is `1`.

Example:

```text
coefficient = 0x923456
```

Because:

```text
0x92 & 0x80 != 0
```

the compact representation would be interpreted as negative.

Bitcoin Core normalizes it by:

```text
coefficient >>= 8
exponent += 1
```

Conceptually:

```text
0x923456 × 256^k
```

is represented as:

```text
0x009234 × 256^(k + 1)
```

This preserves the represented magnitude while leaving the sign bit clear.

The official reference describes this adjustment when creating `nBits` values. ([Bitcoin Developer](https://developer.bitcoin.org/reference/block_chain.html))

---

## 22. Compact Encoding Is Lossy

A compact target has only about three bytes of coefficient precision.

When a target requires more bytes, lower-order bytes are discarded during encoding.

Example conceptual target:

```text
0x123456789abcdef...
```

may encode only its most significant coefficient:

```text
0x123456
```

plus an exponent.

Decoding the compact value produces:

```text
0x123456000000000...
```

not necessarily the exact original integer.

Therefore:

```text
decode(encode(target))
```

may differ from:

```text
target
```

for arbitrary targets.

The format is deterministic but not fully lossless.

---

## 23. Why Precision Loss Is Acceptable

Bitcoin's difficulty system does not require arbitrary 256-bit target precision.

It requires:

- deterministic target calculation,
- deterministic compact encoding,
- consensus agreement,
- sufficient granularity for retargeting.

The lost lower-order bits represent a very small relative change compared with the target's full magnitude.

However, precision loss matters when:

- reproducing consensus code,
- calculating exact chainwork,
- comparing explorer outputs,
- implementing retarget rules,
- testing edge cases.

---

## 24. Canonical and Non-Canonical Compact Encodings

Because compact encoding behaves like scientific notation, more than one syntactic representation may sometimes decode to related or equal magnitudes in general-purpose arithmetic contexts.

Bitcoin consensus should not be described as accepting arbitrary numeric-equivalent `nBits` encodings.

At each height, the expected compact target is determined by consensus difficulty rules.

A block must normally contain the required encoded value, not merely any alternative encoding that happens to decode to a similar numeric target.

Institutional analysis should distinguish:

```text
numeric target equivalence
```

from:

```text
consensus-required nBits encoding
```

## 29. Byte Order

The `nBits` field is serialized as a four-byte little-endian integer inside the block header.

Suppose the logical value is:

```text
0x1d00ffff
```

Serialized header bytes are:

```text
ff ff 00 1d
```

An analyst reading raw block-header hex must reverse the field bytes to obtain the logical integer.

The exponent and coefficient are extracted from the logical integer:

```text
0x1d00ffff
```

not directly from the byte sequence as visually encountered in serialized hex.

---

## 30. Common Byte-Order Mistake

Incorrect interpretation:

```text
serialized bytes:
ff ff 00 1d

exponent = 0xff
```

Correct interpretation:

```text
serialized bytes:
ff ff 00 1d

↓

decode uint32 little-endian

↓

logical value:
0x1d00ffff

↓

exponent = 0x1d
coefficient = 0x00ffff
```

Byte-order mistakes can produce targets differing by enormous magnitudes.

## 31. `nBits` and Difficulty Calculation

Difficulty is commonly calculated as:

```text
difficulty =
difficulty_1_target / current_target
```

The current target should be derived from `nBits` using consensus-compatible compact decoding.

A naïve calculation may be wrong if it:

- treats `nBits` as the full target,
- ignores little-endian serialization,
- ignores the sign bit,
- assumes all compact values are exact,
- uses floating-point arithmetic too early,
- confuses `powLimit` with the conventional difficulty-1 target.

For exact analysis:

1. decode using integer arithmetic,
2. validate the compact value,
3. compute ratios using arbitrary-precision arithmetic,
4. convert to decimal only for presentation.

---

## 32. `nBits` and Chainwork

Per-block expected work is calculated from the decoded target:

```text
block_work =
floor(2^256 / (target + 1))
```

Therefore:

```text
nBits

↓

decoded target

↓

expected block work

↓

cumulative chainwork
```

A compact-decoding discrepancy can cause disagreement about:

- block work,
- chainwork,
- best-chain selection.

This makes `nBits` decoding consensus-sensitive.

---

## 33. `nBits` and Difficulty Adjustment

During retargeting, Bitcoin calculates a new full target using the previous target and observed timespan.

The result is then encoded back into compact form:

```text
calculated target

↓

apply powLimit

↓

GetCompact()

↓

new nBits
```

Because compact encoding loses lower-order precision, the target actually placed in the next block header is the compactly representable form.

This behavior must be reproduced exactly by every consensus implementation.

---

## 34. `nBits` Does Not Prove Correct Difficulty Alone

A block contains an `nBits` value.

That value is a miner claim.

Nodes independently determine whether it is permitted.

Validation questions:

1. Does the compact value decode safely?
2. Is the target at or below `powLimit`?
3. Is this the target required by consensus at this height?
4. Does the block hash satisfy that target?

A correct compact encoding does not imply the block used the correct difficulty.

---

## 35. Bitcoin Core Conceptual Flow

```text
Block Header nBits

↓

GetNextWorkRequired()
determines required compact target

↓

Compare header nBits with required nBits

↓

SetCompact()
decodes full arithmetic target

↓

Reject if:
- negative
- zero
- overflow
- above powLimit

↓

Compute block-header SHA256d

↓

Reject if:
hash > target
```

Different validation stages may be located in different parts of the codebase.

The analytical point is that compact decoding and expected-difficulty validation are separate responsibilities.

## 36. Simplified Decoder Pseudocode

```python
def decode_compact(nbits: int) -> tuple[int, bool, bool]:
    size = nbits >> 24
    word = nbits & 0x007FFFFF

    if size <= 3:
        target = word >> (8 * (3 - size))
    else:
        target = word << (8 * (size - 3))

    negative = (
        word != 0
        and (nbits & 0x00800000) != 0
    )

    overflow = (
        word != 0
        and (
            size > 34
            or (word > 0xFF and size > 33)
            or (word > 0xFFFF and size > 32)
        )
    )

    return target, negative, overflow
```

The exact conditions should be taken from the relevant Bitcoin Core version when implementing consensus-compatible software. ([GitHub](https://github.com/bitcoin/bitcoin/blob/master/src/arith_uint256.cpp))

## 37. Simplified Encoder Pseudocode

```python
def encode_compact(target: int, negative: bool = False) -> int:
    size = (target.bit_length() + 7) // 8

    if size <= 3:
        compact = target << (8 * (3 - size))
    else:
        compact = target >> (8 * (size - 3))

    if compact & 0x00800000:
        compact >>= 8
        size += 1

    compact |= size << 24

    if negative and (compact & 0x007FFFFF):
        compact |= 0x00800000

    return compact
```

For Bitcoin Proof-of-Work targets:

```text
negative = false
```

## 38. Round-Trip Behavior

For a compactly representable target:

```text
encode(decode(nBits))
```

should produce the normalized compact representation.

For an arbitrary full target:

```text
decode(encode(target))
```

may produce a rounded value whose lower bytes are zeroed.

Example conceptual behavior:

```text
original:
0x123456789abc
```

```text
encoded coefficient:
0x123456
```

```text
decoded:
0x123456000000
```

The loss occurs in the least-significant bytes.

---

## 39. Why Rounding Direction Matters

An encoded target should not accidentally become easier than intended due to incorrect rounding.

Consensus code must reproduce Bitcoin Core's truncation and normalization behavior exactly.

A one-byte shift or sign-normalization error can change the target by a factor of:

```text
256
```

or more.

Potential consequences include:

- accepting insufficient Proof of Work,
- rejecting valid blocks,
- calculating incorrect chainwork,
- splitting consensus.

This is why generic floating-point types are inappropriate.

---

## 40. Never Use IEEE Floating Point for Consensus Decoding

The compact format resembles scientific notation, but it must not be decoded with ordinary `float` or `double`.

Reasons:

- limited mantissa precision,
- platform-dependent edge behavior,
- rounding differences,
- inability to represent arbitrary 256-bit integers exactly.

Use:

- integer shifts,
- arbitrary-precision integers,
- consensus-compatible unsigned arithmetic.

The "floating-point-like" description explains the layout, not the implementation method.

---

## 41. Network Differences

The same compact-decoding algorithm is used across Bitcoin networks, but acceptable target ranges and difficulty rules differ.

Examples:

- mainnet has its own `powLimit`,
- test networks may permit minimum-difficulty exceptions,
- regtest uses an exceptionally easy target,
- signet has separate network parameters.

The developer reference lists:

```text
0x1d00ffff
```

as the conventional difficulty-1 value for the documented mainnet/testnet context and:

```text
0x207fffff
```

for regtest's near-instant block production setting. ([Bitcoin Developer](https://developer.bitcoin.org/reference/block_chain.html))

Do not infer network identity from `nBits` alone.

```text
target =
0x7fffff × 256^(32 - 3)
```

This target occupies a very large portion of the 256-bit hash space.

Therefore, valid blocks can be mined quickly during local testing.

The coefficient remains below the sign-bit boundary:

```text
0x7fffff < 0x800000
```

---

## 43. Security Boundary

`nBits` is only four bytes, but mistakes around it can be consensus-critical.

Potential implementation failures include:

- accepting negative targets,
- accepting overflowed targets,
- accepting targets above `powLimit`,
- incorrect little-endian parsing,
- incorrect exponent shifts,
- sign-bit mishandling,
- floating-point rounding,
- failing to verify required difficulty,
- incorrect compact re-encoding.

A secure alternative implementation should treat Bitcoin Core tests as mandatory compatibility vectors, not optional examples.

## 47. Common Misinterpretations

### Misinterpretation 1

> `nBits` is the mining difficulty.

Incorrect.

It is a compact encoding of the target.

---

### Misinterpretation 2

> `nBits` stores the full 256-bit target exactly.

Incorrect.

It uses a limited-precision compact format.

---

### Misinterpretation 3

> The first byte is the number of leading zero bits.

Incorrect.

It is a base-256 exponent describing the target's byte scale.

---

### Misinterpretation 4

> The remaining three bytes are always an unsigned coefficient.

Incomplete.

One bit is inherited as a sign bit.

---

### Misinterpretation 5

> Any positive decoded target is valid.

Incorrect.

It must also be non-zero, non-overflowing, at or below `powLimit`, and required by consensus.

---

### Misinterpretation 6

> Two numerically equivalent encodings are always interchangeable.

Incorrect.

Consensus expects the required compact representation.

---

### Misinterpretation 7

> Floating-point arithmetic is appropriate because the format resembles scientific notation.

Incorrect.

Consensus implementations require deterministic integer arithmetic.

---

### Misinterpretation 8

> `0x1d00ffff` is stored in the header as bytes `1d 00 ff ff`.

Incorrect.

The logical integer is serialized little-endian as:

```text
ff ff 00 1d
```

---

### Misinterpretation 9

> Compact-format rounding is too small to matter.

Incorrect.

Even small disagreements can split consensus or alter exact chainwork.

---

### Misinterpretation 10

> A valid `nBits` proves the block has sufficient work.

Incorrect.

The block hash must still satisfy the decoded target.

---

## 48. Counter Evidence and Limitations

The compact format is historically inherited and includes awkward properties:

- sign-bit behavior,
- limited precision,
- normalization rules,
- multiple conceptual layers,
- byte-order confusion.

A new protocol could use a simpler target encoding, such as:

- a full 256-bit integer,
- an unsigned exponent/coefficient format without a sign bit,
- a logarithmic difficulty field,
- a fixed precision rational representation.

Bitcoin retains `nBits` because changing consensus-critical header interpretation would require major protocol coordination and compatibility considerations.

Historical deployment and consensus stability outweigh aesthetic simplicity.
