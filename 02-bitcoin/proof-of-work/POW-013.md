## 3. Executive Summary

Bitcoin Core Proof-of-Work validation has two distinct layers:

```text
1. Does the header hash satisfy the target claimed by nBits?
2. Is that nBits value the target the block is allowed to claim at this height and parent?
```

The first layer is handled by `CheckProofOfWork`. It calls `DeriveTarget`, rejects invalid compact target encodings, and compares the block hash against the derived target.[^ref-btc-core-pow]

The second layer is contextual. `ContextualCheckBlockHeader` recomputes the expected `nBits` using `GetNextWorkRequired` and rejects the header with `bad-diffbits` if the block's `nBits` does not match the required value.[^ref-btc-core-validation]

This separation matters. A header can have a hash below the target encoded in its own `nBits` but still be invalid if that `nBits` value is easier than the target required by the parent and height.

Proof-of-Work validation is necessary but insufficient. `CheckBlock` also checks the Merkle root, size limits, coinbase placement, transaction structure, and other block rules. Later connection checks validate UTXO spending, fees, scripts, and coinbase amount.[^ref-btc-core-validation]

---

## 4. Definition and Scope

Proof-of-Work validation in Bitcoin Core means checking that a block header satisfies the network's target rules.

It includes:

- decoding `nBits`,
- rejecting invalid target encodings,
- enforcing `powLimit`,
- comparing header hash to target,
- checking expected target transition in context,
- checking parent availability and invalid-parent status before adding new headers.

It does not include:

- transaction validity,
- script execution,
- UTXO availability,
- coinbase reward amount,
- block relay policy,
- mempool acceptance.

---

## 5. Historical Background

The Bitcoin Whitepaper describes Proof of Work as finding a hash that begins with a required number of zero bits, with verification requiring one hash.[^ref-btc-wp]

Bitcoin Core implements the modern form using the compact `nBits` target field and a numerical comparison:

```text
hash <= target
```

Later implementation details include target derivation, overflow checks, network-specific `powLimit`, difficulty-transition validation, contextual timestamp checks, and special behavior for non-mainnet networks.

---

## 6. Original Design

The original design goal is asymmetry:

```text
expensive to find
cheap to verify
```

Bitcoin Core preserves this asymmetry. Given a candidate header, the node hashes the header, derives the target from `nBits`, and compares the two.

However, modern validation does more than the whitepaper's simplified description. It must also ensure that the block claims the correct target for its position in the chain.

---

## 7. Protocol Structure

Proof-of-Work validation uses these header and consensus inputs:

| Input | Role |
|---|---|
| Header hash | Value tested against the target. |
| `nBits` | Compact encoding of the claimed target. |
| `powLimit` | Network-specific easiest permitted target. |
| Parent block index | Determines next permitted target. |
| Block height | Determines retarget boundary and deployment context. |
| Timestamp | Used in contextual checks and retarget logic. |
| Network parameters | Mainnet, testnet, signet, regtest behavior differs. |

The key distinction is:

```text
nBits validity: can this compact target be decoded and is it within powLimit?
hash validity: is the header hash <= decoded target?
contextual target validity: is this nBits exactly what the parent and height require?
```

## 8. Technical Mechanics

### 8.1 Target Derivation

`DeriveTarget` converts `nBits` into a full target. It rejects the target when:

- the compact encoding is negative,
- the target is zero,
- the target overflows,
- the target exceeds `powLimit`.

If the target passes, `DeriveTarget` returns the target.[^ref-btc-core-pow]

### 8.2 Header Hash Comparison

`CheckProofOfWorkImpl` calls `DeriveTarget`. If no target is returned, Proof-of-Work validation fails.

If a target is returned, Bitcoin Core converts the header hash to an arithmetic integer and rejects it if:

```text
hash > target
```

Equivalently, the header passes this layer when:

```text
hash <= target
```

This is the direct work check.[^ref-btc-core-pow]

### 8.3 Contextual Target Check

`ContextualCheckBlockHeader` checks:

```text
block.nBits == GetNextWorkRequired(parent, block, consensusParams)
```

If the values differ, the block is rejected with `bad-diffbits`.[^ref-btc-core-validation]

This prevents a miner from choosing an easier target even if the header hash satisfies that easier target.

### 8.4 Header Acceptance

`AcceptBlockHeader`:

1. Detects duplicates.
2. Runs `CheckBlockHeader`.
3. Looks up the previous block.
4. Rejects missing parents with `prev-blk-not-found`.
5. Rejects invalid parents with `bad-prevblk`.
6. Runs `ContextualCheckBlockHeader`.
7. Requires minimum anti-DoS proof-of-work precheck before adding a new header.[^ref-btc-core-validation]

### 8.5 Full Block Validation Boundary

`CheckBlock` calls `CheckBlockHeader` but also checks non-PoW block structure. For Signet, it additionally checks the block solution when configured. It then checks the Merkle root, size limits, coinbase placement, and transaction structure.[^ref-btc-core-validation]

Therefore:

```text
valid PoW header
does not imply
valid block
```

## 9. Mathematical or Economic Model

Let:

- `H` be the block header hash interpreted as a 256-bit integer.
- `T_claimed` be the target decoded from the block's `nBits`.
- `T_required` be the target computed from parent, height, timestamps, and consensus parameters.

A header must satisfy:

```text
T_claimed is valid
H <= T_claimed
T_claimed == T_required
```

Toy example:

```text
required target: 100
claimed target:  200
header hash:     150
```

The hash satisfies the claimed target:

```text
150 <= 200
```

But the claimed target is not permitted:

```text
200 != 100
```

The header fails contextual validation.

Second example:

```text
required target: 100
claimed target:  100
header hash:     120
```

The target is correct, but the hash is too high:

```text
120 > 100
```

The header fails Proof-of-Work hash validation.

## 10. Security Assumptions

Bitcoin Core Proof-of-Work validation assumes:

- nodes independently recompute required targets,
- compact target decoding is deterministic,
- `powLimit` is network-specific and enforced,
- hash comparison is exact integer comparison,
- contextual checks are performed with the correct parent,
- invalid parent branches are not extended as valid history.

It does not assume:

- miners report difficulty honestly,
- block explorers define consensus validity,
- a valid header hash proves transaction validity,
- a received header has enough work to be useful for anti-DoS purposes.

## 11. Failure Modes and Attack Surface

### Invalid Compact Target

A miner can provide malformed or invalid `nBits`. `DeriveTarget` rejects negative, zero, overflowing, or above-limit targets.

### High Hash

The decoded target may be valid, but the header hash may be greater than the target. Bitcoin Core reports this Proof-of-Work failure as `high-hash` in `CheckBlockHeader`.[^ref-btc-core-validation]

### Bad Difficulty Bits

The header hash may satisfy the claimed target, but `nBits` may not match the required value for that height. Bitcoin Core rejects this as `bad-diffbits` in `ContextualCheckBlockHeader`.[^ref-btc-core-validation]

### Missing or Invalid Parent

Contextual validation needs the previous block index. `AcceptBlockHeader` rejects unknown parents and parents already marked failed.[^ref-btc-core-validation]

### Confusing Header Validity With Block Validity

Even a valid header can belong to a block body that fails Merkle root, size, coinbase, transaction, script, or UTXO rules.

## 12. Bitcoin Core or Protocol Implementation

### `pow.h`

`pow.h` declares the proof-of-work functions:

- `DeriveTarget`
- `GetNextWorkRequired`
- `CalculateNextWorkRequired`
- `CheckProofOfWork`
- `CheckProofOfWorkImpl`
- `PermittedDifficultyTransition`[^ref-btc-core-pow-h]

### `DeriveTarget`

`DeriveTarget` decodes the compact target and returns no target if the decoded value is negative, zero, overflowing, or above `powLimit`.[^ref-btc-core-pow]

### `CheckProofOfWorkImpl`

`CheckProofOfWorkImpl` derives the target, fails if target derivation failed, and rejects the header when the hash is numerically above the target.[^ref-btc-core-pow]

### `CheckProofOfWork`

`CheckProofOfWork` normally calls `CheckProofOfWorkImpl`. The source also contains a fuzz-determinism branch used during fuzz testing; this should not be treated as normal consensus behavior.[^ref-btc-core-pow]

### `CheckBlockHeader`

`CheckBlockHeader` calls `CheckProofOfWork` when Proof-of-Work checking is enabled. If this check fails, it returns `BLOCK_INVALID_HEADER` with reason `high-hash`.[^ref-btc-core-validation]

### `ContextualCheckBlockHeader`

`ContextualCheckBlockHeader` recomputes the expected `nBits` with `GetNextWorkRequired` and rejects mismatches as `bad-diffbits`. It also checks timestamp constraints and certain version rules.[^ref-btc-core-validation]

### `AcceptBlockHeader`

`AcceptBlockHeader` combines context-free header checks, parent lookup, invalid-parent detection, contextual header checks, and minimum anti-DoS work gating before adding a new header to the block index.[^ref-btc-core-validation]

## 14. Modern Context

Bitcoin Core validation separates responsibilities across functions:

```text
pow.cpp:
  target derivation
  target range checks
  hash <= target
  difficulty transition helpers

validation.cpp:
  header validation orchestration
  parent lookup
  expected nBits check
  timestamp context
  full block structure checks
```

This separation is important for researchers. A block can fail for multiple distinct reasons, and each reason implies a different kind of problem.

For example:

- `high-hash` means the header did not satisfy its claimed target.
- `bad-diffbits` means the claimed target was not the required target.
- `prev-blk-not-found` means the node cannot contextualize the header.
- full block validation failures may be unrelated to Proof of Work.

## 15. On-Chain Implications

### Directly Observable

From a block header and known chain context, an analyst can observe:

- header hash,
- `nBits`,
- parent hash,
- timestamp,
- height if connected to known parent chain.

### Deterministically Derivable

An analyst can derive:

- decoded target,
- whether target is within `powLimit`,
- whether `hash <= target`,
- expected `nBits` for the height and parent,
- whether the header would fail `high-hash` or `bad-diffbits` under the checked rules.

### Node-Local or Context-Dependent

An analyst may need local node state for:

- whether the parent is known,
- whether the parent is marked invalid,
- whether a header was already cached,
- whether minimum anti-DoS work gating was satisfied,
- whether a block body is available and valid.

### Unobservable From Header Alone

A header alone does not reveal:

- transaction validity,
- UTXO availability,
- script validity,
- coinbase reward correctness,
- miner identity,
- full block propagation history.

## 16. Institutional Thinking

### Observation

A block header hash is below the target encoded by its `nBits`.

### Weak Interpretation

"The block is valid."

### Institutional Decomposition

An institutional researcher should separate:

- compact target validity,
- hash-to-target comparison,
- expected target for height,
- parent availability,
- timestamp validity,
- Merkle root and block structure,
- transaction and UTXO validation,
- script execution,
- coinbase reward constraints.

### Current Conclusion

A header hash below the claimed target establishes only one Proof-of-Work condition. Full Bitcoin validity requires contextual header checks and full block validation.

### Confidence

FACT — ECL-A for the hash-to-target comparison when source data is available.  
FACT — ECL-A for contextual `nBits` validation when parent and consensus parameters are known.  
INTERPRETATION — ECL-B for broader operational conclusions about why a miner produced an invalid block.

## 17. Analyst Notes

When diagnosing a PoW-related invalid block, separate:

```text
invalid compact target
hash above target
incorrect nBits for height
missing parent
invalid parent
non-PoW block body failure
```

Do not summarize all of these as:

```text
bad mining
```

The exact failure reason matters.

For reproducibility, record:

- block hash,
- header bytes,
- `nBits`,
- decoded target,
- parent block,
- expected `nBits`,
- network parameters,
- Bitcoin Core version or commit used for validation.

## 18. Common Misinterpretations

### Misinterpretation

> If `hash <= nBits`, the block is valid.

### Assessment

Incorrect.

### Correction

`nBits` is compact target encoding, not the target itself. The target must be decoded, checked against `powLimit`, and verified in context.

### Misinterpretation

> If a header satisfies its own `nBits`, the header is valid.

### Assessment

Incomplete.

### Correction

The header must also claim the target required by its parent and height.

### Misinterpretation

> Proof-of-Work validation validates transactions.

### Assessment

Incorrect.

### Correction

Proof-of-Work validation checks the header target condition. Transaction validity is checked elsewhere.

### Misinterpretation

> `high-hash` and `bad-diffbits` are the same failure.

### Assessment

Incorrect.

### Correction

`high-hash` means the header hash is above the claimed target. `bad-diffbits` means the claimed target is not the required target.

### Misinterpretation

> Bitcoin Core accepts headers solely because they have enough work.

### Assessment

Incorrect.

### Correction

Bitcoin Core also checks duplicates, parent availability, invalid-parent status, contextual target, timestamps, and anti-DoS work gating before adding new headers.

## 19. Counter Evidence and Limitations

Bitcoin Core source is primary implementation evidence for Bitcoin Core behavior, not a complete description of every possible compatible implementation's internal organization.

Some validation paths expose flags such as `fCheckPOW`, `min_pow_checked`, and fuzz-testing behavior. These should be interpreted in their implementation context, not generalized as normal mainnet consensus shortcuts.

This document focuses on Proof-of-Work and header-context validation. Full validity requires transaction, script, UTXO, block weight, Merkle root, witness commitment, and coinbase checks.

Network-specific behavior matters. Signet, testnet, testnet4, and regtest can differ from mainnet.
