## 3. Executive Summary
Bitcoin mining is the process through which candidate blocks are constructed, Proof of Work is performed, and valid blocks are proposed to the network.
Mining is not one operation.
It is a pipeline:
```text
Observe current chain tip
↓
Select valid transactions
↓
Construct coinbase transaction
↓
Calculate transaction fees and permitted reward
↓
Build transaction Merkle tree
↓
Construct candidate block header
↓
Search for a header hash below the target
↓
Submit completed block
↓
Independent node validation
↓
Block propagation and chain selection
```
The miner does not decide unilaterally whether a block is valid.
Each fully validating node independently checks:
- the previous-block reference,
- the required target,
- Proof of Work,
- timestamp constraints,
- Merkle root,
- transaction validity,
- UTXO availability,
- script execution,
- block weight,
- coinbase reward,
- every applicable consensus rule.
Mining provides a permissionless block-proposal mechanism.
Validation remains the responsibility of nodes.
A useful distinction is:
```text
Miners propose ordering.
Nodes enforce validity.
```
Mining also contains an economic system.
A successful miner may receive:
```text
block subsidy
+
transaction fees
```
The reward encourages miners to spend resources securing the network. However, expected revenue is uncertain because block discovery is probabilistic.
Mining pools reduce payout variance by combining work from many miners and distributing revenue according to submitted shares.
---
## 4. What Bitcoin Mining Is
### FACT — ECL-A
Bitcoin mining combines three major responsibilities:
1. Constructing a valid candidate block.
2. Searching for Proof of Work satisfying the target.
3. Broadcasting a completed block for independent validation.
Mining should not be reduced to:
```text
creating new bitcoin
```
New issuance is one protocol-defined incentive attached to successful block production.
The deeper protocol function is:
```text
permissionless transaction ordering backed by costly work
```
---
## 5. What Bitcoin Mining Is Not
Mining is not:
- decrypting transactions,
- solving a unique equation,
- validating only the nonce,
- creating arbitrary bitcoin,
- deciding consensus rules,
- forcing nodes to accept a block,
- directly transferring electricity into bitcoin,
- recording every attempted hash on-chain.
A miner discovers a candidate header satisfying the target.
The network then verifies the full block.

## 7. Mining Begins With the Current Chain Tip
A miner normally attempts to extend the valid chain tip selected by its node.
The candidate header includes:
```text
previous_block_hash
```
which commits the new block to one particular predecessor.
When a new block becomes the best known tip, miners must quickly update their templates.
Work based on the previous tip generally becomes stale for extending the newly selected chain.
This makes mining latency-sensitive.
Important factors include:
- block-relay speed,
- node connectivity,
- pool-server latency,
- template-refresh speed,
- ASIC job-switching time.
---
## 8. Transaction Sources
Candidate transactions commonly come from a node's mempool.
The mempool contains transactions that the node currently considers valid for potential inclusion but which have not yet been confirmed in a block.
The mempool is not a global consensus object.
Different nodes may have different mempools because of:
- network timing,
- local policy,
- fee filters,
- replacement policy,
- memory limits,
- transaction propagation differences.
Therefore, different miners may create different candidate blocks even when building on the same parent.
---
## 9. Transaction Selection
A miner cannot simply sort every transaction by standalone fee.
Transactions may depend on unconfirmed parents.
A useful economic measure is:
```text
feerate = fee / transaction weight
```
For dependent transactions, miners may evaluate packages:
```text
parent transaction
+
child transaction
```
The package may be economically attractive even when the parent alone has a low fee rate.
Candidate selection must also respect:
- block weight,
- transaction dependencies,
- finality constraints,
- script validity,
- sigop limits,
- consensus rules,
- implementation policy.
Bitcoin Core's block assembler constructs candidate blocks from valid mempool entries while tracking fees, weight, and package relationships.
---
## 10. Miner Policy vs Consensus Rules
Miners operate under both consensus and policy constraints.
### Consensus Rules
Violating these makes a block invalid to all conforming nodes.
Examples include:
- spending nonexistent outputs,
- invalid scripts,
- excessive coinbase reward,
- invalid Proof of Work,
- incorrect required target,
- excessive block weight.
### Miner Policy
A miner may choose among many consensus-valid options.
Examples include:
- minimum fee rate,
- transaction prioritization,
- filtering particular transactions,
- coinbase output structure,
- payout address,
- pool-identification tag.
A miner may produce an unusual block that is still consensus-valid.
Policy differences do not necessarily imply consensus disagreement.
---
## 11. Block Construction
A simplified candidate-block construction process is:
```text
1. Read current chain tip.
2. Determine next block height.
3. Determine required target.
4. Select valid mempool transactions.
5. Calculate transaction fees.
6. Construct coinbase transaction.
7. Add witness commitment when required.
8. Build transaction Merkle tree.
9. Calculate Merkle root.
10. Set header fields.
11. Begin Proof-of-Work search.
```
Bitcoin Core implements candidate construction through its mining interfaces and block assembler.
---
## 12. The Coinbase Transaction
The first transaction in a block is the coinbase transaction.
It differs from ordinary transactions because it does not spend a previous transaction output.
Its input uses a null previous outpoint.
The coinbase transaction creates outputs paying the miner or mining pool.
The maximum permitted reward is:
```text
block subsidy
+
total fees from included transactions
```
The miner may claim less than the permitted maximum.
It may not claim more.
---
## 13. Coinbase Is Not an Exchange Coinbase
The term:
```text
coinbase transaction
```
is a Bitcoin protocol term.
It is unrelated to the cryptocurrency exchange named Coinbase.
In protocol context:
```text
coinbase transaction =
special first transaction in a block
```
---
## 14. Block Subsidy
The block subsidy is newly issued bitcoin permitted by the consensus subsidy schedule.
Conceptually:
```text
subsidy(height)
```
declines through periodic halvings.
The subsidy is not chosen by miners.
Nodes independently calculate the maximum subsidy permitted at the block height.
If a miner claims more than allowed:
```text
block is invalid
```
The exact subsidy schedule is studied in:
```text
BITCOIN-024 — Bitcoin Monetary Policy
BITCOIN-025 — Halving
```
---
## 15. Transaction Fees
For an ordinary transaction:
```text
fee =
sum(inputs)
-
sum(outputs)
```
The miner may claim the aggregate fees of the transactions included in its block.
Conceptually:
```text
maximum coinbase output value =
subsidy
+
sum(included transaction fees)
```
Fees are not a separate protocol token.
They are the difference between consumed and created transaction value.
---
## 16. Coinbase Maturity
Outputs created by a coinbase transaction cannot be spent immediately.
Bitcoin requires a maturity period before a coinbase output may be spent.
This protects the system against complications if the block creating the reward is removed during a chain reorganization.
Until maturity:
```text
coinbase output exists
but
cannot yet be validly spent
```
---
## 17. Block Height in the Coinbase
BIP34 requires the coinbase transaction's input script to begin with the block height.
This binds the coinbase transaction to a particular block height and helps make its transaction identifier distinct.
A simplified coinbase script may contain:
```text
block height
+
extra nonce
+
pool data
+
optional miner data
```
The permitted layout is constrained by consensus limits, but the full operational format is not globally standardized.
---
## 18. Extra Nonce
The block header's direct nonce contains only 32 bits.
Mining software therefore commonly places an extra nonce in the coinbase transaction.
Changing extra nonce data changes:
```text
coinbase bytes
↓
coinbase TXID
↓
Merkle root
↓
block header
↓
SHA256d output
```
This creates a new family of candidate block headers.
The extra nonce is not a dedicated block-header field.
---
## 19. SegWit Witness Commitment
A block containing SegWit transaction data must include the required witness commitment structure in the coinbase transaction.
This creates two related commitments:
- the traditional transaction Merkle root in the block header,
- the witness commitment carried through the coinbase transaction.
Candidate construction must calculate these commitments correctly.
A block with valid Proof of Work but an incorrect witness commitment remains invalid.
---
## 20. Merkle Root Construction
After selecting transactions and creating the coinbase transaction, the miner calculates the transaction Merkle root.
Conceptually:
```text
coinbase TXID
transaction TXID 1
transaction TXID 2
...
```
are combined through a binary hash tree until one root remains.
That root is placed in the block header:
```text
hashMerkleRoot
```
The Merkle root commits the header to:
- the transaction set,
- transaction order,
- coinbase transaction.
Changing one of these changes the root and creates a different Proof-of-Work input.
---
## 21. Candidate Block Header
The candidate header contains:
```text
version
previous_block_hash
merkle_root
timestamp
nBits
nonce
```
The miner must use the target required by consensus for the candidate's position in the chain.
A self-selected easier target does not become valid merely because the header hash satisfies it.
---
## 22. Proof-of-Work Search
For each candidate header:
```text
hash = SHA256d(serialized_header)
```
The header qualifies when:
```text
hash ≤ target
```
A simplified search loop is:
```text
for nonce in 0 .. 0xffffffff:
    header.nonce = nonce
    if SHA256d(header) ≤ target:
        submit block
```
When the direct nonce range does not contain a valid candidate, the miner changes another part of the block template and begins again.
---
## 23. Search-Space Expansion
Miners can create new candidate headers by changing:
- header nonce,
- coinbase extra nonce,
- transaction selection,
- transaction order,
- coinbase payout,
- timestamp within valid limits,
- version bits where permitted,
- witness-related coinbase data.
The mining process is better represented as:
```text
template generation
+
header-family generation
+
high-speed nonce search
```
not merely:
```text
guess nonce
```
---
## 24. ASIC Mining
An Application-Specific Integrated Circuit, or ASIC, is hardware designed for a narrow computational task.
Bitcoin mining ASICs are optimized for repeated double-SHA-256 block-header processing.
ASIC specialization can improve:
- hashes per second,
- energy efficiency,
- cost per hash.
ASICs do not change:
- SHA256d,
- target rules,
- block validity,
- chainwork calculation,
- node verification.
A node verifies an ASIC-mined block using the same consensus rules as any other block.
---
## 25. Mining Software vs ASIC
### Mining Software or Pool Server
Typically handles:
- block templates,
- transaction selection,
- coinbase construction,
- extra-nonce allocation,
- Merkle-root calculation,
- job distribution,
- share accounting,
- block submission.
### ASIC Hardware
Typically handles:
- high-throughput candidate hashing,
- nonce iteration,
- selected version rolling,
- reporting qualifying results.
The division is operational rather than a consensus requirement.
A different mining implementation may divide the work differently.
---
## 26. `getblocktemplate`
Bitcoin Core supports external mining software through the `getblocktemplate` RPC mechanism associated with BIP22 and extensions such as BIP23.
A template may provide information such as:
- block version,
- previous block hash,
- transactions,
- coinbase value,
- target,
- compact target,
- height,
- weight or size limits,
- mutable fields,
- required consensus rules.
The external miner constructs a compliant candidate block from this information.
`getblocktemplate` is an interface.
It is not the Bitcoin consensus algorithm itself.
---
## 27. Long Polling and Template Refresh
Mining on an outdated chain tip wastes work.
Mining interfaces may support long polling so mining software is notified when relevant state changes, such as:
- a new best block,
- material mempool changes,
- template invalidation.
A rapid template refresh reduces stale-work risk.
Mining latency directly affects expected revenue because work on an obsolete parent may no longer extend the selected chain.
---
## 28. Block Proposal Validation
Mining interfaces may allow a candidate block to be checked before expensive mining or final submission.
Proposal validation can detect issues such as:
- malformed transactions,
- invalid coinbase construction,
- incorrect commitments,
- block-limit violations.
This does not eliminate the need for final validation after Proof of Work is found.
The final serialized block may differ from the earlier proposal.
---
## 29. Solo Mining
In solo mining, a miner or mining organization:
- constructs or receives its own block templates,
- performs its own work,
- submits its own valid blocks,
- receives the full block reward when successful.
Expected revenue over a long period is proportional to the miner's share of network hash rate.
Payout variance can be extremely high.
A small miner may wait a very long time between block discoveries.
---
## 30. Expected Solo-Mining Block Rate
Let:
```text
h_miner = miner hash rate
H_network = total network hash rate
```
The miner's approximate share is:
```text
s = h_miner / H_network
```
If the network produces an average of:
```text
B blocks per unit time
```
then the miner's expected discoveries are:
```text
E[miner blocks] = s × B
```
This is an expectation.
Actual discovery is probabilistic.
A miner can experience long periods without finding a block even when continuously hashing.
---
## 31. Pool Mining
A mining pool aggregates work from many miners.
The pool typically:
- creates or coordinates jobs,
- assigns workers distinct work,
- sets share targets,
- verifies shares,
- submits network-valid blocks,
- distributes revenue according to a payout method.
Pooling reduces payout variance.
It does not alter Bitcoin's network target or block-validity rules.
---
## 32. Mining Shares
A share is a Proof-of-Work result satisfying a pool target that is usually easier than the network target.
```text
network_target < pool_share_target
```
A result may satisfy:
```text
hash ≤ pool_share_target
```
but fail:
```text
hash ≤ network_target
```
Such a result demonstrates work to the pool but is not a valid Bitcoin block.
Every network-valid result also satisfies an easier pool target.
Most pool shares do not satisfy the network target.
---
## 33. Why Pools Use Shares
A pool cannot directly observe every hash attempted by a remote miner.
Shares provide statistically verifiable evidence of work.
If a worker consistently submits shares at an assigned difficulty, the pool can estimate its contributed hash rate.
Shares enable:
- contribution measurement,
- frequent accounting,
- payout calculation,
- worker monitoring,
- hardware-failure detection.
Shares are usually off-chain operational data.
---
## 34. Variable Share Difficulty
Pools may assign different share difficulty to different workers.
A higher-hash-rate worker may receive a harder share target.
This reduces:
- network traffic,
- server verification load,
- excess low-difficulty submissions.
A lower-hash-rate worker may receive an easier target so shares arrive frequently enough for stable measurement.
Pool share difficulty does not affect:
- Bitcoin network difficulty,
- block chainwork,
- consensus rules,
- block rewards.
---
## 35. Pool Payout Methods
Common payout models include variations of:
- proportional,
- Pay Per Share,
- Full Pay Per Share,
- Pay Per Last N Shares,
- score-based systems.
These methods allocate:
- block reward risk,
- fee revenue,
- variance,
- operator risk
differently between miners and the pool.
Payout policy is not defined by Bitcoin consensus.
Institutional mining analysis should identify the exact pool contract rather than treating all pool mining as economically identical.
---
## 36. Pool Operator and Block Template Control
In traditional pool architectures, the pool operator may select:
- transactions,
- block template,
- coinbase payout,
- pool policy.
Workers contribute hashing power to that template.
This can concentrate transaction-selection power even when physical mining hardware is distributed.
Newer mining protocols and job-negotiation designs attempt to give individual miners or downstream operators greater template-selection influence.
Mining decentralization therefore has multiple layers:
- hash ownership,
- ASIC ownership,
- pool affiliation,
- template construction,
- payout control,
- geographic distribution,
- energy-source distribution.
---
## 37. Found Block Submission
When mining software finds a header satisfying the network target, it assembles the complete block and submits it to a node.
Submission may occur through:
- local node interfaces,
- mining RPCs,
- pool infrastructure,
- direct integration.
The receiving node does not accept the block solely because the miner labels it valid.
It runs independent validation.
---
## 38. Independent Block Validation
A node may validate:
### Header
- Proof of Work,
- expected target,
- previous-block reference,
- timestamp,
- version and deployment rules.
### Block Structure
- block serialization,
- transaction count,
- Merkle root,
- witness commitment,
- block weight.
### Transactions
- valid inputs,
- no prohibited double spends,
- script execution,
- value conservation,
- finality,
- lock-time rules.
### Coinbase
- first transaction position,
- correct form,
- permitted subsidy,
- permitted fee claim,
- height commitment,
- maturity rules for later spending.
A failure in any consensus-critical check makes the block invalid.
---
## 39. Valid Work Does Not Override Invalid Transactions
Suppose a miner finds an extremely difficult block hash but includes an invalid transaction.
Nodes reject it.
Proof of Work does not grant permission to violate consensus rules.
The protocol does not apply:
```text
more work
↓
more right to redefine validity
```
Instead:
```text
validity first
+
work comparison among valid candidates
```
Chainwork matters only among chains satisfying consensus rules.
---
## 40. Block Propagation
A successful miner benefits from distributing its block quickly.
If another miner finds a competing valid block at a similar time, different nodes may temporarily see different tips.
Fast propagation reduces the probability that the miner's block loses the race to become part of the eventual active chain.
Block propagation has been improved through mechanisms such as:
- compact block relay,
- high-connectivity relay networks,
- optimized validation,
- direct pool interconnection.
These are networking and implementation layers, not changes to the fundamental Proof-of-Work target.
---
## 41. Competing Blocks
Two valid blocks may extend the same parent.
Temporarily:
```text
Parent Block
├── Block A
└── Block B
```
Different nodes may first accept different branches.
Miners typically begin building on the valid branch their node currently selects.
When one branch accumulates more work, nodes converge on it.
Transactions in the losing block may return to mempools if they remain valid and unconfirmed.
The losing valid block is commonly called stale in modern operational discussion.
---
## 42. Stale Block vs Invalid Block
### Stale Block
A valid block that is not part of the eventual selected active chain.
Possible cause:
- another competing branch accumulated more work.
### Invalid Block
A block violating one or more consensus rules.
Examples:
- invalid Proof of Work,
- excessive reward,
- invalid transaction,
- incorrect Merkle root.
These categories must not be conflated.
A stale block may be technically valid.
An invalid block is never rescued by later chain selection.
---
## 43. Orphan Terminology
Historically, the term orphan block has been used inconsistently.
It may refer to:
- a valid block whose parent is not yet known,
- a stale valid block that lost a competing-chain race.
For precision, institutional documentation should distinguish:
```text
parent unknown
```
from:
```text
valid but stale branch
```
and avoid ambiguous terminology where possible.
---
## 44. Stale-Block Risk
A miner's probability of losing a near-simultaneous block race may increase with:
- slower propagation,
- weaker connectivity,
- delayed validation,
- geographic latency,
- slow template switching,
- pool infrastructure delays.
Larger blocks may take longer to transmit and validate, though modern relay mechanisms reduce this effect.
Stale risk is an economic cost because a losing block normally earns no main-chain subsidy or fees.
---
## 45. Mining Revenue
For a successful active-chain block:
```text
gross block revenue =
subsidy
+
transaction fees
```
Expected miner revenue depends on:
```text
miner hash share
×
expected network block production
×
expected reward per block
```
Pool fees and payout rules modify the miner's received amount.
Revenue is usually denominated operationally in bitcoin before conversion into local currency.
---
## 46. Mining Costs
Mining costs may include:
- electricity,
- ASIC purchase,
- facility construction,
- cooling,
- maintenance,
- labor,
- pool fees,
- firmware,
- networking,
- financing,
- taxes,
- insurance,
- curtailment opportunity cost.
The blockchain does not report these costs.
They must be estimated from external operational and market data.
---
## 47. Miner Profitability
A simplified model is:
```text
profit =
mining revenue
-
operating cost
-
capital cost
-
financing cost
```
Revenue drivers include:
- BTC price,
- subsidy,
- transaction fees,
- miner hash rate,
- network difficulty,
- uptime,
- pool payout.
Cost drivers include:
- energy price,
- ASIC efficiency,
- facility efficiency,
- maintenance,
- debt.
Difficulty alone cannot determine profitability.
---
## 48. Hash Price
Mining analysts often use a metric representing expected miner revenue per unit of hash rate over time.
Conceptually:
```text
hash price =
expected network mining revenue
/
network hash rate
```
Its exact unit and methodology depend on the data provider.
Hash price may respond to:
- BTC price,
- fees,
- subsidy,
- network difficulty,
- hash-rate competition.
It is an analytical metric, not a Bitcoin consensus variable.
---
## 49. Energy as a Security Input
Proof of Work intentionally makes block production costly.
However, nodes do not verify electricity consumption.
They verify:
```text
SHA256d(header) ≤ target
```
Energy consumption emerges from miners competing to produce valid hashes.
The protocol observes only successful cryptographic outputs.
It does not observe:
- electricity source,
- exact joules consumed,
- carbon intensity,
- miner cost basis.
Energy claims require external data and explicit methodology.
---
## 50. Is Mining Computation Useful Outside Bitcoin?
Bitcoin mining computation is optimized to search for qualifying block-header hashes.
The computation's protocol purpose is:
- costly leader selection,
- chainwork production,
- history-rewrite resistance.
It is not designed to produce a separate scientific result such as:
- protein folding,
- weather simulation,
- AI training.
Attempts to replace mining with externally useful work face additional verification, unpredictability, and incentive-design problems.
The relevant question is not whether the hash has external reuse.
It is whether the computation provides Bitcoin's intended security properties.
---
## 51. Mining and Transaction Censorship
A miner may choose not to include a transaction in its own candidate block.
That does not automatically prevent another miner from including it.
Persistent censorship becomes more plausible when a sufficiently large share of block producers:
- coordinate exclusion,
- refuse to build on blocks containing selected transactions,
- enforce out-of-band policies.
Censorship analysis should distinguish:
- one-block omission,
- fee-based exclusion,
- temporary propagation failure,
- coordinated long-term censorship,
- consensus-level invalidation.
Miner transaction selection is not the same as node consensus validity.
---
## 52. Mining and Consensus Changes
Miners may signal support for protocol changes through block-version mechanisms.
However, miner signaling alone does not necessarily determine the consensus rules enforced by validating nodes.
A protocol upgrade may involve:
- developers,
- node operators,
- miners,
- exchanges,
- wallets,
- businesses,
- users.
Mining influence is significant but not unlimited.
A miner producing blocks rejected by the economic network earns no usable main-chain reward.
---
## 53. Mining Centralization Dimensions
Mining decentralization cannot be measured by pool share alone.
Relevant dimensions include:
| Dimension | Example Question |
|---|---|
| Pool concentration | How much reported hash rate points to each pool? |
| Hardware ownership | Who owns the ASICs? |
| Manufacturer concentration | How many firms produce competitive ASICs? |
| Template control | Who selects transactions? |
| Geographic concentration | Where are facilities located? |
| Energy concentration | Do miners depend on the same grid or supplier? |
| Firmware control | Who controls mining-device software? |
| Custodial exposure | Who controls payout keys? |
| Financing concentration | Are miners dependent on the same lenders? |
One entity may operate hardware while another controls pool templates.
Pool labels are not equivalent to beneficial ownership.

## 54. On-Chain Mining Data
The blockchain directly exposes or permits derivation of:
- block headers,
- winning nonce,
- `nBits`,
- block timestamp,
- coinbase transaction,
- claimed reward,
- transaction fees,
- Merkle root,
- block weight,
- transaction set,
- coinbase tags,
- block intervals,
- difficulty changes.
The blockchain does not directly expose:
- losing hashes,
- exact miner hash rate,
- electricity consumption,
- hardware model,
- power price,
- facility location,
- miner identity,
- ownership structure,
- pool contract,
- actual profit.
Institutional analysis must separate direct observations from estimates.

## 55. Miner Identification
Mining pools sometimes include recognizable tags in coinbase input data or pay rewards to known output patterns.
Analysts may use these signals to attribute blocks to pools.
Attribution remains heuristic.
A label may be:
- copied,
- changed,
- omitted,
- proxied,
- used by multiple downstream miners.
Therefore:
```text
coinbase tag
≠
cryptographically proven beneficial owner
```

## 56. Hash-Rate Estimation
Network hash rate is inferred from:
- target or difficulty,
- observed block production.
A conceptual estimator is:
```text
estimated hash rate =
expected hashes per block
/
observed average block interval
```
Because block arrivals are probabilistic, short-window estimates are noisy.
A credible analysis should state:
- window length,
- estimator,
- confidence interval,
- recent retarget timing,
- treatment of stale blocks.
---
## 57. Miner Revenue From On-Chain Data
For a block:
```text
fees =
sum(transaction inputs)
-
sum(non-coinbase transaction outputs)
```
The coinbase claim can be compared with:
```text
permitted subsidy
+
fees
```
Analysts can measure gross on-chain block revenue.
They cannot derive net miner profit without external cost information.
---
## 58. Fee-Sniping Incentive
When a previous block contains unusually high fees, a miner may theoretically consider attempting to replace it to capture those fees.
This is known as fee sniping.
The incentive depends on:
- miner hash share,
- fee amount,
- reorganization depth,
- competing-chain probability,
- opportunity cost,
- network response.
Lock-time behavior and mining incentives have historically considered this risk.
Fee sniping demonstrates that mining incentives involve more than simply extending the visible tip.
---
## 59. Empty Blocks
A miner may publish a block containing only a coinbase transaction.
Such a block can be consensus-valid.
Possible causes include:
- rapid mining immediately after receiving a new header,
- template-construction delay,
- miner policy,
- infrastructure design,
- temporary mempool differences.
An empty block does not necessarily prove that no transactions were available globally.
It reflects one miner's candidate construction and timing.
---
## 60. Block Template Updates
A miner may refresh a template when:
- a new parent block arrives,
- high-fee transactions arrive,
- timestamp needs updating,
- extra-nonce space changes,
- policy changes,
- transaction conflicts appear.
Frequent refresh can improve fee capture but may impose operational overhead.
Mining systems balance:
- search continuity,
- template freshness,
- propagation,
- fee optimization.

## 62. Simplified Mining Pseudocode
```python
while True:
    tip = node.get_active_chain_tip()
    target = node.get_required_target(tip)
    transactions = select_valid_transactions(
        mempool=node.mempool,
        max_block_weight=MAX_BLOCK_WEIGHT
    )
    for extra_nonce in extra_nonce_range:
        coinbase = build_coinbase_transaction(
            height=tip.height + 1,
            extra_nonce=extra_nonce,
            subsidy=get_block_subsidy(tip.height + 1),
            fees=sum_transaction_fees(transactions),
            payout_script=miner_payout_script
        )
        block_transactions = [coinbase] + transactions
        witness_commitment = build_witness_commitment(block_transactions)
        merkle_root = calculate_merkle_root(block_transactions)
        header = build_header(
            version=choose_version(),
            previous_block_hash=tip.hash,
            merkle_root=merkle_root,
            timestamp=current_valid_time(),
            nbits=encode_compact(target),
            nonce=0
        )
        for nonce in range(0, 2**32):
            if node.active_tip_changed(tip):
                break
            header.nonce = nonce
            block_hash = sha256d(serialize(header))
            if block_hash <= target:
                block = assemble_block(
                    header,
                    block_transactions
                )
                if node.validate_and_submit(block):
                    return block
        if node.active_tip_changed(tip):
            break
```
Real systems distribute this process across nodes, pool servers, mining protocols, firmware, and ASIC hardware.

## 63. Institutional Thinking
### Observation
A mining pool produced 30% of blocks during a selected period.
### Weak Conclusion
> One company owns 30% of Bitcoin mining hardware and can unilaterally control the network.
### Institutional Decomposition
Ask:
1. Does the pool own the connected ASICs?
2. Can miners redirect hash rate quickly?
3. Who constructs block templates?
4. Does the pool support job negotiation?
5. Are coinbase labels reliable?
6. Is the measurement window long enough?
7. How concentrated are ASIC manufacturers?
8. Where are physical facilities located?
9. Who owns payout keys?
10. Is hash rate stable or transient?
11. Could coordinated pools exceed a security threshold?
12. Which attack is actually being evaluated?
### Conclusion
Pool block share measures one layer of mining concentration.
It does not fully measure:
- hardware ownership,
- geographic distribution,
- economic control,
- template control,
- coordinated behavior.

## 65. Common Misinterpretations
### Misinterpretation 1
> Mining is only nonce guessing.
Incorrect.
Mining includes candidate-block construction, Proof-of-Work search, submission, and network validation.
---
### Misinterpretation 2
> Miners validate the network and nodes merely observe.
Incomplete.
Miners construct and propose blocks. Fully validating nodes independently enforce consensus rules.
---
### Misinterpretation 3
> A miner may include any transaction after finding sufficient work.
Incorrect.
Invalid transactions make the block invalid regardless of work.
---
### Misinterpretation 4
> Mining pools own all hash rate attributed to them.
Incorrect.
Pools often coordinate independently owned mining hardware.
---
### Misinterpretation 5
> A share is a nearly valid Bitcoin block.
Imprecise.
A share satisfies a pool-defined target. It may be far easier than the network target.
---
### Misinterpretation 6
> Hash rate is directly recorded on-chain.
Incorrect.
It is statistically inferred.
---
### Misinterpretation 7
> The coinbase transaction is created by the Coinbase exchange.
Incorrect.
The terms are unrelated.
---
### Misinterpretation 8
> Miners can issue any amount of bitcoin.
Incorrect.
Nodes reject excessive coinbase rewards.
---
### Misinterpretation 9
> A stale block is invalid.
Incorrect.
It may be fully valid but excluded from the selected chain.
---
### Misinterpretation 10
> Higher difficulty automatically improves every miner's profit.
Incorrect.
Higher difficulty generally increases competition per unit of hash power.
---
### Misinterpretation 11
> Mining energy consumption is directly visible in block data.
Incorrect.
Energy use requires external estimation.
---
### Misinterpretation 12
> A pool with the largest share can permanently censor transactions by itself.
Incomplete.
The answer depends on its sustained hash share, other miners' behavior, branch strategy, and economic response.

## 66. Counter Evidence and Limitations
The mining architecture described here is representative, not universal.
Mining systems may use:
- custom block-template providers,
- private relay networks,
- specialized firmware,
- proprietary pool protocols,
- Stratum variants,
- merged-mining infrastructure,
- remote hosting arrangements,
- alternative payout systems.
Bitcoin consensus defines valid blocks.
It does not prescribe one mining business model or hardware architecture.
Documentation of commercial mining operations is often incomplete.
Analysts should avoid treating:
- pool APIs,
- coinbase labels,
- manufacturer specifications,
- corporate disclosures
as equally reliable evidence.
