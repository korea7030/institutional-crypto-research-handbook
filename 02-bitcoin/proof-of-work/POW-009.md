## 3. Executive Summary

The coinbase transaction is the special first transaction in a Bitcoin block. It has exactly one input, and that input uses a null previous outpoint because it does not spend a prior transaction output.[^ref-btc-dev-tx]

The coinbase transaction performs three major functions:

```text
miner compensation
+
mining search-space extension
+
protocol commitments
```

Miner compensation is constrained. A miner may claim the block subsidy plus the total fees from included non-coinbase transactions, but a validating node rejects a block if the coinbase pays more than that limit.[^ref-btc-core-validation]

The coinbase transaction is also a commitment surface. BIP34 requires the coinbase script to begin with the block height.[^ref-bip-0034] BIP141 commits SegWit witness data through a witness Merkle root and a coinbase output commitment.[^ref-bip-0141]

Finally, the coinbase transaction is part of mining mechanics. Changing coinbase script data changes the coinbase transaction ID, which changes the block Merkle root, which changes the block header, which changes the Proof-of-Work search input. This is why miners commonly use coinbase extra nonce data after exhausting or partitioning the 32-bit header nonce space.[^ref-btc-dev-tx][^ref-btc-dev-mining]

---

## 4. Definition and Scope

A coinbase transaction is the first transaction in a Bitcoin block. It is the only transaction in the block that creates spendable outputs without consuming previous transaction outputs.

This does not mean miners can create arbitrary bitcoin. The maximum coinbase output value is constrained by consensus:

```text
maximum coinbase value = block subsidy + included transaction fees
```

The term `coinbase` here is a Bitcoin protocol term. It is unrelated to the company or exchange named Coinbase.

This document focuses on the coinbase transaction as a Proof-of-Work and block-construction component. Monetary policy, mining-pool reward distribution, and complete SegWit transaction semantics are covered elsewhere.

## 5. Historical Background

The Bitcoin Whitepaper introduces the economic function of the first transaction in Section 6. It states that the first transaction in a block starts a new coin owned by the block creator and adds an incentive for nodes to support the network.[^ref-btc-wp]

The original whitepaper does not describe BIP34 block-height encoding or SegWit witness commitments. Those are later protocol changes.

BIP34, assigned on 2012-07-06, added the block height as the first item in the coinbase transaction's scriptSig. Its stated motivations included enforcing transaction uniqueness and assisting unconnected block validation.[^ref-bip-0034]

BIP141, assigned on 2015-12-22, added Segregated Witness and introduced a witness commitment structure recorded in the coinbase transaction. This lets witness data be committed to blocks while preserving soft-fork compatibility.[^ref-bip-0141]

## 6. Original Design

In the original Bitcoin design, the coinbase transaction is mainly an incentive mechanism:

```text
successful block creation
↓
first transaction creates reward
↓
miner is compensated
```

The whitepaper frames this reward as a way to initially distribute coins and to encourage nodes to contribute CPU power to the network.[^ref-btc-wp]

Modern Bitcoin preserves that incentive role but adds additional consensus and commitment roles:

- the coinbase must be first,
- only one coinbase transaction is allowed,
- the coinbase script must begin with the block height after BIP34 activation,
- the coinbase may contain the SegWit witness commitment after SegWit activation,
- the coinbase reward must not exceed subsidy plus fees.

The original design intent and current implementation should therefore be separated. The whitepaper explains why the reward exists. Current specifications and implementation define how modern blocks must encode and validate it.

---

## 7. Protocol Structure

The coinbase transaction has the same broad transaction container as other transactions:

```text
version
inputs
outputs
lock_time
```

Its input is special. Bitcoin Developer documentation describes the coinbase input as using:

| Field | Coinbase value |
|---|---|
| Previous outpoint hash | 32-byte null value |
| Previous outpoint index | `0xffffffff` |
| Script bytes | Length of the coinbase script, up to 100 bytes |
| Script contents | Block height plus miner-controlled data |
| Sequence | Sequence number |

The first transaction in a block must be coinbase, and later transactions must not be coinbase. Bitcoin Core's `CheckBlock` enforces this shape with `bad-cb-missing` and `bad-cb-multiple` failure paths.[^ref-btc-dev-tx][^ref-btc-core-validation]

The coinbase transaction's outputs usually pay the miner, pool, or payout script. They may also include special zero-value `OP_RETURN` outputs, such as the SegWit witness commitment output.[^ref-bip-0141]

## 8. Technical Mechanics

### 8.1 Reward Claim

For each included non-coinbase transaction:

```text
fee = sum(inputs) - sum(outputs)
```

The block's maximum coinbase output value is:

```text
block_reward_limit = subsidy(height) + sum(included_fees)
```

Bitcoin Core constructs a candidate coinbase using `nFees + GetBlockSubsidy(height, consensusParams)` in `BlockAssembler::CreateNewBlock`.[^ref-btc-core-miner]

During block connection, Bitcoin Core accumulates transaction fees from non-coinbase transactions and rejects a block with `bad-cb-amount` if the first transaction pays more than the calculated reward limit.[^ref-btc-core-validation]

### 8.2 Block Height Commitment

BIP34 requires the coinbase transaction's scriptSig to begin with the block height using minimally encoded serialized `CScript` form.[^ref-bip-0034]

Bitcoin Core constructs the candidate coinbase scriptSig with the next block height. During contextual block validation, it computes the expected height script and rejects a block with `bad-cb-height` if the coinbase script does not begin with the expected encoding after the height-in-coinbase deployment is active.[^ref-btc-core-miner][^ref-btc-core-validation]

### 8.3 Extra Nonce Search Space

The block header contains a 32-bit nonce. Large miners can exhaust 32-bit nonce ranges quickly or divide nonce ranges among devices. They therefore need additional ways to produce new candidate headers.

One common mechanism is to change arbitrary data in the coinbase script after the required BIP34 height prefix. This data is commonly called an extra nonce.

The dependency chain is:

```text
change extra nonce
↓
change coinbase transaction bytes
↓
change coinbase txid
↓
change transaction Merkle root
↓
change block header
↓
change Proof-of-Work hash stream
```

The extra nonce is an operational convention, not a named consensus field. Consensus constrains the coinbase script shape and size, but it does not globally standardize pool tags or extra nonce layout.[^ref-btc-dev-tx][^ref-btc-dev-mining]

### 8.4 SegWit Witness Commitment

BIP141 adds a witness commitment rule. For blocks containing witness data, the coinbase transaction includes a commitment output whose script begins with:

```text
OP_RETURN 0x24 0xaa21a9ed
```

followed by a 32-byte commitment hash.[^ref-bip-0141]

BIP141 defines the coinbase transaction's `wtxid` as all zeroes for witness Merkle tree construction. The coinbase input witness must contain a single 32-byte witness reserved value. The commitment hash is:

```text
Double-SHA256(witness root hash | witness reserved value)
```

Bitcoin Core's `GenerateCoinbaseCommitment` creates the witness commitment output when needed, and `ContextualCheckBlock` validates witness commitments after SegWit activation.[^ref-btc-core-validation]

## 9. Mathematical or Economic Model

Let:

- `S(h)` be the block subsidy at height `h`.
- `F_i` be the fee paid by included non-coinbase transaction `i`.
- `C` be the total output value of the coinbase transaction.

The consensus reward constraint is:

```text
C <= S(h) + Σ F_i
```

Where:

```text
F_i = input_value_i - output_value_i
```

Toy example:

```text
subsidy at height h: 3.125 BTC
included fees:       0.080 BTC
maximum coinbase:    3.205 BTC
```

If the coinbase outputs sum to `3.204 BTC`, the miner has underclaimed by `0.001 BTC`. That block can still satisfy the reward constraint.

If the coinbase outputs sum to `3.206 BTC`, the block exceeds the reward limit and is invalid.

This model is exact only if all transaction input values and output values are known from the UTXO set and the block's transaction list. Fee estimation from mempool data before mining is observer-specific and not consensus evidence.

## 10. Security Assumptions

Coinbase validation relies on independent full-node verification. Miners do not self-certify their reward.

The main security assumptions are:

- nodes can identify the first transaction as coinbase,
- non-coinbase transactions are checked against the UTXO set,
- fees can be computed from consumed and created values,
- subsidy can be computed from height and consensus parameters,
- BIP34 height commitment is checked after activation,
- witness commitments are checked after SegWit activation,
- the Merkle root in the header matches the transaction list.

Proof of Work does not replace any of these checks. A block with valid Proof of Work but an excessive coinbase reward, missing height commitment, or invalid witness commitment remains invalid.

---

## 11. Failure Modes and Attack Surface

### Excess Coinbase Reward

A miner can construct a block whose coinbase pays too much. Nodes reject it because the first transaction's output value exceeds subsidy plus fees.[^ref-btc-core-validation]

### Missing or Incorrect BIP34 Height

After BIP34 activation, the coinbase script must begin with the block height. A block with the wrong height prefix is invalid even if its Proof of Work is valid.[^ref-bip-0034][^ref-btc-core-validation]

### Incorrect Witness Commitment

After SegWit activation, a block with witness data must satisfy the witness commitment rules. An invalid witness commitment is a consensus failure.[^ref-bip-0141][^ref-btc-core-validation]

### Misleading Miner Tags

Coinbase script data often contains pool names or tags. These tags are not authenticated identity claims. A miner can omit, alter, or imitate a tag.

### Commitment Surface Abuse

The coinbase transaction can carry arbitrary or semi-arbitrary data within constraints. Analysts must distinguish consensus-required commitments from non-consensus metadata.

## 12. Bitcoin Core or Protocol Implementation

Bitcoin Core's `BlockAssembler::CreateNewBlock` constructs a candidate block by adding a placeholder coinbase, selecting transactions, calculating fees, constructing the coinbase, setting the BIP34 height prefix, generating the coinbase commitment, and filling header fields.[^ref-btc-core-miner]

Important construction steps include:

```text
coinbase input prevout = null
coinbase reward = nFees + GetBlockSubsidy(height)
coinbase scriptSig starts with block height
GenerateCoinbaseCommitment(...)
hashMerkleRoot = BlockMerkleRoot(block)
```

Bitcoin Core's validation path enforces the corresponding rules:

- `CheckBlock` requires the first transaction to be coinbase and later transactions not to be coinbase.
- `ContextualCheckBlock` checks the BIP34 height prefix.
- `ContextualCheckBlock` checks witness commitments.
- `ConnectBlock` accumulates fees and rejects excessive coinbase output value.

These checks show that coinbase validity is distributed across context-free block checks, context-dependent block checks, and UTXO-dependent connection checks.[^ref-btc-core-validation]

## 13. Related Standards and BIPs

### BIP34 — Block v2, Height in Coinbase

BIP34 added the block height as the first item in the coinbase scriptSig. It was deployed as a soft fork and is now part of modern Bitcoin consensus behavior.[^ref-bip-0034]

### BIP141 — Segregated Witness

BIP141 added witness data and a coinbase witness commitment structure. The witness commitment is nested into the block through the coinbase transaction for soft-fork compatibility.[^ref-bip-0141]

### Whitepaper Section 6 — Incentive

The whitepaper's incentive section explains the original rationale for the first transaction in a block creating the miner reward.[^ref-btc-wp]

## 14. Modern Context

In modern Bitcoin, the coinbase transaction is no longer just a reward transaction. It is a multi-purpose block-construction object.

It is:

- the block's reward claim,
- the first leaf in the transaction Merkle tree,
- a miner-controlled search-space surface,
- the BIP34 block-height commitment carrier,
- the SegWit witness commitment carrier,
- a common location for mining-pool tags.

This multi-purpose role is why changing the coinbase transaction can affect consensus validity, mining search space, and analyst interpretation at the same time.

## 15. On-Chain Implications

### Directly Observable

An on-chain analyst can observe:

- the coinbase transaction,
- the coinbase input's null previous outpoint,
- the coinbase script bytes,
- the BIP34 height prefix,
- coinbase outputs,
- the aggregate coinbase output value,
- the witness commitment output when present,
- miner or pool tags if embedded,
- the Merkle root in the block header.

### Deterministically Derivable

An analyst can derive:

- whether the coinbase is first,
- whether there is exactly one coinbase transaction,
- the transaction fees of included non-coinbase transactions if the spent UTXOs are known,
- whether coinbase output value exceeds subsidy plus fees,
- whether the coinbase transaction affects the Merkle root as expected.

### Estimated or Inferred

An analyst may estimate or infer:

- mining-pool attribution from coinbase tags,
- extra nonce position,
- miner template structure,
- payout distribution,
- private miner identity.

### Unobservable From Chain Alone

An analyst cannot know from coinbase data alone:

- the physical miner operating the hardware,
- the pool's private payout ledger,
- whether a tag is truthful,
- all devices that contributed hashes,
- the exact off-chain extra nonce assignment policy.

## 16. Institutional Thinking

### Observation

A block's coinbase script contains a recognizable pool tag.

### Weak Interpretation

"This pool definitely mined the block and controls the underlying hash hardware."

### Institutional Decomposition

An institutional researcher should separate:

- block producer tag,
- pool server identity,
- hash-rate contributor identity,
- payout address ownership,
- pool payout records,
- network first-seen data,
- external miner disclosures.

### Current Conclusion

Coinbase tags are useful attribution evidence, but they are not cryptographic identity proofs. They should be treated as moderate-confidence evidence only when corroborated by independent data.

### Confidence

FACT — ECL-A for the presence of bytes in the coinbase transaction.  
INTERPRETATION — ECL-B or ECL-C for pool attribution, depending on corroborating evidence.

## 17. Analyst Notes

Do not treat the coinbase transaction as an ordinary payment transaction. It creates the block reward and does not spend a previous output.

When analyzing miner revenue, distinguish:

```text
claimed coinbase output value
from
maximum permitted reward
from
actual miner or pool payout
```

The first two can be analyzed from chain data and UTXO context. The third often requires off-chain pool records.

When analyzing search space, distinguish:

```text
header nonce
from
extra nonce inside coinbase script data
```

The header nonce is an explicit block-header field. Extra nonce is an operational use of coinbase script data.

## 18. Common Misinterpretations

### Misinterpretation

> The coinbase transaction spends newly created bitcoin from a hidden protocol account.

### Assessment

Incorrect.

### Correction

The coinbase transaction has no previous outpoint. It creates outputs under the block subsidy and fee rules.

### Misinterpretation

> Miners can choose any reward amount they want.

### Assessment

Incorrect.

### Correction

Miners can claim at most subsidy plus included transaction fees. Nodes reject blocks that claim more.

### Misinterpretation

> The coinbase script is entirely arbitrary.

### Assessment

Incomplete.

### Correction

Some coinbase script data is miner-controlled, but modern consensus requires the script to begin with the BIP34 block-height encoding.

### Misinterpretation

> Extra nonce is a block-header field.

### Assessment

Incorrect.

### Correction

Extra nonce is commonly placed in the coinbase transaction. Changing it changes the Merkle root and therefore the block header.

### Misinterpretation

> A coinbase tag proves miner identity.

### Assessment

Unsupported.

### Correction

A tag proves that certain bytes appear in the coinbase transaction. Identity attribution requires additional evidence.

## 19. Counter Evidence and Limitations

The whitepaper explains the original reward rationale but does not describe BIP34 or SegWit. Current coinbase behavior must be checked against later BIPs and implementation.

Bitcoin Developer documentation describes common coinbase fields and format, but implementation and consensus checks should be consulted for exact current behavior.

Bitcoin Core mining construction is not the only possible block-construction implementation. It is strong evidence for Bitcoin Core behavior, but consensus validity is determined by rules all compatible implementations must follow.

Pool tags are not authenticated. Attribution research must avoid treating visible strings as proof of ownership or intent.

Coinbase output value does not necessarily equal realized miner income. Pools may distribute rewards later, charge fees, smooth payouts, or use internal accounting.
