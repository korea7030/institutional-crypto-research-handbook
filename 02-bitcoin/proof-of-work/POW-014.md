## 3. Executive Summary

Bitcoin Proof of Work is a cost-based ordering mechanism. It makes history expensive to rewrite because changing a past block requires redoing that block's work and enough later work to overtake the honest chain's cumulative work.[^ref-btc-wp] Bitcoin Core implements this by validating block headers against their encoded targets and by selecting the valid chain with the most accumulated work.[^ref-btc-core-pow][^ref-btc-core-validation]

The central attack model is not "breaking SHA-256." It is controlling enough block-production probability, propagation advantage, or victim network view to make a competing valid history more attractive to some node or counterparty than the history the victim expected.

The classic double-spend attack is a race. An attacker pays a merchant in the public chain while privately mining an alternative chain that spends the same coins back to the attacker. If the private chain catches up and surpasses the public chain in cumulative work, honest nodes can reorganize to the attacker's valid alternative history.[^ref-btc-wp]

Proof of Work does not allow invalid coins to be created. Nakamoto's analysis is explicit that attackers cannot make nodes accept invalid transactions or blocks; the attacker's practical target is changing the ordering or inclusion of the attacker's own recent transactions.[^ref-btc-wp]

Attack models fall into five practical buckets:

| Attack Model | Primary Goal | Main Resource | Core Risk |
|---|---|---|---|
| Double-spend reorg | Reverse a recent payment | Hashrate and time | Counterparty finality loss |
| Majority attack | Reliably rewrite or censor recent history | Majority or near-majority hashpower | Chain liveness and settlement risk |
| Selfish mining | Earn more revenue than proportional hash share | Hashrate plus propagation advantage | Mining centralization pressure |
| Eclipse-assisted attack | Control a victim's chain view | Network-positioning resources | Victim-specific false finality |
| Difficulty/timestamp manipulation | Distort future mining conditions | Coordinated mining power | Block-interval and difficulty instability |

For analysts, the key distinction is between global consensus risk and victim-local perception risk. A public reorg is globally observable after it occurs. A pending private fork is not directly observable. An eclipse attack against one victim may be invisible to the public chain until the victim's local decisions are compared with the wider network view.

## 4. Original Design

The Bitcoin whitepaper frames Proof of Work as a mechanism for ordering history without a trusted timestamping authority. The "longest chain" represents the greatest accumulated proof-of-work effort in the original description.[^ref-btc-wp] Later implementation and documentation are more precise: nodes follow the valid chain with the most cumulative work, not merely the greatest block count.[^ref-btc-dev-blockchain][^ref-btc-dev-operating]

The security claim is probabilistic. If honest miners control more hashpower than a cooperating attacker group, honest miners are expected to extend the honest chain faster than the attacker extends a conflicting chain.[^ref-btc-wp] As confirmations accumulate, the attacker's required catch-up work increases.

The original design also defines an important limit on the attacker's power. Even if an attacker generates an alternate chain faster, honest nodes still validate transactions and blocks. An attacker cannot create value out of nothing, spend coins without valid authorization, or force honest full nodes to accept invalid blocks.[^ref-btc-wp]

This produces a practical model:

1. Consensus rules define which blocks are valid.
2. Proof of Work orders competing valid histories.
3. Cumulative work determines which valid history full nodes select.
4. Confirmations measure growing replacement cost, not absolute irreversibility.
5. Adversaries attack ordering, propagation, incentives, and local visibility.

## 5. Protocol Structure

### Defensive Layers

Bitcoin's PoW security depends on multiple layers:

| Layer | Defensive Role | Attack Surface |
|---|---|---|
| Cryptographic hash function | Makes block search unpredictable | ASIC concentration, not practical hash inversion |
| Target and difficulty rules | Normalize expected block interval | Timestamp manipulation, difficulty transition edge cases |
| Cumulative chainwork | Selects the most-work valid chain | Private-fork competition |
| Full validation | Rejects invalid blocks and transactions | Node isolation or weak client assumptions |
| Peer-to-peer relay | Distributes blocks and transactions | Eclipse, partition, propagation advantage |
| Miner incentives | Rewards honest extension | Selfish mining, withholding, fee-driven reorg incentives |

Proof of Work is not a single security switch. A block can satisfy its hash target but still be invalid because it violates transaction, merkle-root, coinbase, version, or contextual rules.[^ref-btc-core-validation] Conversely, a block may be fully valid but still lose a chain race if another valid branch accumulates more work.

### Attack Surfaces

PoW attacks usually target one or more of the following:

| Surface | Question |
|---|---|
| Hashrate share | Can the attacker produce blocks fast enough to compete? |
| Time | How long can the attacker keep the race open? |
| Confirmations | How much honest work must the attacker replace? |
| Propagation | Can the attacker shape which blocks miners see first? |
| Network view | Can the attacker isolate a victim from honest peers? |
| Economic incentives | Is the attack more profitable than honest mining? |
| Difficulty rules | Can timestamp or retarget behavior be exploited? |

### Failure Modes

| Failure Mode | Description | Global or Local |
|---|---|---|
| Public reorg | A previously accepted branch is replaced by a higher-work branch | Global once propagated |
| Private-fork success | A hidden branch overtakes the public branch | Global after release |
| Censorship | Transactions are excluded or delayed by dominant miners | Global if sustained |
| Stale-block increase | More blocks lose propagation races | Global symptom |
| Victim eclipse | A victim sees an adversarial network view | Local until compared |
| Incentive deviation | Miners withhold or selectively publish blocks | Partly hidden |

## 6. Technical Mechanics

### Model 1: Double-Spend Reorganization

A double-spend reorganization has four stages:

1. The attacker creates a public transaction paying the victim.
2. The victim waits for confirmations on the public chain.
3. The attacker privately mines a conflicting valid branch that excludes or replaces that payment.
4. If the private branch accumulates more work, the attacker publishes it and honest nodes may reorganize to it.

The attack uses valid blocks. It does not require invalid transactions. It exploits the fact that recent chain history is probabilistic until the replacement cost becomes economically and statistically prohibitive.

The whitepaper's scenario is a sender who wants the recipient to believe payment occurred, then later switches to an alternative transaction paying back to himself.[^ref-btc-wp]

### Model 2: Majority-Hashrate Attack

A majority-hashrate attacker has an expected growth rate greater than the honest chain. This changes a probabilistic attack into a reliable or eventually reliable attack under the model assumptions. With majority hashpower, the attacker can attempt to:

- reverse the attacker's own recent payments;
- censor selected transactions by refusing to include them;
- orphan blocks found by honest miners;
- create instability around settlement finality;
- selectively reveal private branches.

The attacker still cannot:

- create coins beyond consensus subsidy and fee rules;
- spend coins without valid signatures;
- make invalid scripts valid;
- make honest full nodes accept invalid blocks;
- change past history without doing the required replacement work.

This distinction matters for institutional risk. Majority hashpower threatens settlement ordering and liveness. It does not remove full-node validation.

### Model 3: Selfish Mining

Selfish mining is an incentive attack. The selfish miner withholds discovered blocks instead of publishing immediately. Honest miners continue mining on the public chain, while the selfish miner privately extends its branch. The selfish miner releases blocks strategically when the public branch threatens to catch up or when release can waste honest mining work.[^ref-eyal-sirer]

Eyal and Sirer's model argues that the Bitcoin mining protocol is not strictly incentive-compatible under all network and propagation assumptions. The model's risk is not only immediate chain rewrite. It is that a miner or pool may earn more than its proportional hash share, making strategic withholding attractive and encouraging mining concentration.[^ref-eyal-sirer]

Selfish mining depends on:

- attacker hashpower share;
- propagation advantage during block races;
- honest miners' tie-breaking behavior;
- the ability to keep private blocks secret;
- the economic payoff of higher relative revenue.

For analysts, selfish mining may appear through elevated stale rates, suspiciously timed block releases, and abnormal orphaning patterns. It is difficult to prove from public chain data alone because a private withheld block is invisible until it is published.

### Model 4: Eclipse-Assisted Attacks

An eclipse attack targets a victim's peer-to-peer network view. The Heilman, Kendler, Zohar, and Goldberg paper describes an adversary monopolizing all connections to and from a victim Bitcoin node. Once isolated, the victim can be shown an adversarial view of blocks and transactions.[^ref-heilman-eclipse]

This can amplify PoW attacks in three ways:

1. Victim-specific double spend: the victim sees confirmations that the wider network does not treat the same way.
2. Mining disruption: an eclipsed miner can waste hashpower on stale or adversarial branches.
3. Fork manipulation: the victim may receive blocks late, selectively, or in a distorted order.

An eclipse attack does not automatically change global chain selection. It changes what the victim sees. The risk is highest for services that make high-value decisions from a small number of peers or from externally hosted node infrastructure.

### Model 5: Difficulty and Timestamp Manipulation

Difficulty adjustment is part of the PoW attack surface because target rules convert observed block times into future target values. Bitcoin Core's `CalculateNextWorkRequired` constrains retargeting through the consensus interval and timespan limits.[^ref-btc-core-pow] Bitcoin Core's contextual validation also checks timestamps, including median-time-past and future-time limits.[^ref-btc-core-validation]

Timestamp manipulation is therefore bounded, but not irrelevant. A coordinated miner set can influence block timestamps within consensus-permitted ranges. This can affect measured block intervals and, over retarget periods, difficulty calculations. The practical attack question is not whether one miner can arbitrarily set difficulty. The question is whether a coordinated set can bias inputs to retarget logic enough to alter future mining conditions.

For mainnet Bitcoin, this is constrained by:

- median-time-past requirements;
- future timestamp limits;
- 2016-block retarget intervals;
- retarget adjustment bounds;
- economic cost of mining blocks that other nodes will reject if timestamps are invalid.

### Model 6: SPV and Weak-Client Attacks

The whitepaper describes simplified payment verification as checking inclusion in the longest proof-of-work chain without full transaction validation.[^ref-btc-wp] The developer documentation similarly separates full-node validation from lighter security models.[^ref-btc-dev-operating]

Weak-client attack risk is not that PoW fails. It is that the client delegates too much validation or peer discovery to other parties. A light client can be misled longer than a full node if it cannot independently validate all block and transaction rules or if its network view is controlled.

This creates an operational rule:

> Confirmation count is stronger when measured by an independently validating full node with a healthy peer view.

## 7. Mathematical or Economic Model

### Catch-Up Probability

Nakamoto models the double-spend race as a random walk:

```text
p = probability honest miners find the next block
q = probability attacker finds the next block
z = honest-chain lead in blocks
```

If `p > q`, the probability that an attacker ever catches up from `z` blocks behind is:

```text
q_z = (q / p)^z
```

If `p <= q`, the model gives the attacker eventual catch-up probability of `1`.[^ref-btc-wp]

The intuition is straightforward:

- confirmations increase `z`;
- lower attacker hash share lowers `q / p`;
- probability decays exponentially when `q < p`;
- probability does not decay to safety when `q >= p`.

### Poisson Approximation for Confirmed Transactions

The whitepaper then accounts for the fact that while the honest chain found `z` blocks, the attacker may also have found some private blocks. The attacker's private progress is modeled with a Poisson distribution with expected value:

```text
lambda = z * (q / p)
```

This gives a more practical estimate of success probability after a transaction receives `z` confirmations.[^ref-btc-wp]

The model is useful because it shows why confirmation policy should depend on:

- transaction value;
- counterparty risk;
- observed network conditions;
- estimated attacker hashpower;
- tolerance for probabilistic settlement risk.

### Economic Cost

A double-spend attacker pays an opportunity cost:

```text
expected_attack_cost ~= forgone honest mining revenue
                       + direct operating cost
                       + failed-attack loss
                       + market/reputation impact
                       - recoverable double-spend value
```

This is an interpretation, not a consensus rule. It helps explain why high confirmation counts can be economically meaningful even though they are not mathematically final.

### Selfish Mining Revenue

Selfish mining changes the objective from "can I reverse a specific payment?" to "can I earn more than my fair revenue share?" Eyal and Sirer define the attack around relative revenue, block withholding, and network propagation during ties.[^ref-eyal-sirer]

The key variables are:

| Variable | Meaning |
|---|---|
| attacker hash share | probability the selfish pool finds blocks |
| propagation advantage | fraction of honest miners that mine on attacker branch during a tie |
| private lead | hidden branch length over public branch |
| stale rate | honest work wasted on branches that do not survive |
| relative revenue | attacker's share of accepted block rewards |

Selfish mining risk is therefore economic and network-sensitive. A lower direct double-spend risk can still coexist with mining centralization pressure.

## 8. Security Assumptions

### Core Assumptions

Bitcoin PoW security depends on these assumptions:

1. Honest miners control more effective block-production power than any colluding attacker for the relevant time horizon.
2. Honest full nodes validate all consensus rules independently.
3. Valid blocks and transactions propagate broadly enough that no attacker consistently controls the network view of important participants.
4. Miners are economically incentivized to publish valid blocks and extend the most-work valid chain.
5. Difficulty adjustment tracks long-run hashpower without allowing abrupt or arbitrary target manipulation.

### Assumptions Often Overstated

| Overstatement | More Precise Statement |
|---|---|
| "Six confirmations are final." | Six confirmations are a convention that may be sufficient for many risk profiles, not deterministic finality. |
| "51% attackers can steal anyone's coins." | They can reorder or censor valid transactions, but cannot spend coins without valid authorization. |
| "PoW alone protects light clients." | Light clients rely on headers, peers, and assumptions about the chain they are shown. |
| "Selfish mining requires majority hashpower." | The selfish-mining literature studies profitable deviations below majority under propagation assumptions. |
| "A reorg always means an attack." | Small reorgs can occur from normal block propagation races. |

### Threat Boundary

PoW attacks do not cover every institutional loss scenario. Wallet compromise, private-key theft, custodian failure, social engineering, exchange insolvency, and bridge exploits are not PoW attacks even if they occur on or around Bitcoin transactions.

## 9. Bitcoin Core Implementation

Bitcoin Core does not contain a function named "detect majority attack" or "detect selfish mining." It enforces local validation and chain-selection rules.

Relevant implementation boundaries:

| Component | Role |
|---|---|
| `CheckProofOfWork` | Validates that the header hash satisfies the claimed target.[^ref-btc-core-pow] |
| `ContextualCheckBlockHeader` | Checks whether `nBits`, timestamp, and contextual header rules are correct.[^ref-btc-core-validation] |
| `CheckBlock` | Validates full block structure, merkle root, coinbase placement, and transaction-level structure.[^ref-btc-core-validation] |
| `AcceptBlockHeader` | Connects header validation to known parents and contextual checks.[^ref-btc-core-validation] |
| Chainwork accounting | Supports selection of the valid chain with the most accumulated work.[^ref-btc-dev-operating] |

An attack succeeds against Bitcoin Core only if the attacker presents a chain that passes consensus validation and has enough cumulative work to become the selected chain. Invalid blocks remain invalid.

This is why attack analysis must separate:

- validity: will full nodes accept the blocks?
- work: does the branch have more cumulative work?
- propagation: who saw which branch first?
- timing: when did counterparties make settlement decisions?
- visibility: was the victim's node view healthy?

### Reorg Handling

Bitcoin Core's consensus behavior is local and rule-driven. A node does not decide whether a branch is "honest." It validates blocks and tracks the best valid chain according to work and contextual rules. If a valid higher-work branch appears, reorganization is normal protocol behavior.

This means on-chain labels like "attack reorg" are analyst interpretations. The chain data can show a reorg. Intent requires additional evidence.

## 10. On-Chain Implications

### Observable Signals

| Signal | Possible Meaning | Evidence Strength |
|---|---|---|
| Reorg depth | Recent history replaced by another branch | Strong for reorg, weak for intent |
| Stale/orphan block rate | Propagation race or withholding behavior | Medium |
| Repeated competing blocks by same pool | Potential propagation or strategic behavior | Medium |
| Delayed block release patterns | Possible withholding or network issue | Medium to weak |
| Transaction confirmed then removed | Direct settlement risk | Strong for affected transaction |
| Long confirmation gaps | Hashrate drop, network issue, or luck | Weak alone |
| Abnormal timestamp patterns | Miner timestamp behavior | Medium when persistent |
| Pool concentration | Majority or selfish-mining risk factor | Strong as exposure metric, weak as attack proof |

### Not Directly Observable

The following are usually not directly visible from public chain data alone:

- a private fork before release;
- whether a stale block was accidental or strategic;
- whether a miner intentionally censored a transaction;
- whether a victim node was eclipsed;
- whether a pool internally withheld a valid block;
- whether a miner's timestamp choice was coordinated.

### Confirmation Policy

Confirmation policy should be risk-based:

| Context | Lower Confirmation Tolerance | Higher Confirmation Requirement |
|---|---|---|
| Transaction value | Small | Large |
| Counterparty trust | Known and low-risk | Unknown or adversarial |
| Asset liquidity | Hard to monetize quickly | Easy to monetize quickly |
| Network conditions | Normal stale rate and propagation | Reorgs, delays, or peer issues |
| Node setup | Independent full node | Third-party API or weak client |
| Business reversibility | Can freeze settlement | Irreversible delivery |

An analyst should treat confirmation count as an input to risk, not as a binary finality switch.

### Reorg Interpretation Workflow

When a reorg is observed:

1. Measure depth in blocks.
2. Identify affected transactions.
3. Compare cumulative work, not only height.
4. Identify which branch became active.
5. Check block timestamps and arrival times if available.
6. Compare independent full-node views.
7. Check mining-pool attribution cautiously.
8. Separate mechanical consensus outcome from attacker intent.

## 11. Institutional Thinking

### Settlement Risk

Institutions should treat Bitcoin settlement as probabilistic finality. The practical question is not "is it final?" The practical question is:

> Is the probability and cost of reversal acceptable for this transaction, counterparty, amount, and operational workflow?

For high-value inflows, confirmation thresholds should be paired with:

- independent full-node validation;
- peer diversity;
- reorg monitoring;
- mempool awareness;
- delayed crediting or staged release;
- chain surveillance for replacement attempts;
- incident procedures for reorg events.

### Custody and Exchange Controls

PoW attack models intersect with operational controls:

| Control | Reason |
|---|---|
| Run independent full nodes | Avoid third-party or eclipsed chain views |
| Use multiple network paths | Reduce local isolation risk |
| Monitor reorgs before crediting | Catch replacement risk |
| Scale confirmations by value | Match probabilistic finality to exposure |
| Track pool concentration | Monitor majority and selfish-mining risk |
| Keep withdrawal delays configurable | Slow attacker monetization |
| Retain branch and stale-block data | Improve post-incident reconstruction |

### Analyst Mistakes to Avoid

Do not infer:

- that every reorg is malicious;
- that no attack occurred just because no invalid block appeared;
- that majority hashpower lets attackers break signatures;
- that a public chain view is the same as every victim's local view;
- that stale blocks prove selfish mining;
- that confirmation count has the same risk meaning for every transaction size.

### Risk Matrix

| Attack | Probability on Bitcoin Mainnet | Impact if Successful | Analyst Confidence From Public Chain Alone |
|---|---|---|---|
| One-block accidental reorg | Low but normal | Usually low | High |
| Deep double-spend reorg | Very low under normal hash distribution | High for affected counterparties | High after release |
| Sustained majority censorship | Very low under normal hash distribution | Very high | Medium |
| Selfish mining | Model-dependent | Medium to high over time | Low to medium |
| Eclipse against institution | Infrastructure-dependent | High for victim | Low unless logs are available |
| Difficulty manipulation | Very low on mainnet under normal conditions | Medium to high if sustained | Medium |

Probability labels are qualitative. They should be updated with current hashrate distribution, mining-pool concentration, network health, and business exposure.

## 12. Common Misconceptions

### Misconception 1: A 51% attacker can do anything.

Incorrect. A majority attacker can control ordering and censorship with enough work, but full nodes still reject invalid transactions and invalid blocks.[^ref-btc-wp][^ref-btc-core-validation]

### Misconception 2: A double spend requires invalid signatures.

Incorrect. A double-spend reorg uses two conflicting valid spends of the same coins. The winning chain determines which spend remains in accepted history.

### Misconception 3: Confirmations create deterministic finality.

Incorrect. Confirmations make reversal increasingly expensive and statistically less likely when the attacker has less hashpower than honest miners.[^ref-btc-wp]

### Misconception 4: Selfish mining is the same as a 51% attack.

Incorrect. Selfish mining is a strategic withholding and revenue attack that can be profitable below majority under the model assumptions studied by Eyal and Sirer.[^ref-eyal-sirer]

### Misconception 5: Eclipse attacks are visible as a special on-chain marker.

Incorrect. Eclipse attacks manipulate a victim's network view. The public chain may look normal while the victim is being isolated.[^ref-heilman-eclipse]

## 13. Analyst Checklist

Before classifying an event as a PoW attack, ask:

1. Did a reorg occur?
2. What was the reorg depth?
3. Which transactions were removed, replaced, or newly confirmed?
4. Did the replacement branch have more cumulative work?
5. Were all blocks valid under consensus rules?
6. Were blocks delayed or unusually clustered?
7. Were known pools involved in competing branches?
8. Did affected counterparties rely on third-party APIs or their own full nodes?
9. Were peer-connection logs, node logs, or block-arrival timestamps available?
10. Is there evidence of intent beyond the mechanical chain outcome?

For double-spend risk, ask:

1. Was the attacker economically motivated by the reversed transaction amount?
2. Was the transaction credited before adequate confirmations?
3. Was the victim isolated from the wider network?
4. Was the conflicting spend visible before the reorg?
5. Was the attacker's expected gain greater than the cost and risk of failed mining?

For selfish-mining risk, ask:

1. Are stale blocks elevated above baseline?
2. Are stale blocks concentrated around a pool or region?
3. Are block releases suspiciously timed after competing public blocks?
4. Is there independent relay-network data?
5. Could ordinary network latency explain the pattern?
