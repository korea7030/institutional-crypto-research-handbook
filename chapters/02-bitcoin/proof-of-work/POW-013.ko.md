## 3. Executive Summary

Bitcoin Core의 작업증명 검증은 서로 다른 두 층으로 나뉜다.

```text
1. 헤더 해시가 nBits가 주장하는 목표값을 만족하는가?
2. 그 nBits 값이 해당 높이와 부모 블록 맥락에서 허용되는 목표값인가?
```

첫 번째 층은 `CheckProofOfWork`가 담당한다. 이 함수는 `DeriveTarget`을 호출해 잘못된 compact 목표값 인코딩을 거부하고, 블록 해시를 도출된 목표값과 비교한다.[^ref-btc-core-pow]

두 번째 층은 컨텍스트 기반이다. `ContextualCheckBlockHeader`는 `GetNextWorkRequired`로 기대 `nBits`를 다시 계산하고, 블록의 `nBits`가 요구값과 다르면 `bad-diffbits`로 헤더를 거부한다.[^ref-btc-core-validation]

이 분리는 중요하다. 헤더 해시가 자기 `nBits`에 인코딩된 목표값보다 작더라도, 그 `nBits`가 부모와 높이가 요구하는 목표값보다 더 쉬운 값이라면 그 헤더는 여전히 무효다.

Bitcoin Developer 문서는 작업증명을 노드가 가장 큰 누적 작업량을 가진 체인을 식별하는 메커니즘으로 설명하며, Bitcoin Core는 `CBlockIndex`에 `nBits`와 누적 Chainwork 같은 블록별 메타데이터를 저장한다.[^ref-btc-dev-blockchain][^ref-btc-core-chain]

작업증명 검증은 필요조건이지 충분조건이 아니다. `CheckBlock`은 머클 루트, 크기 제한, 코인베이스 위치, 트랜잭션 구조, 기타 블록 규칙도 함께 검사한다. 이후 연결 단계에서는 UTXO 지출, 수수료, 스크립트, 코인베이스 금액까지 검증한다.[^ref-btc-core-validation]

## 4. 정의와 범위

Bitcoin Core에서 작업증명 검증이란, 블록 헤더가 네트워크의 목표값 규칙을 만족하는지 확인하는 것을 말한다.

여기에는 다음이 포함된다.

- `nBits` 디코딩
- 잘못된 목표값 인코딩 거부
- `powLimit` 강제
- 헤더 해시와 목표값 비교
- 컨텍스트에 맞는 목표값 전이 검증
- 새 헤더를 추가하기 전에 부모 존재 여부와 invalid-parent 상태 확인

여기에는 다음이 포함되지 않는다.

- 트랜잭션 유효성
- 스크립트 실행
- UTXO 존재 여부
- 코인베이스 보상 금액
- 블록 릴레이 정책
- mempool 수용

## 5. 역사적 배경

Bitcoin 백서는 작업증명을 "필요한 수의 0 비트로 시작하는 해시"를 찾는 것으로 설명하며, 검증에는 한 번의 해시 계산이면 충분하다고 말한다.[^ref-btc-wp]

Bitcoin Core는 이를 compact `nBits` 목표값 필드와 수치 비교 방식으로 구현한다.

```text
hash <= target
```

이후 구현 세부 사항에는 목표값 도출, overflow 체크, 네트워크별 `powLimit`, 난이도 전이 검증, 컨텍스트 기반 타임스탬프 체크, 비메인넷 네트워크의 특수 동작이 포함되었다.

## 6. 원래 설계

원래 설계의 목표는 비대칭성이다.

```text
expensive to find
cheap to verify
```

Bitcoin Core는 이 비대칭성을 유지한다. 후보 헤더가 주어지면 노드는 헤더를 해시하고, `nBits`에서 목표값을 도출한 뒤, 두 값을 비교한다.

하지만 현대 검증은 백서의 단순화된 설명보다 더 많은 일을 한다. 블록이 체인 내 자신의 위치에서 올바른 목표값을 주장하고 있는지도 반드시 확인해야 한다.

## 7. 프로토콜 구조

작업증명 검증은 다음 헤더 및 합의 입력을 사용한다.

| 입력 | 역할 |
|---|---|
| 헤더 해시 | 목표값과 비교되는 값 |
| `nBits` | 주장된 목표값의 compact 인코딩 |
| `powLimit` | 네트워크별 가장 쉬운 허용 목표값 |
| 부모 블록 인덱스 | 다음에 허용되는 목표값 결정 |
| 블록 높이 | 리타깃 경계와 배포 컨텍스트 결정 |
| 타임스탬프 | 컨텍스트 검증과 리타깃 로직에 사용 |
| 네트워크 파라미터 | mainnet, testnet, signet, regtest의 동작 차이 |

핵심 구분은 다음과 같다.

```text
nBits validity: can this compact target be decoded and is it within powLimit?
hash validity: is the header hash <= decoded target?
contextual target validity: is this nBits exactly what the parent and height require?
```

## 8. 기술적 메커니즘

### 8.1 목표값 도출

`DeriveTarget`은 `nBits`를 전체 목표값으로 변환한다. 다음 경우 목표값을 거부한다.

- compact 인코딩이 음수인 경우
- 목표값이 0인 경우
- 목표값이 overflow하는 경우
- 목표값이 `powLimit`를 초과하는 경우

검사를 통과하면 `DeriveTarget`은 목표값을 반환한다.[^ref-btc-core-pow]

### 8.2 헤더 해시 비교

`CheckProofOfWorkImpl`는 `DeriveTarget`을 호출한다. 목표값을 얻지 못하면 작업증명 검증은 실패한다.

목표값이 반환되면 Bitcoin Core는 헤더 해시를 산술 정수로 변환하고, 다음 조건이면 거부한다.

```text
hash > target
```

동치로 말하면, 헤더는 다음을 만족할 때 이 단계를 통과한다.

```text
hash <= target
```

이것이 직접적인 작업량 체크다.[^ref-btc-core-pow]

### 8.3 컨텍스트 기반 목표값 체크

`ContextualCheckBlockHeader`는 다음을 검사한다.

```text
block.nBits == GetNextWorkRequired(parent, block, consensusParams)
```

값이 다르면, 블록은 `bad-diffbits`로 거부된다.[^ref-btc-core-validation]

이 검증이 있기 때문에, 채굴자는 헤더 해시가 만족하는 더 쉬운 목표값을 임의로 골라 넣을 수 없다.

### 8.4 헤더 수용

`AcceptBlockHeader`는 다음을 수행한다.

1. 중복 감지
2. `CheckBlockHeader` 실행
3. 이전 블록 조회
4. 부모가 없으면 `prev-blk-not-found`로 거부
5. 부모가 무효로 표시되어 있으면 `bad-prevblk`로 거부
6. `ContextualCheckBlockHeader` 실행
7. 최소 anti-DoS 작업량 사전검사를 통과한 경우에만 새 헤더 추가[^ref-btc-core-validation]

### 8.5 전체 블록 검증 경계

`CheckBlock`은 `CheckBlockHeader`를 호출하지만, 작업증명 외의 블록 구조도 검사한다. Signet에서는 설정에 따라 블록 솔루션도 추가로 체크한다. 이후 머클 루트, 크기 제한, 코인베이스 위치, 트랜잭션 구조를 검증한다.[^ref-btc-core-validation]

따라서:

```text
valid PoW header
does not imply
valid block
```

## 9. 수학적 또는 경제적 모델

다음을 정의하자.

- `H`: 256비트 정수로 해석한 블록 헤더 해시
- `T_claimed`: 블록의 `nBits`에서 디코딩한 주장 목표값
- `T_required`: 부모, 높이, 타임스탬프, 합의 파라미터로 계산한 요구 목표값

헤더는 다음을 모두 만족해야 한다.

```text
T_claimed is valid
H <= T_claimed
T_claimed == T_required
```

간단한 예시:

```text
required target: 100
claimed target:  200
header hash:     150
```

해시는 주장 목표값은 만족한다.

```text
150 <= 200
```

하지만 주장 목표값은 허용되지 않는다.

```text
200 != 100
```

따라서 이 헤더는 컨텍스트 검증에서 실패한다.

두 번째 예시:

```text
required target: 100
claimed target:  100
header hash:     120
```

목표값은 맞지만 해시가 너무 높다.

```text
120 > 100
```

따라서 이 헤더는 작업증명 해시 검증에서 실패한다.

## 10. 보안 가정

Bitcoin Core의 작업증명 검증은 다음을 가정한다.

- 노드가 요구 목표값을 독립적으로 다시 계산한다.
- compact 목표값 디코딩은 결정적이다.
- `powLimit`는 네트워크별로 정의되며 강제된다.
- 해시 비교는 정확한 정수 비교다.
- 컨텍스트 검증은 올바른 부모 블록을 기준으로 수행된다.
- 무효 부모 브랜치는 유효한 역사로 계속 확장되지 않는다.

다음은 가정하지 않는다.

- 채굴자가 난이도를 정직하게 보고한다.
- 블록 익스플로러가 합의 유효성을 정의한다.
- 유효한 헤더 해시가 트랜잭션 유효성까지 증명한다.
- 수신한 헤더가 anti-DoS 목적에 쓸 만큼 충분한 작업량을 반드시 가진다.

## 11. 실패 모드와 공격 표면

### 잘못된 compact 목표값

채굴자는 malformed 또는 invalid한 `nBits`를 제시할 수 있다. `DeriveTarget`은 음수, 0, overflow, 상한 초과 목표값을 거부한다.

### High Hash

디코딩된 목표값은 유효해도 헤더 해시가 목표값보다 클 수 있다. Bitcoin Core는 이 작업증명 실패를 `CheckBlockHeader`에서 `high-hash`로 보고한다.[^ref-btc-core-validation]

### Bad Difficulty Bits

헤더 해시가 주장된 목표값을 만족하더라도, `nBits`가 해당 높이에서 요구되는 값과 다를 수 있다. Bitcoin Core는 이를 `ContextualCheckBlockHeader`에서 `bad-diffbits`로 거부한다.[^ref-btc-core-validation]

### 부모 블록 부재 또는 무효

컨텍스트 검증에는 이전 블록 인덱스가 필요하다. `AcceptBlockHeader`는 부모를 모르면 거부하고, 이미 실패로 표시된 부모 위의 헤더도 거부한다.[^ref-btc-core-validation]

### 헤더 유효성과 블록 유효성 혼동

헤더가 유효해도 블록 본문은 머클 루트, 크기, 코인베이스, 트랜잭션, 스크립트, UTXO 규칙에서 실패할 수 있다.

## 12. Bitcoin Core 또는 프로토콜 구현

### `pow.h`

`pow.h`는 다음 작업증명 관련 함수를 선언한다.

- `DeriveTarget`
- `GetNextWorkRequired`
- `CalculateNextWorkRequired`
- `CheckProofOfWork`
- `CheckProofOfWorkImpl`
- `PermittedDifficultyTransition`[^ref-btc-core-pow-h]

### `DeriveTarget`

`DeriveTarget`은 compact 목표값을 디코딩하고, 디코딩 값이 음수, 0, overflow, 또는 `powLimit` 초과면 목표값을 반환하지 않는다.[^ref-btc-core-pow]

### `CheckProofOfWorkImpl`

`CheckProofOfWorkImpl`는 목표값을 도출하고, 도출에 실패하면 실패한다. 도출에 성공하면 해시가 목표값보다 수치적으로 큰 경우 헤더를 거부한다.[^ref-btc-core-pow]

### `CheckProofOfWork`

`CheckProofOfWork`는 보통 `CheckProofOfWorkImpl`를 호출한다. 소스에는 fuzz 테스트 중 결정론을 위한 분기 역시 포함되어 있지만, 이는 정상적인 합의 동작으로 해석하면 안 된다.[^ref-btc-core-pow]

### `CheckBlockHeader`

`CheckBlockHeader`는 작업증명 체크가 활성화된 경우 `CheckProofOfWork`를 호출한다. 이 검사가 실패하면 `BLOCK_INVALID_HEADER`와 이유 `high-hash`를 반환한다.[^ref-btc-core-validation]

### `ContextualCheckBlockHeader`

`ContextualCheckBlockHeader`는 `GetNextWorkRequired`로 기대 `nBits`를 다시 계산하고, 불일치를 `bad-diffbits`로 거부한다. 또한 타임스탬프 제약과 일부 버전 규칙도 검사한다.[^ref-btc-core-validation]

### `AcceptBlockHeader`

`AcceptBlockHeader`는 컨텍스트 비의존 헤더 검증, 부모 조회, invalid-parent 감지, 컨텍스트 기반 헤더 검증, 최소 anti-DoS 작업량 게이팅을 결합해 새 헤더를 block index에 추가한다.[^ref-btc-core-validation]

- POW-012 — Difficulty Adjustment
- POW-014 — Proof-of-Work Attack Models

## 14. 현대적 맥락

Bitcoin Core 검증은 함수별로 책임을 분리한다.

```text
pow.cpp:
  target derivation
  target range checks
  hash <= target
  difficulty transition helpers

validation.cpp:
  header validation orchestration
  parent lookup
  expected nBits check
  timestamp context
  full block structure checks
```

이 분리는 리서처에게 중요하다. 어떤 블록이 실패하는 이유는 여러 종류가 있을 수 있고, 실패 이유마다 시사하는 문제가 다르기 때문이다.

예를 들어:

- `high-hash`는 헤더가 자신이 주장한 목표값을 만족하지 못했다는 뜻이다.
- `bad-diffbits`는 주장한 목표값이 요구된 목표값이 아니었다는 뜻이다.
- `prev-blk-not-found`는 노드가 해당 헤더를 컨텍스트에 놓고 판단할 수 없다는 뜻이다.
- 전체 블록 검증 실패는 작업증명과 무관할 수 있다.

## 15. 온체인 함의

### 직접 관측 가능한 것

알려진 체인 컨텍스트와 블록 헤더만 있으면 분석가는 다음을 볼 수 있다.

- 헤더 해시
- `nBits`
- 부모 해시
- 타임스탬프
- 알려진 부모 체인에 연결된 경우 블록 높이

### 결정적으로 도출 가능한 것

분석가는 다음을 도출할 수 있다.

- 디코딩된 목표값
- 목표값이 `powLimit` 안에 있는지 여부
- `hash <= target`인지 여부
- 해당 부모와 높이에서 기대되는 `nBits`
- 해당 규칙 아래에서 헤더가 `high-hash` 또는 `bad-diffbits`로 실패하는지 여부

### 노드 로컬 또는 컨텍스트 의존 정보

분석가는 다음 항목을 판단하려면 로컬 노드 상태가 필요할 수 있다.

- 부모 블록을 노드가 이미 알고 있는지
- 부모 블록이 invalid로 표시되었는지
- 헤더가 이미 캐시되어 있는지
- 최소 anti-DoS 작업량 게이팅을 통과했는지
- 블록 본문이 존재하며 유효한지

### 헤더만으로는 알 수 없는 것

헤더만으로는 다음을 알 수 없다.

- 트랜잭션 유효성
- UTXO 사용 가능성
- 스크립트 유효성
- 코인베이스 보상 정확성
- 채굴자 신원
- 전체 블록 전파 이력

## 16. 기관 관점에서의 해석

### 관측

블록 헤더 해시가 자신의 `nBits`에 인코딩된 목표값보다 낮다.

### 약한 해석

"이 블록은 유효하다."

### 기관 분석 분해

기관 리서처는 다음을 분리해야 한다.

- compact 목표값 유효성
- 해시-목표값 비교
- 해당 높이에서 요구되는 목표값
- 부모 블록 존재 여부
- 타임스탬프 유효성
- 머클 루트와 블록 구조
- 트랜잭션과 UTXO 검증
- 스크립트 실행
- 코인베이스 보상 제약

### 현재 결론

헤더 해시가 주장 목표값보다 낮다는 사실은 작업증명 조건 하나만 충족한다는 뜻이다. 완전한 Bitcoin 유효성에는 컨텍스트 기반 헤더 검증과 전체 블록 검증이 추가로 필요하다.

### 신뢰 수준

FACT — 소스 데이터가 있으면 해시-목표값 비교는 ECL-A.  
FACT — 부모와 합의 파라미터를 알고 있으면 컨텍스트 기반 `nBits` 검증은 ECL-A.  
INTERPRETATION — 왜 채굴자가 무효 블록을 만들었는지 같은 더 넓은 운영적 결론은 ECL-B.

## 17. Analyst Notes

작업증명 관련 무효 블록을 진단할 때는 다음을 분리할 것.

```text
invalid compact target
hash above target
incorrect nBits for height
missing parent
invalid parent
non-PoW block body failure
```

이 모든 경우를 단순히 다음처럼 요약하면 안 된다.

```text
bad mining
```

정확한 실패 이유가 중요하다.

재현성을 위해 다음을 기록할 것.

- 블록 해시
- 헤더 바이트
- `nBits`
- 디코딩된 목표값
- 부모 블록
- 기대 `nBits`
- 네트워크 파라미터
- 검증에 사용한 Bitcoin Core 버전 또는 커밋

## 18. 흔한 오해

### 오해

> `hash <= nBits`이면 블록은 유효하다.

### 평가

틀렸다.

### 교정

`nBits`는 목표값 자체가 아니라 compact 목표값 인코딩이다. 목표값을 디코딩하고, `powLimit` 안에 있는지 확인하고, 컨텍스트에서도 검증해야 한다.

### 오해

> 헤더가 자신의 `nBits`를 만족하면 그 헤더는 유효하다.

### 평가

불완전하다.

### 교정

그 헤더는 부모와 높이가 요구하는 목표값도 정확히 주장해야 한다.

### 오해

> 작업증명 검증은 트랜잭션까지 검증한다.

### 평가

틀렸다.

### 교정

작업증명 검증은 헤더의 목표값 조건을 확인할 뿐이다. 트랜잭션 유효성은 다른 경로에서 검사된다.

### 오해

> `high-hash`와 `bad-diffbits`는 같은 실패다.

### 평가

틀렸다.

### 교정

`high-hash`는 헤더 해시가 주장 목표값보다 높다는 뜻이고, `bad-diffbits`는 주장 목표값이 요구 목표값이 아니라는 뜻이다.

### 오해

> Bitcoin Core는 작업량이 충분한 헤더라면 그냥 받아들인다.

### 평가

틀렸다.

### 교정

Bitcoin Core는 새 헤더를 추가하기 전에 중복, 부모 존재 여부, invalid-parent 상태, 컨텍스트 목표값, 타임스탬프, anti-DoS 작업량 게이팅도 함께 점검한다.

## 19. 반증과 한계

Bitcoin Core 소스는 Bitcoin Core 동작에 대한 1차 구현 증거이지, 가능한 모든 호환 구현의 내부 구조를 완전하게 설명하는 문서는 아니다.

일부 검증 경로에는 `fCheckPOW`, `min_pow_checked`, fuzz 테스트 동작 같은 플래그가 노출된다. 이런 요소들은 해당 구현 맥락에서 해석해야 하며, 일반적인 메인넷 합의 지름길로 일반화하면 안 된다.

이 문서는 작업증명과 헤더 컨텍스트 검증에 집중한다. 전체 유효성에는 트랜잭션, 스크립트, UTXO, 블록 weight, 머클 루트, 위트니스 커밋먼트, 코인베이스 체크가 추가로 필요하다.

네트워크별 동작 차이도 중요하다. Signet, testnet, testnet4, regtest는 메인넷과 다를 수 있다. Bitcoin Core는 작업증명 한계와 난이도 관련 설정을 포함한 네트워크별 합의 파라미터를 chain parameters에 정의한다.[^ref-btc-core-chainparams]
