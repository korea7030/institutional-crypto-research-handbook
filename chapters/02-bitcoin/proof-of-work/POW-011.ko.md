## 3. Executive Summary

누적 작업량(Chainwork)은 하나의 브랜치에서 각 유효 블록이 나타내는 목표값 기반 기대 작업량을 합한 값이다. 이것이 작업증명 아래에서 Bitcoin 브랜치를 비교하는 정량적 기반이다.

Bitcoin Core는 누적 작업량을 `CBlockIndex::nChainWork`에 저장하며, 이를 해당 블록까지 포함한 체인의 총 기대 작업량으로 문서화한다.[^ref-btc-core-chain] 블록별 작업량은 `GetBlockProof`를 통해 계산되며, 이 함수는 `GetBitsProof(block.nBits)`를 반환한다.[^ref-btc-core-chain]

Bitcoin Core의 `GetBitsProof`는 compact `nBits`를 목표값으로 디코딩하고, 디코딩된 목표값이 음수, overflow, 또는 0이면 0을 반환한다. 그렇지 않으면 다음과 동등한 정수형 표현으로 목표값에 대응하는 작업량을 계산한다.

```text
floor(2^256 / (target + 1))
```

여기서 `+ 1`이 중요한 이유는 `0`부터 `target`까지의 모든 해시 출력이 유효하기 때문에, 유효한 출력의 개수가 `target + 1`개이기 때문이다.[^ref-btc-core-chainwork]

Chainwork는 정확한 winning hash로부터 계산되지 않는다. 목표값을 간신히 만족하는 블록과 목표값보다 훨씬 낮은 해시를 가진 블록은, 동일한 유효 `nBits`를 가졌다면 같은 블록별 작업량을 기여한다. 네트워크가 신용을 부여하는 것은 관측된 운(luck)이 아니라 목표값이 표현하는 기대 작업량이다.

## 4. 정의와 범위

누적 작업량(Chainwork)은 다음과 같다.

```text
the sum of per-block expected work from genesis to a branch tip
```

블록별 작업량은 블록의 인코딩된 목표값에서 도출된다. 이것은 다음이 아니다.

- 실제로 시도된 해시 횟수
- 실제 전력 소비량
- 정확한 ASIC fleet 규모
- winning block hash의 정확한 값
- 해당 브랜치의 블록 개수

이 문서는 Chainwork를 합의 규칙 및 분석 개념으로 다룬다. 실제 마이닝 비용이나 공격자 수익성 추정은 다루지 않는다.

## 5. 역사적 배경

Bitcoin 백서는 수용된 역사를 가장 큰 작업증명 노력이 투입된 체인으로 설명한다.[^ref-btc-wp]

백서는 자주 "longest chain"이라는 약칭을 사용한다. 하지만 현대 Bitcoin 분석에서는 블록당 작업량이 난이도에 따라 바뀌므로, 누적 작업량이 더 정확한 측정값이다.

Bitcoin Developer의 풀노드 문서는 공격자가 현재 체인보다 더 큰 난이도를 가진 대체 역사를 제공해야 한다고 설명하며, 이 보안 모델 아래에서 가장 큰 누적 작업증명을 가진 체인을 진짜 체인으로 설명한다.[^ref-btc-dev-operating]

## 6. 원래 설계

원래 설계의 아이디어는 다음과 같이 요약할 수 있다.

```text
더 많은 작업증명 노력
↓
더 강한 수용된 역사
↓
과거 트랜잭션을 대체하기 더 어려움
```

백서의 보안 논리는 공격자가 수정된 블록의 작업을 다시 해야 하고, 그 뒤에 추가된 작업량도 따라잡아야 한다는 점에 의존한다.[^ref-btc-wp]

현대 Bitcoin은 이 아이디어를 각 유효 블록에 목표값 기반 작업량을 부여하고, 이를 block index 전체에 걸쳐 누적하는 방식으로 구현한다.

## 7. 프로토콜 구조

각 블록 헤더는 다음을 포함한다.

```text
nBits
```

`nBits`는 목표값 임계치를 compact하게 인코딩한다. 유효한 블록 해시는 반드시 그 목표값보다 작거나 같아야 한다.

Chainwork의 의존 그래프는 다음과 같다.

```text
nBits
↓
decoded target
↓
per-block work
↓
parent chainwork + per-block work
↓
tip chainwork
↓
branch comparison
```

Bitcoin Core의 `CBlockIndex`는 다음을 저장한다.

| Field | Role |
|---|---|
| `nBits` | Compact target for the block. |
| `pprev` | Pointer to parent block index. |
| `nHeight` | Block height. |
| `nChainWork` | Cumulative work through this block. |

`nHeight`와 `nChainWork`는 서로 관련 있지만 동일하지 않다. 높이는 블록 수를 세고, Chainwork는 목표값 기반 기대 작업량을 합산한다.

## 8. 기술적 메커니즘

### 8.1 목표값 디코딩

블록의 `nBits` 값은 Bitcoin의 compact encoding 규칙에 따라 목표값으로 디코딩된다. 목표값이 무효라면 유효하게 수용된 Chainwork에 기여할 수 없다.

Bitcoin Core의 `GetBitsProof`는 `SetCompact(bits, &fNegative, &fOverflow)`를 호출하고, 디코딩된 값이 음수, overflow, 또는 0이면 0을 반환한다.[^ref-btc-core-chainwork]

### 8.2 블록별 작업량 계산

개념적으로:

```text
block_work = floor(2^256 / (target + 1))
```

Bitcoin Core는 `2^256`을 256비트 정수 안에 직접 표현할 수 없으므로, 다음과 동등한 정수식 표현을 사용한다.

```text
(~target / (target + 1)) + 1
```

여기서 `~target`은 256비트 unsigned integer 영역에서 `2^256 - target - 1`을 나타낸다.[^ref-btc-core-chainwork]

### 8.3 Chainwork 누적

개념적으로:

```text
chainwork(block) = chainwork(parent) + block_work(block)
```

브랜치 전체로는:

```text
chainwork(tip) = Σ block_work(block_i)
```

Bitcoin Core는 이 누적값을 `nChainWork`에 저장하며, non-genesis 블록의 Chainwork가 부모 Chainwork보다 크거나 같아야 한다는 내부 일관성 검사를 포함한다.[^ref-btc-core-validation]

### 8.4 브랜치 비교

두 유효 브랜치를 비교하려면:

```text
if chainwork(branch_A_tip) > chainwork(branch_B_tip):
    branch_A has more cumulative work
else:
    branch_B has more cumulative work
```

다만 체인 선택은 여전히 검증과 블록 데이터 가용성을 요구한다. 브랜치가 무효하거나 검증에 필요한 데이터가 충분하지 않다면, Chainwork만으로는 충분하지 않다.

## 9. 수학적 또는 경제적 모델

다음을 정의하자.

- `T`는 디코딩된 목표값
- `N = 2^256`은 SHA-256 해시 출력 공간의 크기
- `p`는 한 번의 해시 시도가 성공할 확률
- `E`는 성공 1회를 얻기 위한 기대 시도 횟수

유효한 출력은:

```text
0, 1, 2, ..., T
```

이므로, 유효한 출력의 개수는:

```text
T + 1
```

이다. 따라서:

```text
p = (T + 1) / 2^256
```

그리고 기대 시도 횟수는:

```text
E = 1 / p = 2^256 / (T + 1)
```

Bitcoin Core는 다음의 정수형 작업량을 사용한다.

```text
block_work = floor(2^256 / (T + 1))
```

간단한 예시:

```text
hash space: 0..255
target: 15
valid outputs: 0..15
success probability: 16 / 256
expected attempts: 256 / 16 = 16
block_work: 16
```

두 브랜치가 다음처럼 다를 수 있다.

| Branch | Blocks | Work per block | Cumulative work |
|---|---:|---:|---:|
| A | 5 | 16 | 80 |
| B | 4 | 24 | 96 |

Branch B는 블록 수는 더 적지만 누적 작업량은 더 많다.

이 예시는 설명을 위해 작은 해시 공간을 사용한 것이다. 실제 Bitcoin은 256비트 해시 공간과 compact target encoding을 사용한다.

## 10. 보안 가정

Chainwork는 다음을 가정한다.

- 유효한 compact target
- 유효한 작업증명
- 독립적으로 검증된 블록 헤더
- 올바른 parent linkage
- 무효 브랜치에 대한 작업량 미인정
- SHA-256d 출력이 실질적으로 예측 불가능하고 균등 분포로 모델링될 수 있다는 가정

Chainwork는 다음을 증명하지 않는다.

- 실제로 시도된 해시 횟수
- 정확한 전력 소비량
- 채굴자 신원
- 채굴자의 정직성
- 절대적 의미의 트랜잭션 finality

Chainwork가 측정하는 것은 수용된 목표값 임계치가 암시하는 기대 작업량이다.

## 11. 실패 모드와 공격 표면

### 블록 수를 작업량 대신 세는 경우

분석가는 단순히 높이만으로 브랜치를 비교하는 실수를 할 수 있다. 블록별 작업량이 다르면 이 비교는 틀릴 수 있다.

### Winning Hash의 운(luck)에 추가 가중치를 부여하는 경우

목표값보다 훨씬 낮은 블록 해시는 시각적으로 인상적일 수 있다. 하지만 Bitcoin은 이에 대해 추가 Chainwork를 부여하지 않는다. 작업량은 winning hash가 아니라 목표값에서 도출된다.

### 무효 작업량까지 계산하는 경우

겉보기에 작업량을 나타내는 헤더를 가진 무효 브랜치가 있을 수 있다. 수용된 Chainwork 분석은 합의 규칙 검증에 실패하는 브랜치를 배제해야 한다.

### 해시레이트와 Chainwork를 혼동하는 경우

해시레이트는 초당 시도 횟수의 추정값이다. Chainwork는 수용된 블록 전체에 누적된 목표값 기반 기대 작업량이다. 둘은 관련 있지만 같은 값이 아니다.

### Reorg 비용을 과장하는 경우

Chainwork 차이는 목표값 기반 기대 작업량을 추정해 줄 뿐, 공격자의 실제 비용을 보장하지는 않는다. 실제 비용은 하드웨어, 전력, 기회비용, 시장 접근성, 타이밍에 따라 달라진다.

## 12. Bitcoin Core 또는 프로토콜 구현

Bitcoin Core는 `chain.h`, `chain.cpp`, 그리고 validation 로직 전반에서 핵심 Chainwork 모델을 구현한다.

### `CBlockIndex::nChainWork`

`CBlockIndex::nChainWork`는 해당 블록까지 포함한 체인의 누적 기대 작업량을 저장한다.[^ref-btc-core-chain]

### `GetBlockProof`

`GetBlockProof`는 `GetBitsProof(block.nBits)`를 반환하므로, 블록별 작업량은 compact target 필드에서 도출된다.[^ref-btc-core-chain]

### `GetBitsProof`

`GetBitsProof`는 다음을 수행한다.

1. `SetCompact`로 `nBits`를 디코딩한다.
2. 디코딩된 목표값이 음수, overflow, 또는 0이면 0을 반환한다.
3. `floor(2^256 / (target + 1))`과 동등한 정수 표현을 사용해 목표값 기반 작업량을 계산한다.[^ref-btc-core-chainwork]

### 검증 일관성

Bitcoin Core의 validation consistency checks는 모든 non-genesis 블록의 Chainwork가 적어도 부모 Chainwork 이상이어야 한다고 단언한다.[^ref-btc-core-validation]

### 체인 선택과의 연결

`POW-010`에서는 Bitcoin Core가 이렇게 계산된 `nChainWork`를 최대 작업량 체인 선택에 어떻게 사용하는지 다뤘다. 이 문서는 그 값의 산술적 의미와 해석에 초점을 둔다.

## 13. 관련 표준과 BIP

누적 Chainwork를 별도 기능으로 도입한 BIP는 없다. 이것은 Bitcoin의 원래 작업증명 체인 선택 모델에서 자연스럽게 따라나오는 개념이다.

관련 문서:

- POW-006 — Difficulty Target
- POW-007 — Compact Target Encoding (`nBits`)
- POW-010 — Chain Selection
- POW-012 — Difficulty Adjustment

난이도 조정은 미래 블록의 목표값을 바꾼다. Chainwork는 각 실제 목표값이 블록 헤더에 인코딩된 뒤, 그 목표값이 암시하는 작업량을 측정한다.

## 14. 현대적 맥락

현대 Bitcoin explorer, 노드 소프트웨어, 분석 시스템은 Chainwork 값을 직접 노출하거나 헤더로부터 이를 계산해 낼 수 있다.

기관 분석에서는 다음을 논할 때 Chainwork가 높이보다 더 유용한 경우가 많다.

- 브랜치 비교
- reorg 비용
- confirmation depth
- 동기화 보안
- 대체 브랜치 위험

그러나 Chainwork는 반드시 검증 상태와 함께 해석해야 한다. 높은 작업량을 가진 브랜치라도 무효라면 수용된 역사가 아니다.

---

## 15. 온체인 함의

### 직접 관측 가능한 것

분석가는 다음을 관측할 수 있다.

- 블록 헤더
- `nBits`
- parent hash
- 블록 높이
- 노드가 보는 활성 체인 시퀀스

### 결정적으로 도출 가능한 것

분석가는 다음을 도출할 수 있다.

- 디코딩된 목표값
- 블록별 작업량
- 누적 Chainwork
- 관측된 두 브랜치 사이의 작업량 차이
- Bitcoin Core의 `GetBlockProofEquivalentTime`와 같은 개념을 따라, 현재 tip의 작업량과 목표 간격을 사용한 등가 시간 추정치

### 추정 또는 추론의 영역

분석가는 다음을 추정할 수 있다.

- wall-clock time 동안 축적된 작업량으로부터의 해시레이트
- 브랜치를 대체하는 경제적 비용
- 공격자의 실행 가능성
- 결제 확신도(settlement confidence)

### Chainwork만으로는 알 수 없는 것

Chainwork만으로는 다음을 알 수 없다.

- 실제 시도된 해시 횟수
- 정확한 전력 소비량
- 채굴자의 비용 기반
- 채굴자 신원
- reorg 시도가 진행 중인지 여부
- 특정 브랜치가 패배한 이유

## 16. Institutional Thinking

### Observation

어떤 트랜잭션은, 그 뒤에 추가 Chainwork가 축적된 브랜치에서 6개의 confirmation을 받았다.

### 약한 해석

"6 confirmation이면 그 트랜잭션은 final이다."

### 기관적 분해

기관 연구자는 다음을 분리해야 한다.

- confirmation 개수
- 트랜잭션 이후에 쌓인 누적 작업량
- 현재 해시레이트 환경
- 잠재적 공격자 자원
- 위험에 노출된 가치
- 거래소 또는 커스터디 정산 정책
- 관측된 stale 및 reorg 조건

### 현재 결론

confirmation은 사용자 친화적 proxy다. 누적 Chainwork는 활성 브랜치에서 특정 트랜잭션을 제거하기 위해 공격자가 얼마나 많은 목표값 기반 작업량을 대체해야 하는지 보여주는 더 정밀한 기술적 측정값이다.

### Confidence

FACT — ECL-A for computing cumulative chainwork from valid headers.  
INTERPRETATION — ECL-B for translating chainwork into economic settlement confidence.

## 17. Analyst Notes

브랜치를 비교할 때는 Chainwork를 사용하라. 비교되는 모든 블록의 작업량이 사실상 동일하거나, 높이 자체가 명시적 분석 대상일 때만 높이를 사용하라.

해시가 목표값보다 훨씬 낮다고 해서 해당 블록에 추가 작업량 점수를 부여해서는 안 된다.

해시레이트를 추정할 때는:

```text
estimated_hash_rate =
work_accumulated / elapsed_time
```

를 사용할 수 있다. 다만 측정 구간을 반드시 명시해야 하고, 블록 도착은 확률적이라는 점을 기억해야 한다.

reorg를 논의할 때는 다음 둘 다 보고해야 한다.

```text
reorg depth in blocks
```

그리고 가능하다면:

```text
work difference
```

## 18. 흔한 오해

### Misinterpretation

> Chainwork is the number of actual hashes miners performed.

### Assessment

틀렸다.

### Correction

Chainwork는 목표값으로부터 도출된 기대 작업량이다. 실제 실패한 해시 시도 횟수는 온체인에 기록되지 않는다.

### Misinterpretation

> A hash far below target contributes more chainwork.

### Assessment

틀렸다.

### Correction

블록별 작업량은 winning hash가 목표값보다 얼마나 더 낮은지가 아니라 `nBits`로부터 도출된다.

### Misinterpretation

> The branch with the highest height always has the most chainwork.

### Assessment

불완전하다.

### Correction

높이는 블록 개수를 세는 값이고, Chainwork는 목표값 기반 작업량을 합산한 값이다. 목표값이 다르면 더 적은 블록이 더 많은 작업량을 나타낼 수도 있다.

### Misinterpretation

> Chainwork proves energy consumption exactly.

### Assessment

틀렸다.

### Correction

Chainwork는 목표값 임계치가 암시하는 기대 해시 시도 횟수를 측정한다. 에너지 소비는 하드웨어 효율과 운영 조건에 따라 달라진다.

### Misinterpretation

> Chainwork alone validates a chain.

### Assessment

틀렸다.

### Correction

브랜치는 모든 적용 가능한 합의 규칙을 만족해야 한다. Chainwork는 유효한 후보 브랜치들 사이에서 선택할 때 사용되는 하나의 입력일 뿐이다.

## 19. 반증과 한계

Chainwork 공식은 Bitcoin Core의 목표값 기반 작업량 회계에 대해서는 정확하지만, 여전히 기대 작업량 모델이다. 실제로 수행된 해시 횟수를 드러내지는 않는다.

이 계산은 compact target 디코딩이 올바르다는 전제에 의존한다. 무효한 compact target은 유효한 수용 작업량을 생성하지 못한다.

Bitcoin Core 문서와 소스 코드는 Bitcoin Core 구현에 대한 1차 근거다. 다른 구현은 내부 계산 구조를 다르게 둘 수 있지만, 합의 호환 노드라면 유효 헤더와 브랜치 선택 결과에 대해서는 동일한 결론에 도달해야 한다.

Chainwork의 경제적 해석은 하드웨어 시장, 전력 가격, 풀 행동, 기회비용에 대한 가정을 요구한다. 이러한 가정은 블록체인 내부에 포함되어 있지 않다.
