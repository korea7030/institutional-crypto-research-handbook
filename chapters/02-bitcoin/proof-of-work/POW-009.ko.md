## 4. 정의

### 코인베이스 트랜잭션(Coinbase Transaction)

코인베이스 트랜잭션은 Bitcoin 블록의 특별한 첫 번째 트랜잭션이다. 이 트랜잭션은 이전 출력을 소비하지 않고 하나 이상의 출력을 생성한다. 또한 블록 생산자가 허용된 블록 보조금과 블록 내 비코인베이스 트랜잭션에서 발생한 거래 수수료를 청구하는 경로이기도 하다.[^ref-btc-wp][^ref-btc-dev-transactions]

### 코인베이스 입력(Coinbase Input)

코인베이스 입력은 코인베이스 트랜잭션의 입력이다. 일반 입력과 달리, 이전에 지출 가능한 출력을 참조하지 않는다. Bitcoin Developer 문서는 코인베이스 입력이 이전 outpoint를 갖지 않기 때문에 32바이트 null hash와 출력 인덱스 `0xffffffff`를 사용한다고 설명한다.[^ref-btc-dev-transactions]

### 비코인베이스 입력(Non-Coinbase Input)

비코인베이스 트랜잭션 입력은 이전 트랜잭션의 outpoint를 소비한다. outpoint는 과거 트랜잭션 해시와 출력 인덱스를 식별한다. Bitcoin Core는 이를 `COutPoint`와 `CTxIn`으로 모델링한다.[^ref-btc-core-transaction]

### 트랜잭션 출력(Transaction Output)

트랜잭션 출력은 금액과 잠금 스크립트를 지정한다. Bitcoin Core는 `nValue`와 `scriptPubKey`를 포함한 `CTxOut`으로 트랜잭션 출력을 모델링한다.[^ref-btc-core-transaction]

### 블록 보조금(Block Subsidy)

블록 보조금은 특정 블록 높이에서 합의 규칙상 보조금 스케줄에 따라 허용되는 신규 발행 bitcoin이다. 이 값은 채굴자가 임의로 선택하는 것이 아니다.

### 거래 수수료(Transaction Fee)

거래 수수료는 비코인베이스 트랜잭션이 소비한 입력값과 생성한 출력값의 차이다.

```text
fee = input value - output value
```

Bitcoin Core의 `CheckTxInputs`는 입력값이 출력값보다 작지 않음을 확인한 뒤, `nValueIn - value_out`으로 수수료를 계산한다.[^ref-btc-core-tx-verify]

### Extra Nonce

extra nonce는 일반적으로 코인베이스 트랜잭션 안에 배치되는 채굴자 제어 데이터다. 이 데이터는 코인베이스 트랜잭션 식별자, 트랜잭션 머클 루트, 그리고 결국 해시되는 블록 헤더를 바꾼다. 이는 마이닝 관행이지 `extra_nonce`라는 별도의 합의 규칙 필드가 아니다.

## 5. 역사적 맥락

Bitcoin 백서는 이 특별한 첫 번째 트랜잭션을 인센티브 시스템의 일부로 도입했다. 백서는 블록의 첫 번째 트랜잭션이 블록 생성자에게 귀속되는 새로운 코인을 시작하며, 이를 통해 노드가 네트워크를 지원할 인센티브를 제공하고 코인을 초기 분배하는 수단을 마련한다고 설명한다.[^ref-btc-wp]

원래 설계에서 이 특별한 트랜잭션은 기본적으로 인센티브 메커니즘이었다. 현대 Bitcoin에서 코인베이스 트랜잭션은 동시에 마이닝 커밋먼트 표면이기도 하다. 이 트랜잭션은 트랜잭션 머클 트리의 첫 번째 리프를 구성하고, 채굴자가 제어하는 스크립트 데이터를 담을 수 있으며, 이후의 소프트포크 커밋먼트, 예를 들어 witness 관련 커밋먼트도 실을 수 있다.

중요한 역사적 전환은 다음과 같다.

```text
백서에서의 역할:
    채굴자 보상과 코인 분배

현대 운영상 역할:
    채굴자 보상
    거래 수수료 청구
    블록 높이 커밋먼트
    머클 루트 입력
    extra nonce 탐색 공간 확장
    메타데이터 표면
```

이 역할 확장이 합의 규칙 경계를 흐리게 해서는 안 된다. 채굴자는 코인베이스 트랜잭션을 구성할 수 있지만, 풀노드는 블록 보상과 블록 구조가 유효한지 독립적으로 검증한다.

## 6. 기술적 기초

### 트랜잭션 형태

Bitcoin Developer 문서는 raw transaction이 다음을 포함한다고 설명한다.

- version
- 입력 개수
- 하나 이상의 트랜잭션 입력
- 출력 개수
- 하나 이상의 트랜잭션 출력
- lock time[^ref-btc-dev-transactions]

Bitcoin Core의 `CTransaction` 역시 `vin`, `vout`, `version`, `nLockTime` 필드를 가진다.[^ref-btc-core-transaction]

코인베이스 트랜잭션은 동일한 넓은 의미의 트랜잭션 컨테이너를 사용하지만 입력이 특별하다. 일반 트랜잭션은 기존 UTXO를 소비한다. 코인베이스 트랜잭션은 기존 UTXO를 소비하지 않고 허용된 출력을 생성한다.

### 코인베이스 위치 강제

Bitcoin Core의 블록 검증은 코인베이스의 위치를 검사한다. 유효한 블록은 반드시 첫 번째 트랜잭션으로 코인베이스 트랜잭션을 가져야 하며, 그 뒤의 트랜잭션들은 코인베이스여서는 안 된다. 첫 번째 트랜잭션이 코인베이스가 아니면 검증은 `bad-cb-missing`을 반환하고, 코인베이스가 둘 이상 존재하면 `bad-cb-multiple`을 반환한다.[^ref-btc-core-validation]

이 규칙이 중요한 이유는 코인베이스 트랜잭션이 블록 보조금과 거래 수수료를 청구하는 메커니즘이기 때문이다. 이는 단순한 지갑 관행이나 블록 탐색기 표시 형식이 아니다.

### 기본 트랜잭션 검사

Bitcoin Core의 `CheckTransaction`은 컨텍스트와 무관한 검사를 수행한다. 이 함수는 비어 있는 입력 벡터, 비어 있는 출력 벡터, 과도한 직렬화 크기, 음수 출력, 과도하게 큰 출력, 과도하게 큰 총 출력값, 중복 입력, null previous outpoint를 사용하는 비코인베이스 트랜잭션, 허용 범위를 벗어난 크기의 코인베이스 스크립트를 거부한다.[^ref-btc-core-tx-check]

이 검사들은 트랜잭션 유효성이 작업증명만으로 정의되지 않음을 보여준다. 블록 헤더 해시가 유효하더라도, 트랜잭션이 합의 규칙 검사를 통과하지 못하면 그 블록은 여전히 무효다.

### UTXO 의존 검사

Bitcoin Core의 `CheckTxInputs`는 모든 입력이 UTXO 뷰에서 사용 가능한지 확인하고, 코인베이스 출력 지출 시 maturity를 강제하며, 입력값 총합을 계산하고, 금액 범위를 검사하고, 입력값이 출력값보다 작은 트랜잭션을 거부하며, 거래 수수료를 입력값에서 출력값을 뺀 값으로 계산한다.[^ref-btc-core-tx-verify]

이것이 거래 수수료에 대한 UTXO 회계 기반이다.

```text
sum(previous outputs spent by transaction)
-
sum(new outputs created by transaction)
=
transaction fee
```

수수료는 명시적인 출력이 아니다. 이는 트랜잭션이 배정하지 않고 남겨둔 가치이며, 이후 블록의 코인베이스 트랜잭션이 집계해서 청구할 수 있다.

## 7. 코인베이스 보상 메커니즘

### 보상 공식

높이 `h`의 블록에 대해:

```text
maximum coinbase value =
    GetBlockSubsidy(h, consensus parameters)
    +
    sum(fees of included non-coinbase transactions)
```

Bitcoin Core는 블록을 연결할 때 이 로직을 사용한다. 허용 가능한 블록 보상을 계산하고, 코인베이스 트랜잭션이 허용된 보조금과 수수료의 합보다 더 많은 금액을 지급하면 `bad-cb-amount`로 블록을 거부한다.[^ref-btc-core-validation]

### 덜 청구하기(Underclaiming)

채굴자는 허용된 최대 보상보다 적은 금액만 청구할 수 있다. 합의 규칙상 실패 조건은 underclaiming이 아니라 overclaiming이다.

예시:

```text
subsidy:           3.125 BTC
included fees:     0.080 BTC
maximum coinbase:  3.205 BTC
coinbase outputs:  3.204 BTC
```

이 경우 `0.001 BTC`를 덜 청구한 것이다. 보상 금액 규칙은 여전히 충족된다.

### 초과 청구하기(Overclaiming)

예시:

```text
subsidy:           3.125 BTC
included fees:     0.080 BTC
maximum coinbase:  3.205 BTC
coinbase outputs:  3.206 BTC
```

이 경우 `0.001 BTC`를 초과 청구했다. 블록 헤더가 작업증명을 만족하더라도, 완전 검증 노드는 이 블록을 거부한다.

### 금액 범위

Bitcoin Core는 사토시 단위의 `CAmount`, `COIN = 100000000`, `MAX_MONEY = 21000000 * COIN`, 그리고 값이 유효한 화폐 범위 내에 있는지 검사하는 `MoneyRange`를 정의한다.[^ref-btc-core-amount]

이러한 금액 범위는 일반적인 화폐 유효성 제약이다. 하지만 이것이 블록별 보상 규칙을 대체하지는 않는다. 코인베이스 출력이 `MAX_MONEY`보다 작더라도, 보조금과 수수료의 합을 초과하면 여전히 무효다.

## 8. 마이닝 커밋먼트

### 코인베이스는 하나의 머클 리프다

코인베이스 트랜잭션은 블록의 첫 번째 트랜잭션이다. 이 트랜잭션의 식별자는 트랜잭션 머클 트리의 리프 가운데 하나다. 블록 헤더가 머클 루트를 담고 있기 때문에, 코인베이스 트랜잭션은 간접적으로 작업증명 입력에 커밋된다.

커밋먼트 경로는 다음과 같다.

```text
coinbase transaction bytes
    -> coinbase txid
    -> transaction Merkle tree
    -> Merkle root
    -> block header
    -> proof-of-work hash
```

코인베이스 트랜잭션을 바꾸면 머클 루트도 바뀐다. 예외는 동일한 트랜잭션 식별자와 동일한 트리 루트를 유지하는 경우뿐인데, 이는 관련 해시 가정을 깨뜨리거나 동일한 직렬화 트랜잭션을 다시 만들어야 한다는 뜻이다.

### Extra Nonce 탐색 공간

블록 헤더에는 32비트 nonce가 있다. 대형 채굴자는 할당된 nonce 범위를 빠르게 소진할 수 있다. 따라서 마이닝 소프트웨어는 헤더에 영향을 주는 다른 데이터를 바꾸어 새로운 후보 헤더를 만든다.

대표적인 방법은 코인베이스 트랜잭션 내부의 채굴자 제어 바이트를 바꾸는 것이다. 이렇게 하면 다음이 함께 바뀐다.

```text
coinbase script or output data
    -> coinbase txid
    -> Merkle root
    -> block header
    -> hash-search input
```

이 때문에 extra nonce는 마이닝 커밋먼트 논의의 일부가 된다. 이것은 블록 헤더 안의 별도 합의 규칙 필드가 아니다. 더 많은 헤더 후보 집합을 만들기 위한 관행이다.

### 트랜잭션 선택 커밋먼트

머클 루트는 선택된 비코인베이스 트랜잭션들과 그 순서에도 커밋한다. 트랜잭션을 추가, 제거, 재정렬하면 일반적으로 머클 루트가 바뀐다.

이로부터 중요한 분석적 연결이 나온다.

```text
miner transaction selection
    -> transaction list
    -> fee total
    -> coinbase reward limit
    -> Merkle root
    -> proof-of-work search input
```

따라서 마이닝은 단순한 nonce 반복이 아니다. 반복적인 후보 블록 커밋먼트 구성 과정이다.

Bitcoin Core의 마이닝 코드는 이 구성 파이프라인을 반영한다. `BlockAssembler::CreateNewBlock`는 후보 블록을 만들고, 코인베이스 트랜잭션을 생성하고, 수수료와 보조금을 반영하고, 최종 헤더에 대해 작업증명 탐색을 수행하기 전에 트랜잭션 머클 루트를 할당한다.[^ref-btc-core-miner]

## 9. 합의 규칙, 정책, 구현, 그리고 관행

### 합의 규칙

다음은 합의 규칙 수준의 제약이다.

| Rule | Evidence |
|---|---|
| A valid block must have a coinbase transaction first. | Bitcoin Core validation |
| A valid block must not contain multiple coinbase transactions. | Bitcoin Core validation |
| Coinbase script size is constrained. | Bitcoin Core `CheckTransaction` |
| Non-coinbase transactions must not use null previous outpoints. | Bitcoin Core `CheckTransaction` |
| Duplicate inputs are invalid. | Bitcoin Core `CheckTransaction` |
| Output values must not be negative or out of range. | Bitcoin Core `CheckTransaction` and `MoneyRange` |
| Input value must be at least output value. | Bitcoin Core `CheckTxInputs` |
| Coinbase reward must not exceed subsidy plus fees. | Bitcoin Core block connection |
| Coinbase outputs must mature before spending. | Bitcoin Core `CheckTxInputs` |

### 정책(Policy) 규칙

정책 규칙은 릴레이 및 mempool 수용 여부에 영향을 주지만, 합의 규칙과 동일하지 않다. 예를 들어 standardness, dust 정책, 최소 릴레이 수수료, mempool package 동작이 여기에 속한다. 릴레이 정책상 비표준(non-standard)인 트랜잭션이라도, 합의 규칙을 만족하는 블록에 포함되면 여전히 유효할 수 있다.

이 문서는 모든 정책 규칙을 정의하지 않는다. 여기서 이 구분을 사용하는 목적은 범주 오류를 막기 위해서다.

### 구현 세부사항

Bitcoin Core의 함수와 파일명은 구현 측면의 근거다.

| File | Relevant Role |
|---|---|
| `src/primitives/transaction.h` | Transaction, input, output, and outpoint structures |
| `src/consensus/tx_check.cpp` | Context-free transaction checks |
| `src/consensus/tx_verify.cpp` | UTXO-dependent input and fee checks |
| `src/validation.cpp` | Block validation, coinbase placement, reward checks |
| `src/node/miner.cpp` | Candidate block and coinbase construction |
| `src/consensus/amount.h` | Amount unit and range constants |

### 마이닝 관행

다음은 직접적인 합의 규칙이 아니라 마이닝 관행 또는 운영 관행이다.

- 코인베이스 스크립트 데이터 안의 풀 태그
- extra nonce 레이아웃
- 보상 지급 주소 귀속(attribution)
- 풀 워커 식별자
- 풀 보상 분배
- 트랜잭션 선택 전략
- 채굴자가 보상을 덜 청구할지 여부
- 템플릿 새로고침 정책의 정확한 형태

분석가는 마이닝 관행을 프로토콜에 의해 인증된 사실처럼 다루지 않아야 한다.

## 10. Institutional Thinking

### 왜 코인베이스 분석이 중요한가

코인베이스 데이터는 다음을 연결하기 때문에 중요하다.

- 블록 생산
- 채굴자 보상
- 수수료 포착
- 보상 목적지 스크립트
- 블록 템플릿 구성
- 잠재적인 풀 메타데이터
- 작업증명 탐색 공간 확장

기관 분석가의 관점에서 보면, 코인베이스 트랜잭션은 고가치 증거 객체다. 직접 관측 가능하고, 합의 규칙과 관련되며, 경제적으로도 의미가 있다.

### 코인베이스 데이터가 뒷받침할 수 있는 것

코인베이스 데이터는 다음을 뒷받침할 수 있다.

- 수수료와 보조금 회계
- 블록 보상 검증
- underclaim 탐지
- payout script 군집화
- 마이닝 풀 귀속 가설
- 블록 구성 분석
- extra nonce 패턴 분석
- 역사적 채굴자 행동 연구

### 코인베이스 데이터만으로 증명할 수 없는 것

코인베이스 데이터만으로는 다음을 증명할 수 없다.

- 현실 세계의 채굴자 신원
- 물리적 해시 하드웨어 소유 관계
- 풀 참여자 분포
- 전력 비용
- 수익성
- 오프체인 지급 조건
- 풀 태그의 진위
- 어떤 엔티티가 트랜잭션 선택을 통제했는지

특히 코인베이스 태그는 위험하다. 태그는 특정 바이트가 코인베이스 트랜잭션 안에 존재한다는 사실만 증명한다. 보강 증거가 없다면 신원을 증명하지는 못한다.

### 기관용 통제 기준

연구 시스템은 다음을 수행해야 한다.

- 전체 UTXO 컨텍스트로부터 허용 가능한 코인베이스 값을 계산할 것
- 보조금과 수수료를 분리할 것
- raw 코인베이스 데이터를 보존할 것
- 단일 풀 라벨 소스에 의존하지 않을 것
- 독립 검증 전까지 채굴자 귀속을 휴리스틱으로 표시할 것
- 보상 underclaim와 overclaim 무효성을 분리해 추적할 것
- 분석이 풀노드 데이터, 인덱싱 데이터, 제3자 API 데이터 중 무엇을 사용하는지 문서화할 것

## 11. 사례 연구

### 사례 연구 1: 코인베이스 underclaim

관측:

```text
permitted reward: 3.205 BTC
coinbase outputs: 3.204 BTC
```

분류:

```text
FACT — ECL-A for arithmetic if UTXO input values are known.
INTERPRETATION — ECL-B for miner motivation.
```

결론:

이 블록은 사용 가능한 보상보다 `0.001 BTC`를 덜 청구한다. 그렇다고 블록이 무효가 되지는 않는다. 이 금액만으로 underclaim 이유를 알 수는 없다.

### 사례 연구 2: 과도한 코인베이스 청구

관측:

```text
permitted reward: 3.205 BTC
coinbase outputs: 3.206 BTC
```

분류:

```text
FACT — ECL-A if fee and subsidy inputs are verified.
```

결론:

이 블록은 보상 금액 규칙을 위반하므로 완전 검증 노드는 이를 거부해야 한다.

### 사례 연구 3: 풀 태그 귀속

관측:

```text
coinbase script contains recognizable pool text
```

분류:

```text
FACT — ECL-A for byte presence.
INTERPRETATION — ECL-C for real-world attribution without corroboration.
```

결론:

이 태그는 귀속 가설을 뒷받침할 수는 있지만, 신원 증명은 아니다. payout 주소, 풀 공지, 과거 태그 패턴, 독립 데이터셋과 함께 교차 검증해야 한다.

### 사례 연구 4: Extra Nonce 패턴

관측:

```text
coinbase script contains bytes that change across candidate blocks or pool work units
```

분류:

```text
FACT — ECL-A for observed byte changes.
INTERPRETATION — ECL-B for extra-nonce role if consistent with mining behavior.
```

결론:

바뀌는 바이트는 새로운 머클 루트와 헤더 탐색 공간을 만들기 위해 사용되는 extra nonce 데이터일 수 있다. 정확한 풀 프로토콜상의 의미를 확인하려면 외부 증거가 필요하다.

## 12. 흔한 오해

### 오해 1: 코인베이스 트랜잭션은 Coinbase 거래소에서 온다.

틀렸다. Bitcoin에서 coinbase는 블록의 특별한 첫 번째 트랜잭션을 가리키는 프로토콜 용어다. Coinbase라는 회사와는 무관하다.

### 오해 2: 채굴자는 임의의 bitcoin을 만들어낼 수 있다.

틀렸다. 채굴자는 코인베이스 트랜잭션을 구성할 수 있지만, 코인베이스 출력값이 보조금과 포함된 수수료의 합을 초과하면 풀노드가 그 블록을 거부한다.[^ref-btc-core-validation]

### 오해 3: 수수료는 각 트랜잭션에 명시된 출력이다.

틀렸다. 수수료는 입력값과 출력값의 차이다. 이는 블록의 코인베이스 트랜잭션이 집계해서 청구한다.

### 오해 4: Extra nonce는 블록 헤더 필드다.

틀렸다. 블록 헤더에는 32비트 nonce 필드가 있다. extra nonce는 일반적으로 코인베이스가 제어하는 데이터에 배치되는 마이닝 관행이며, 이를 바꾸면 머클 루트와 헤더가 함께 바뀐다.

### 오해 5: 유효한 작업증명 해시는 코인베이스 금액까지 검증한다.

틀렸다. 작업증명은 헤더의 작업량 주장만 검증한다. 블록은 여전히 트랜잭션, UTXO, 스크립트, 머클 루트, 보상 검증을 통과해야 한다.

### 오해 6: 코인베이스 태그는 풀 신원을 증명한다.

틀렸다. 태그는 트랜잭션 안의 데이터일 뿐이다. 귀속에는 보강 증거가 필요하다.

## 15. 요약

코인베이스 트랜잭션은 Bitcoin 블록의 특별한 첫 번째 트랜잭션이다. 이 트랜잭션은 채굴자가 블록 보조금과 포함된 거래 수수료를 청구하는 메커니즘이다.

코인베이스 트랜잭션은 합의 규칙의 제약을 받는다. 임의의 bitcoin을 만들어낼 수 없다. 출력값은 허용된 보조금과 수수료의 합을 초과할 수 없으며, 완전 검증 노드는 블록 검증 과정에서 이를 강제한다.

코인베이스 트랜잭션은 작업증명 메커니즘 측면에서도 중요하다. 이 트랜잭션은 트랜잭션 머클 트리의 일부이므로, 코인베이스 데이터를 바꾸면 머클 루트가 바뀌고, 결국 해시되는 블록 헤더가 바뀐다. 이를 통해 채굴자는 헤더 nonce를 넘어서는 탐색 공간을 확보할 수 있다.

분석가에게 코인베이스 데이터는 강력하지만 제한적인 증거다. 보상 회계, 수수료 분석, 귀속 가설 수립을 지원할 수 있다. 그러나 이것만으로 채굴자 신원, 수익성, 풀 소유권, 오프체인 지급 규칙을 증명하지는 못한다.
