## 3. Executive Summary

난이도 조정은 전체 마이닝 해시레이트가 변해도 장기적으로 블록 생성 속도를 목표 간격 근처에 유지하도록 만드는 Bitcoin의 메커니즘이다.

Bitcoin 메인넷에서 합의 파라미터는 다음과 같이 설정된다.

```text
target timespan = 14 days
target spacing  = 10 minutes
adjustment interval = 14 days / 10 minutes = 2016 blocks
```

Bitcoin Core 메인넷 파라미터는 `nPowTargetTimespan`을 `14 * 24 * 60 * 60`, `nPowTargetSpacing`을 `10 * 60`, `fPowAllowMinDifficultyBlocks`를 `false`, `fPowNoRetargeting`을 `false`로 설정한다.[^ref-btc-core-chainparams]

개념적으로 리타깃은 다음 공식을 적용한다.

```text
new_target = old_target * actual_timespan / target_timespan
```

블록이 너무 빨리 도착했다면 `actual_timespan`은 예상보다 작고, 목표값(Target)은 낮아지며, 난이도는 올라간다. 반대로 블록이 너무 느리게 도착했다면 목표값은 높아지고 난이도는 내려간다.

Bitcoin Core는 `actual_timespan`을 목표 시간 범위의 1/4배와 4배 사이로 제한하고, 새로운 목표값을 `powLimit` 상한으로 캡하며, 그 결과를 compact `nBits`로 반환한다.[^ref-btc-core-pow]

난이도 조정이 다음 블록이 정확히 10분 뒤에 나온다는 뜻은 아니다. 이것이 바꾸는 것은 장기 기대 생성 속도이며, 개별 블록 발견은 여전히 확률적이다.

Bitcoin Developer 문서 역시 평균 블록 간격을 약 10분으로 유지하기 위해 난이도가 2016블록마다 조정된다고 설명하며, 이는 여기서 다루는 구현 수준 파라미터와 일치한다.[^ref-btc-dev-blockchain]

## 4. 정의와 범위

난이도 조정은 정해진 간격마다 작업증명 목표값을 다시 계산하는 합의 절차다.

목표값은 블록 해시가 만족해야 하는 임계치다.

```text
block_hash <= target
```

난이도는 이 목표값이 암시하는 상대적 난이도다. 목표값이 낮을수록 허용되는 해시 수가 줄어들고, 기대 작업량은 증가한다.

이 문서는 Bitcoin 메인넷 동작을 중심으로 다루며, testnet, testnet4, signet, regtest 차이는 명시적으로 분리한다.

---

## 5. 역사적 배경

Bitcoin 백서는 작업증명 난이도가 시간당 평균 블록 수를 목표로 하는 이동 평균 방식으로 결정되며, 블록이 너무 빨리 생성되면 난이도가 상승한다고 설명한다.[^ref-btc-wp]

백서는 설계 의도를 설명하지만, 현대 구현의 세부 사항까지 모두 담고 있지는 않다. 현재 Bitcoin Core 구현은 정확한 리타깃 간격, 시간 범위 클램프, compact 인코딩, 네트워크별 예외, 검증 체크를 구체적으로 정의한다.

## 6. 원래 설계

원래 설계가 풀고자 한 문제는 단순하다.

```text
hash rate can change
↓
fixed target would change block interval
↓
difficulty adjustment restores long-run expected spacing
```

전체 해시레이트가 올라가는데 목표값이 고정되어 있으면 평균적으로 블록은 더 빨리 도착한다. 해시레이트가 내려가고 목표값이 그대로면 블록은 더 느려진다.

난이도 조정은 피드백 메커니즘이다. 과거 일정 구간의 블록 타임스탬프를 관찰하고, 그 결과를 바탕으로 미래 블록이 요구하는 작업량을 조정한다.

## 7. 프로토콜 구조

메인넷 리타깃은 다음 요소에 의존한다.

| 개념 | 메인넷 값 또는 역할 |
|---|---|
| 목표 간격 | 10분 |
| 목표 시간 범위 | 14일 |
| 조정 간격 | 2016블록 |
| 이전 목표값 | 직전 `nBits`에 인코딩됨 |
| 실제 경과 시간 | 리타깃 구간 양 끝 블록의 타임스탬프 차이 |
| 클램프 | 목표 시간 범위의 0.25배에서 4배 사이 |
| `powLimit` | 허용되는 가장 쉬운 목표값 |
| 출력 | 새로운 compact `nBits` |

간격은 다음과 같다.

```text
14 days * 24 hours/day * 60 minutes/hour
----------------------------------------- = 2016 blocks
10 minutes/block
```

Bitcoin Core는 이를 합의 파라미터와 `DifficultyAdjustmentInterval()`로 노출한다.[^ref-btc-core-chainparams]

## 8. 기술적 메커니즘

### 8.1 리타깃이 아닌 블록

메인넷에서 다음 높이가 난이도 조정 경계가 아니라면, `GetNextWorkRequired`는 이전 블록의 `nBits`를 그대로 반환한다.[^ref-btc-core-pow]

개념적으로는 다음과 같다.

```text
if (next_height % 2016 != 0):
    next_nBits = previous_nBits
```

이 때문에 메인넷 난이도는 빠른 블록이나 느린 블록이 나온 직후 곧바로 반응하지 않는다.

### 8.2 리타깃 경계

리타깃 경계에서는 Bitcoin Core가 조정 윈도우의 첫 블록을 찾는다.

```text
nHeightFirst = pindexLast.height - (DifficultyAdjustmentInterval - 1)
```

그 다음 마지막 블록과 첫 블록의 시간을 `CalculateNextWorkRequired`로 전달한다.[^ref-btc-core-pow]

### 8.3 실제 경과 시간

Bitcoin Core는 다음을 계산한다.

```text
actual_timespan = last_block_time - first_block_time
```

그 다음 구현은 이 값을 다음 범위로 제한한다.

```text
minimum = target_timespan / 4
maximum = target_timespan * 4
```

이것은 한 번의 조정 기간에서 난이도가 최대 4배 상승하거나 최대 4배 하락하도록 제한하는 효과를 낸다.[^ref-btc-core-pow]

### 8.4 새로운 목표값

새로운 목표값은 다음과 같이 계산된다.

```text
new_target = old_target * actual_timespan / target_timespan
```

`new_target`이 `powLimit`를 넘으면 `powLimit`로 캡한다.[^ref-btc-core-pow]

결과는 다시 compact `nBits`로 인코딩된다.

## 9. 수학적 또는 경제적 모델

다음을 정의하자.

- `T_old`: 이전 목표값
- `T_new`: 새로운 목표값
- `A`: 실제 관측된 시간 범위
- `E`: 기대 목표 시간 범위

그러면:

```text
T_new = T_old * A / E
```

그리고:

```text
E = 14 days
A_clamped = min(max(A, E / 4), E * 4)
```

따라서 구현 수준 리타깃은 다음과 같다.

```text
T_new = T_old * A_clamped / E
```

간단한 예시:

```text
old target:        1000
expected timespan: 14 days
actual timespan:   7 days
```

그러면:

```text
new target = 1000 * 7 / 14 = 500
```

목표값은 절반이 되고 난이도는 두 배가 된다.

느린 블록 예시:

```text
old target:        1000
expected timespan: 14 days
actual timespan:  28 days
```

그러면:

```text
new target = 1000 * 28 / 14 = 2000
```

목표값은 두 배가 되고 난이도는 절반이 된다.

이것은 목표값 모델이지, 해시레이트를 직접 측정하는 모델이 아니다. 해시레이트 추정에는 경과 시간 동안의 기대 작업량에 대한 추가 가정이 필요하다.

## 10. 보안 가정

난이도 조정은 다음을 가정한다.

- 블록 타임스탬프가 리타깃에 사용할 수 있을 만큼 충분히 제약되어 있다.
- 채굴자가 임의로 더 쉬운 `nBits`를 고를 수 없다.
- 노드가 요구되는 `nBits`를 독립적으로 다시 계산한다.
- 목표값 변화는 클램프와 `powLimit`에 의해 제한된다.
- 해시레이트 변화는 즉시가 아니라 리타깃 윈도우를 통해 흡수된다.

난이도 조정은 모든 블록이 정확히 10분마다 도착한다고 가정하지 않는다.

또한 이것이 모든 타임스탬프 조작을 막는다는 뜻도 아니다. time-warp 관련 고려 사항이 존재하며, Bitcoin Core는 허용 가능한 난이도 전이 로직과 더 새로운 네트워크별 BIP94 동작 같은 추가 체크도 포함한다.[^ref-btc-core-pow][^ref-bip-0094]

## 11. 실패 모드와 공격 표면

### 단기 블록 분산

목표값이 완벽히 보정되어 있어도 블록 발견은 여전히 무작위다. 연속된 빠른 블록이나 느린 블록 몇 개만으로 난이도 계산이 잘못되었다고 볼 수는 없다.

### 리타깃 이전의 해시레이트 충격

리타깃 직후 해시레이트가 급격히 변하면, 다음 조정 전까지 블록 간격이 비정상적으로 빠르거나 느릴 수 있다.

### 타임스탬프 조작

리타깃은 블록 타임스탬프를 사용한다. 악의적이거나 전략적인 타임스탬프 선택은 합의 제약 안에서 측정 시간 범위에 영향을 줄 수 있다. 그래서 타임스탬프 규칙과 time-warp 논의가 중요하다.

### Testnet 최소 난이도 예외

테스트 네트워크는 메인넷과 달리 최소 난이도 블록을 허용할 수 있다. 분석가는 이런 동작을 메인넷 해석에 가져오면 안 된다.

### Explorer 난이도 혼동

익스플로러는 사람이 읽기 쉬운 난이도 수치를 보여주는 경우가 많다. 그러나 합의가 실제로 사용하는 것은 `nBits`에 인코딩된 목표값이며, 난이도 표시는 파생값이고 표시 규칙이나 반올림이 개입될 수 있다.

## 12. Bitcoin Core 또는 프로토콜 구현

### 메인넷 파라미터

Bitcoin Core 메인넷 파라미터에는 다음이 포함된다.

```text
powLimit = 00000000ffffffffffffffffffffffffffffffffffffffffffffffffffffffff
nPowTargetTimespan = 14 * 24 * 60 * 60
nPowTargetSpacing = 10 * 60
fPowAllowMinDifficultyBlocks = false
fPowNoRetargeting = false
```

이 파라미터들이 메인넷 리타깃 환경을 정의한다.[^ref-btc-core-chainparams]

### `GetNextWorkRequired`

`GetNextWorkRequired`는 리타깃 시점인지 여부를 판단한다. 다음 높이가 조정 경계가 아니라면, 메인넷에서는 이전 블록의 `nBits`를 그대로 반환한다.[^ref-btc-core-pow]

다음 높이가 조정 경계라면, 해당 함수는 구간의 첫 블록을 찾은 뒤 `CalculateNextWorkRequired`를 호출한다.

### `CalculateNextWorkRequired`

`CalculateNextWorkRequired`는 다음 순서로 동작한다.

1. `fPowNoRetargeting`이 켜져 있으면 이전 `nBits`를 그대로 반환한다.
2. 마지막 블록 시간에서 첫 블록 시간을 빼서 실제 시간 범위를 계산한다.
3. 실제 시간 범위를 `[target_timespan / 4, target_timespan * 4]`로 클램프한다.
4. 이전 목표값을 디코딩한다.
5. 실제 시간 범위를 곱한다.
6. 목표 시간 범위로 나눈다.
7. 목표값을 `powLimit`로 캡한다.
8. compact `nBits`를 반환한다.[^ref-btc-core-pow]

### `PermittedDifficultyTransition`

Bitcoin Core에는 `PermittedDifficultyTransition`도 존재하며, 제안된 난이도 전이가 허용 범위 안에 있는지 확인한다. 이는 검증 로직과 연결되며, 허용된 규칙 바깥의 잘못된 목표값 전이를 받아들이지 않도록 한다.[^ref-btc-core-pow]

## 13. 관련 표준 및 BIP

### BIP94 — Testnet 4

BIP94는 testnet4와 관련된다. Bitcoin Core의 리타깃 코드는 BIP94 동작을 강제할 때 기간의 첫 블록이 가진 실제 난이도를 유지하는 testnet4 전용 경로를 포함한다.[^ref-btc-core-pow][^ref-bip-0094]

이것은 메인넷 동작이 아니다.

### Compact Target Encoding

리타깃은 전체 목표값을 계산한 뒤 결과를 compact `nBits`에 저장한다. 인코딩 세부 사항은 `POW-007`에서 다룬다.

## 14. 현대적 맥락

난이도 조정은 흔히 "정확히 10분마다 한 블록을 맞춘다"는 식으로 설명되지만, 더 정확한 표현은 다음과 같다.

```text
Bitcoin adjusts the target so expected long-run block spacing remains near 10 minutes.
```

리타깃은 후행적이다. 직전 조정 윈도우를 보고 반응하며, 해시레이트 충격을 즉시 교정하지는 못한다.

시장 분석에서는 난이도 변화가 채굴자 행동 신호처럼 해석되곤 한다. 이 해석은 유용할 수 있지만, 인과 경로를 분해해야 한다.

```text
observed block timestamps
↓
retarget calculation
↓
new target
↓
derived difficulty
↓
possible hash-rate interpretation
```

마지막 단계의 해석은 해시레이트 동학, 타임스탬프 정확성, 채굴자 유인에 대한 가정에 의존한다.

- 타임스탬프 선택 행태

### 현재 결론

FACT — 목표값과 `nBits` 변화 자체에 대해서는 ECL-A.  
INTERPRETATION — 해시레이트 추론에 대해서는 ECL-B.

현재 해시레이트를 한 개 블록 간격만 보고 추정하지 말 것.

난이도 변화 논의는 반드시 다음 범위를 기준으로 해야 한다.

```text
2016-block window on mainnet
```

난이도 변화 계산에는 목표값 비율을 사용한다.

```text
difficulty_new / difficulty_old = target_old / target_new
```

목표값이 높을수록 난이도는 낮고, 목표값이 낮을수록 난이도는 높다는 점을 항상 기억해야 한다.

testnet의 최소 난이도 동작을 메인넷에 적용하지 말 것.

## 19. 반증과 한계

백서는 난이도 조정의 아이디어를 제시하지만, 현대 구현의 전체 알고리즘까지 명세하지는 않는다. 현재 동작은 구현과 네트워크 파라미터를 기준으로 확인해야 한다.

2016블록 윈도우는 흔히 2주라고 설명되지만, 실제 관측 시간 범위는 구간 양 끝 블록의 타임스탬프로 계산되며 실제 벽시계 기준 2주와 정확히 같을 필요는 없다.

Bitcoin Core의 리타깃 로직은 네트워크별 분기들을 포함한다. 메인넷, testnet, testnet4, signet, regtest는 분리해서 봐야 한다.

난이도 조정은 타임스탬프를 사용하므로, 타임스탬프 조작과 time-warp 관련 고려가 한계로 남는다. 이 문서는 이 이슈를 표시하지만, time-warp 공격 자체를 완전히 분석하지는 않는다.

난이도로부터 해시레이트를 추정하는 것은 모델 의존적이다. 난이도는 프로토콜 출력이지만, 해시레이트는 추정값이다.
