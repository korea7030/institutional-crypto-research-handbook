## 3. Executive Summary

Cumulative chainwork is the sum of target-derived expected work represented by each valid block in a branch. It is the quantitative basis for comparing Bitcoin branches under Proof of Work.

Bitcoin Core stores cumulative work in `CBlockIndex::nChainWork`, documented as the total expected work in the chain up to and including a block.[^ref-btc-core-chain] Per-block work is computed from `nBits` through `GetBlockProof`, which returns `GetBitsProof(block.nBits)`.[^ref-btc-core-chain]

Bitcoin Core's `GetBitsProof` decodes compact `nBits` into a target and returns zero if the decoded target is negative, overflowing, or zero. Otherwise it computes the amount of work corresponding to the target using an integer form equivalent to:

```text
floor(2^256 / (target + 1))
```

The `+ 1` matters because all hash outputs from `0` through `target` are valid, so the number of valid outputs is `target + 1`.[^ref-btc-core-chainwork]

Chainwork is not computed from the exact winning hash. A block whose hash barely satisfies the target and a block whose hash is far below the target contribute the same per-block work if they have the same valid `nBits`. The network credits expected work represented by the target, not observed luck.

---

## 4. Definition and Scope

Cumulative chainwork is:

```text
the sum of per-block expected work from genesis to a branch tip
```

Per-block work is derived from the block's encoded target. It is not:

- the number of actual hashes attempted,
- the exact electricity consumed,
- the exact ASIC fleet size,
- the exact value of the winning block hash,
- the number of blocks in the branch.

This document studies chainwork as a consensus and analysis concept. It does not estimate real mining cost or attacker profitability.

## 5. Historical Background

The Bitcoin Whitepaper describes the accepted history as the chain with the greatest Proof-of-Work effort invested in it.[^ref-btc-wp]

The whitepaper often uses the shorthand "longest chain." In modern Bitcoin analysis, cumulative work is the precise measure because work per block changes with difficulty.

Bitcoin Developer documentation for full nodes states that an adversary would need to provide an alternative history with greater difficulty than the current chain and describes the chain with most cumulative Proof of Work as the true chain under that security model.[^ref-btc-dev-operating]

---

## 6. Original Design

The original design idea is:

```text
more proof-of-work effort
↓
stronger accepted history
↓
harder to replace past transactions
```

The whitepaper's security argument depends on the attacker needing to redo work for a modified block and then catch up with the work added after it.[^ref-btc-wp]

Modern Bitcoin operationalizes this idea by assigning each valid block a work value derived from its target and accumulating those values through the block index.

---

## 7. Protocol Structure

Each block header contains:

```text
nBits
```

`nBits` compactly encodes the target threshold. A valid block hash must be less than or equal to that target.

The chainwork dependency graph is:

```text
nBits
↓
decoded target
↓
per-block work
↓
parent chainwork + per-block work
↓
tip chainwork
↓
branch comparison
```

Bitcoin Core's `CBlockIndex` stores:

| Field | Role |
|---|---|
| `nBits` | Compact target for the block. |
| `pprev` | Pointer to parent block index. |
| `nHeight` | Block height. |
| `nChainWork` | Cumulative work through this block. |

`nHeight` and `nChainWork` are related but not equivalent. Height counts blocks. Chainwork sums target-derived expected work.

## 8. Technical Mechanics

### 8.1 Decode the Target

The block's `nBits` value is decoded into a target using Bitcoin's compact encoding rules. If the target is invalid, it cannot contribute valid accepted chainwork.

Bitcoin Core's `GetBitsProof` calls `SetCompact(bits, &fNegative, &fOverflow)` and returns zero when the decoded value is negative, overflowing, or zero.[^ref-btc-core-chainwork]

### 8.2 Compute Per-Block Work

Conceptually:

```text
block_work = floor(2^256 / (target + 1))
```

Bitcoin Core cannot directly represent `2^256` in a 256-bit integer, so it uses the equivalent integer expression:

```text
(~target / (target + 1)) + 1
```

where `~target` represents `2^256 - target - 1` in the 256-bit unsigned integer domain.[^ref-btc-core-chainwork]

### 8.3 Accumulate Chainwork

Conceptually:

```text
chainwork(block) = chainwork(parent) + block_work(block)
```

For a branch:

```text
chainwork(tip) = Σ block_work(block_i)
```

Bitcoin Core stores this cumulative value in `nChainWork` and includes internal consistency checks that non-genesis blocks have chainwork greater than or equal to their parent chainwork.[^ref-btc-core-validation]

### 8.4 Compare Branches

To compare two valid branches:

```text
if chainwork(branch_A_tip) > chainwork(branch_B_tip):
    branch_A has more cumulative work
else:
    branch_B has more cumulative work
```

Chain selection still requires validation and available block data. Chainwork alone is not enough if the branch is invalid or not fully available for validation.

## 9. Mathematical or Economic Model

Let:

- `T` be the decoded target.
- `N = 2^256` be the size of the SHA-256 hash-output space.
- `p` be one hash attempt's success probability.
- `E` be expected attempts per success.

Because valid outputs are:

```text
0, 1, 2, ..., T
```

the number of valid outputs is:

```text
T + 1
```

Therefore:

```text
p = (T + 1) / 2^256
```

and expected attempts are:

```text
E = 1 / p = 2^256 / (T + 1)
```

Bitcoin Core uses integer work:

```text
block_work = floor(2^256 / (T + 1))
```

Toy example:

```text
hash space: 0..255
target: 15
valid outputs: 0..15
success probability: 16 / 256
expected attempts: 256 / 16 = 16
block_work: 16
```

If two branches differ:

| Branch | Blocks | Work per block | Cumulative work |
|---|---:|---:|---:|
| A | 5 | 16 | 80 |
| B | 4 | 24 | 96 |

Branch B has fewer blocks but more cumulative work.

This toy example uses a small hash space for clarity. Bitcoin uses a 256-bit hash space and compact target encoding.

## 10. Security Assumptions

Chainwork assumes:

- valid compact targets,
- valid Proof of Work,
- independently validated block headers,
- correct parent linkage,
- no credit for invalid branches,
- SHA-256d outputs are practically unpredictable and modeled as uniformly distributed.

Chainwork does not prove:

- exact number of hashes attempted,
- exact energy spent,
- miner identity,
- miner honesty,
- transaction finality in an absolute sense.

It measures expected work implied by accepted target thresholds.

## 11. Failure Modes and Attack Surface

### Counting Blocks Instead of Work

An analyst may incorrectly compare branches by height alone. This can be wrong when per-block work differs.

### Crediting Winning Hash Luck

A block hash far below target looks visually impressive, but Bitcoin does not credit extra chainwork for it. Work is derived from target, not from how far below target the winning hash landed.

### Counting Invalid Work

An invalid branch may contain headers that appear to represent work. Accepted chainwork analysis must exclude branches that fail consensus validation.

### Confusing Hash Rate With Chainwork

Hash rate is an estimate of attempts per second. Chainwork is target-derived expected work accumulated across accepted blocks. They are related, but one is not the other.

### Overstating Reorg Cost

Chainwork difference estimates target-derived expected work, not guaranteed attacker cost. Real cost depends on hardware, electricity, opportunity cost, market access, and timing.

## 12. Bitcoin Core or Protocol Implementation

Bitcoin Core implements the core chainwork model across `chain.h`, `chain.cpp`, and validation logic.

### `CBlockIndex::nChainWork`

`CBlockIndex::nChainWork` stores cumulative expected work in the chain up to and including a block.[^ref-btc-core-chain]

### `GetBlockProof`

`GetBlockProof` returns `GetBitsProof(block.nBits)`, so per-block work is derived from the compact target field.[^ref-btc-core-chain]

### `GetBitsProof`

`GetBitsProof`:

1. Decodes `nBits` with `SetCompact`.
2. Returns zero for negative, overflowing, or zero targets.
3. Computes target-derived work using an integer expression equivalent to `floor(2^256 / (target + 1))`.[^ref-btc-core-chainwork]

### Validation Consistency

Bitcoin Core's validation consistency checks assert that every non-genesis block's chainwork is at least as large as its parent's chainwork.[^ref-btc-core-validation]

### Chain Selection Link

`POW-010` covered how Bitcoin Core uses the resulting `nChainWork` in most-work chain selection. This document focuses on the arithmetic and interpretation behind that value.

## 14. Modern Context

Modern Bitcoin explorers, node software, and analysis systems may expose chainwork values directly or derive them from headers.

For institutional analysis, chainwork is often more useful than height when discussing:

- branch comparison,
- reorg cost,
- confirmation depth,
- synchronization security,
- alternative branch risk.

However, chainwork should be paired with validation status. A high-work branch that is invalid is not accepted history.

## 15. On-Chain Implications

### Directly Observable

An analyst can observe:

- block headers,
- `nBits`,
- parent hashes,
- block height,
- active-chain sequence from a node's view.

### Deterministically Derivable

An analyst can derive:

- decoded target,
- per-block work,
- cumulative chainwork,
- work difference between two observed branches,
- estimated equivalent time using current tip work and target spacing, following the same concept as Bitcoin Core's `GetBlockProofEquivalentTime`.

### Estimated or Inferred

An analyst may estimate:

- hash rate from work accumulated over wall-clock time,
- economic cost to replace a branch,
- attacker feasibility,
- settlement confidence.

### Unobservable From Chainwork Alone

Chainwork alone does not reveal:

- actual hashes attempted,
- exact electricity consumed,
- miner cost basis,
- miner identity,
- whether a reorg attempt is underway,
- the reason a branch lost.

## 16. Institutional Thinking

### Observation

A transaction has six confirmations on a branch whose blocks have accumulated additional chainwork after the transaction.

### Weak Interpretation

"Six confirmations means the transaction is final."

### Institutional Decomposition

An institutional researcher should separate:

- number of confirmations,
- cumulative work after the transaction,
- current hash-rate environment,
- potential attacker resources,
- value at risk,
- exchange or custody settlement policy,
- observed stale and reorg conditions.

### Current Conclusion

Confirmations are a user-facing proxy. Cumulative work is the more precise technical measure of how much target-derived work an attacker must replace to remove a transaction from the active branch.

### Confidence

FACT — ECL-A for computing cumulative chainwork from valid headers.  
INTERPRETATION — ECL-B for translating chainwork into economic settlement confidence.

## 17. Analyst Notes

Use chainwork when comparing branches. Use height only when all compared blocks have comparable work or when height is the explicit subject.

Do not give extra work credit to a block because its hash is far below target.

When estimating hash rate:

```text
estimated_hash_rate =
work_accumulated / elapsed_time
```

State the measurement window and remember that block arrivals are probabilistic.

When discussing reorgs, report both:

```text
reorg depth in blocks
```

and, when possible:

```text
work difference
```

## 18. Common Misinterpretations

### Misinterpretation

> Chainwork is the number of actual hashes miners performed.

### Assessment

Incorrect.

### Correction

Chainwork is expected work derived from targets. Actual failed hashes are not recorded on-chain.

### Misinterpretation

> A hash far below target contributes more chainwork.

### Assessment

Incorrect.

### Correction

Per-block work is derived from `nBits`, not from the winning hash's distance below target.

### Misinterpretation

> The branch with the highest height always has the most chainwork.

### Assessment

Incomplete.

### Correction

Height counts blocks. Chainwork sums target-derived work. Different targets can make fewer blocks represent more work.

### Misinterpretation

> Chainwork proves energy consumption exactly.

### Assessment

Incorrect.

### Correction

Chainwork measures expected hash attempts implied by target thresholds. Energy depends on hardware efficiency and operating conditions.

### Misinterpretation

> Chainwork alone validates a chain.

### Assessment

Incorrect.

### Correction

A branch must satisfy all applicable consensus rules. Chainwork is one input to selecting among valid candidate branches.

## 19. Counter Evidence and Limitations

The chainwork formula is exact for Bitcoin Core's target-derived work accounting, but it is still an expected-work model. It does not reveal actual hashes performed.

The calculation depends on correct compact target decoding. Invalid compact targets produce no valid accepted work.

Bitcoin Core documentation and source code are primary implementation evidence for Bitcoin Core. Other implementations may structure the calculation differently internally, but consensus-compatible nodes must agree on valid headers and branch selection results.

Economic interpretations of chainwork require assumptions about hardware markets, electricity prices, pool behavior, and opportunity cost. Those assumptions are not contained in the blockchain.
