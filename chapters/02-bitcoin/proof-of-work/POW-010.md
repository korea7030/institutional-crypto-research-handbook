## 3. Executive Summary

Bitcoin chain selection is the process by which a node chooses one active branch from a tree of known block headers and blocks. The whitepaper describes nodes as accepting the "longest chain" and working on extending it, while also describing that chain as the one representing the greatest Proof-of-Work effort.[^ref-btc-wp]

In modern technical language, the safer phrase is:

```text
valid chain with the greatest cumulative proof of work
```

This matters because block count and work are not identical. Each block contributes work according to its target. If difficulty differs across branches, a shorter branch can theoretically represent more work than a longer branch.[^ref-btc-core-chainwork]

Bitcoin Core tracks cumulative work in `CBlockIndex::nChainWork`, described as the total expected work in the chain up to and including a block.[^ref-btc-core-chain] Bitcoin Core's `FindMostWorkChain` selects a candidate tip with the most work that is not known invalid and for which needed block data is available; `ActivateBestChain` then attempts to make that branch active.[^ref-btc-core-validation]

Chain selection is not a popularity vote and not a miner identity vote. It is local node logic over validated block data and accumulated work. Relay helps nodes learn candidates; validation and cumulative work determine local activation. Bitcoin Developer documentation describes the practical rule as choosing the block chain with the most cumulative difficulty.[^ref-btc-dev-blockchain]

## 4. Definition and Scope

Chain selection is a node's local procedure for choosing its active chain from known candidate branches.

This procedure is constrained by three requirements:

```text
known block data
+
validity
+
greatest cumulative work
```

This document focuses on Proof-of-Work chain selection. It does not fully cover reorg mempool handling, wallet confirmation policy, economic finality, or attacker probability models.

---

## 5. Historical Background

The whitepaper introduces chain selection in the Proof-of-Work and Network sections. Section 4 says the majority decision is represented by the longest chain, which has the greatest Proof-of-Work effort invested in it. Section 5 says nodes express acceptance of a block by working on the next block using the accepted block's hash as the previous hash.[^ref-btc-wp]

The phrase "longest chain" was understandable in the simplified whitepaper model. However, Bitcoin's difficulty changes over time, and work per block depends on the target. Therefore, modern explanations should not reduce chain selection to simple height or block count.

Bitcoin Developer documentation for operating modes describes full-node security in terms of the chain with the most cumulative Proof of Work.[^ref-btc-dev-operating]

## 6. Original Design

The original design can be summarized as:

```text
nodes learn blocks
↓
nodes validate blocks
↓
nodes identify the branch with the most work
↓
nodes build on that branch
```

The whitepaper's fork-resolution model is probabilistic. If two blocks are found nearly simultaneously, nodes may initially disagree. The branch that receives the next valid Proof-of-Work extension becomes the one nodes converge toward.[^ref-btc-wp]

This is not instant finality. It is eventual convergence under the assumption that honest work continues to extend one valid branch faster than an attacker can replace it.

## 7. Protocol Structure

Bitcoin's block graph is a tree rooted at the genesis block. Each non-genesis block points to exactly one predecessor through the previous-block hash field.

Conceptually:

```text
Genesis
  |
  A
  |
  B
 / \
C   C'
|   |
D   D'
```

At any moment, a node may know multiple valid branches. One branch is active. Other branches may be valid but inactive.

Important concepts:

| Concept | Meaning |
|---|---|
| Block height | Number of links from genesis to a block. |
| Block work | Expected work represented by one block's target. |
| Chainwork | Sum of block work from genesis to a given block. |
| Active chain | The branch currently selected by the node. |
| Competing branch | A valid branch not currently active. |
| Stale block | A valid block not in the active chain. |
| Invalid branch | A branch containing a block that fails consensus validation. |

## 8. Technical Mechanics

### 8.1 Work Per Block

Bitcoin Core computes block work from `nBits`. The `GetBitsProof` function decodes the compact target and returns the amount of work corresponding to that target. Its implementation computes the work equivalent to:

```text
floor(2^256 / (target + 1))
```

using an integer form that avoids representing `2^256` directly in a 256-bit integer.[^ref-btc-core-chainwork]

### 8.2 Cumulative Chainwork

Conceptually:

```text
chainwork(block) =
chainwork(parent)
+
block_work(block)
```

Bitcoin Core stores this cumulative value as `nChainWork` in `CBlockIndex`.[^ref-btc-core-chain]

### 8.3 Candidate Selection

Bitcoin Core maintains candidate block-index entries and uses `FindMostWorkChain` to identify the tip of the chain with the most work that is not known invalid. The implementation also rejects candidates that are missing required block data.[^ref-btc-core-validation]

This detail matters for pruned or partially synced nodes. A header may represent more work, but a node cannot activate a chain without the required block data and validation state.

### 8.4 Branch Switching

When the best candidate is not the current active tip, Bitcoin Core's `ActivateBestChainStep` finds the fork point, disconnects active blocks that are no longer in the best chain, builds the list of blocks to connect, and connects new blocks toward the most-work candidate.[^ref-btc-core-validation]

At a high level:

```text
current active branch
↓
find fork point
↓
disconnect old branch blocks after fork
↓
connect new branch blocks after fork
↓
new active tip
```

This is the implementation basis for a reorganization.

## 9. Mathematical or Economic Model

Let:

- `W(B)` be work contributed by block `B`.
- `CW(B)` be cumulative work up to block `B`.
- `P(B)` be the parent of block `B`.

Then:

```text
CW(B) = CW(P(B)) + W(B)
```

For a branch from genesis to tip:

```text
CW(tip) = Σ W(block_i)
```

Toy example:

| Branch | Blocks after fork | Work per block | Added work |
|---|---:|---:|---:|
| Branch A | 3 | 100 | 300 |
| Branch B | 2 | 170 | 340 |

Branch A has more blocks. Branch B has more cumulative work.

If both branches are valid and known, a greatest-work selection rule chooses Branch B.

This toy model intentionally abstracts away `nBits` compact encoding, target validation, and activation preconditions. `POW-011` covers cumulative chainwork in greater numerical detail.

## 10. Security Assumptions

Chain selection relies on several assumptions:

- nodes independently validate blocks before activation,
- block work is computed from valid Proof-of-Work targets,
- honest nodes can learn enough competing branch data to compare work,
- invalid branches are not activated merely because they have high apparent work,
- the cost of replacing deeper history grows with cumulative work after the transaction.

These assumptions do not produce absolute finality. They produce probabilistic settlement: the deeper a transaction is buried under additional work, the more costly it becomes to replace under the standard Proof-of-Work model.

## 11. Failure Modes and Attack Surface

### Temporary Competing Blocks

Two miners can find valid blocks at similar times. Different nodes may see different blocks first. This creates temporary disagreement until one branch accumulates more work.

### Reorganization

A reorganization occurs when a node replaces part of its active chain with another valid branch. Reorgs can be natural or adversarial. The event alone does not prove malicious intent.

### Invalid High-Work Branch

A branch can contain high Proof of Work but fail consensus validation. Such a branch must not become active.

### Missing Data

A node may know a higher-work header but lack the block data needed to validate and connect the branch. Bitcoin Core's candidate selection accounts for missing block data.[^ref-btc-core-validation]

### Network Isolation

If a node is isolated from honest peers, it may have an incomplete view of competing work. Chain selection is local to the data the node knows.

## 12. Bitcoin Core or Protocol Implementation

Bitcoin Core's relevant structures and functions include:

| Component | Role |
|---|---|
| `CBlockIndex::nChainWork` | Stores cumulative expected work through a block. |
| `GetBitsProof` | Computes work represented by an `nBits` target. |
| `GetBlockProof` | Computes work for a block index entry or header from `nBits`. |
| `setBlockIndexCandidates` | Holds candidate tips with enough work relative to the current tip. |
| `FindMostWorkChain` | Finds the best candidate tip not known invalid and not missing required data. |
| `ActivateBestChain` | Attempts to make the best known chain active. |
| `ActivateBestChainStep` | Disconnects and connects blocks toward the most-work candidate. |

`CBlockIndex::nChainWork` is documented in `chain.h` as total expected work in the chain up to and including the block.[^ref-btc-core-chain]

`GetBlockProof` returns `GetBitsProof(block.nBits)`, so a block's work contribution derives from the compact target field.[^ref-btc-core-chain]

`FindMostWorkChain` selects from candidates using a work comparator and removes unusable candidates if they are known invalid or missing data.[^ref-btc-core-validation]

`ActivateBestChain` calls `FindMostWorkChain` when needed and then calls `ActivateBestChainStep` unless the most-work candidate is already the active tip.[^ref-btc-core-validation]

`ActivateBestChainStep` finds the fork point, disconnects active blocks after that fork, and connects blocks on the candidate branch.[^ref-btc-core-validation]

## 14. Modern Context

Modern Bitcoin discourse often still says "longest chain." This is acceptable only if the phrase is understood as shorthand for accumulated Proof-of-Work effort, not raw block count.

For institutional research, use:

```text
greatest cumulative work
```

or:

```text
most-work valid chain
```

This avoids ambiguity when comparing chains across difficulty changes, test networks, forks, or alternative clients.

The active chain is also node-local. Two honest nodes can briefly disagree because of propagation timing. They converge when they learn and validate the same most-work branch.

## 15. On-Chain Implications

### Directly Observable

An on-chain analyst can observe from a node's chain view:

- active-chain block height,
- parent linkage,
- block hashes,
- `nBits`,
- block timestamps,
- whether a block is in the active chain,
- cumulative chainwork if computed from headers.

### Derivable

An analyst can derive:

- work contribution from each valid header's `nBits`,
- cumulative chainwork along a branch,
- fork points between observed branches,
- reorg depth when competing branch data is available.

### Estimated or Observer-Dependent

An analyst may estimate:

- first-seen time of competing blocks,
- stale-block rate,
- propagation advantage,
- miner behavior during reorgs,
- whether a reorg was accidental or adversarial.

### Unobservable From Final Chain Alone

The final active chain alone does not reveal:

- all competing blocks that were never observed,
- exact propagation paths,
- which node saw which branch first,
- miner intent,
- private withholding behavior.

## 16. Institutional Thinking

### Observation

A transaction had six confirmations and later disappeared from the active chain after a seven-block reorganization.

### Weak Interpretation

"The transaction was final and then Bitcoin broke."

### Institutional Decomposition

An institutional researcher should separate:

- confirmation count,
- cumulative work after the transaction,
- competing branch work,
- validity of both branches,
- timing of block discovery,
- network propagation data,
- miner or pool attribution,
- whether the event is natural or adversarial.

### Current Conclusion

Confirmations are evidence of increasing replacement cost, not absolute finality. A reorg replacing confirmed blocks is serious, but the chain-selection rule itself expects nodes to follow the valid branch with greater cumulative work.

### Confidence

FACT — ECL-A for reorg detection from validated branch data.  
INTERPRETATION — ECL-B or ECL-C for cause attribution without independent network and miner evidence.

## 17. Analyst Notes

Do not write:

```text
Bitcoin always follows the chain with the most blocks.
```

Write:

```text
Bitcoin nodes select the valid known chain with the greatest cumulative Proof of Work.
```

Do not treat confirmations as a binary finality threshold. Treat them as increasing work depth.

When analyzing reorgs, report:

- fork height,
- old active tip,
- new active tip,
- reorg depth,
- work difference when available,
- affected transactions,
- whether competing block data was observed directly.

## 18. Common Misinterpretations

### Misinterpretation

> Longest chain means the branch with the most blocks.

### Assessment

Incomplete.

### Correction

The whitepaper phrase refers to the branch representing the greatest Proof-of-Work effort. Modern writing should use cumulative work rather than block count.

### Misinterpretation

> A higher-work header alone is enough to reorganize the chain.

### Assessment

Incorrect.

### Correction

A node must have and validate the required block data before activating a candidate branch.

### Misinterpretation

> Miners decide the valid chain.

### Assessment

Incomplete.

### Correction

Miners produce work on candidate branches. Full nodes independently validate blocks and activate the valid known branch with greatest cumulative work.

### Misinterpretation

> Reorgs prove an attack.

### Assessment

Unsupported.

### Correction

Reorgs can happen naturally because of network latency and simultaneous block discovery. Attack attribution requires additional evidence.

### Misinterpretation

> Confirmed transactions are impossible to reverse.

### Assessment

Incorrect.

### Correction

Confirmations increase the cost and improbability of replacement. They do not provide absolute finality.

## 19. Counter Evidence and Limitations

The whitepaper uses "longest chain" language, so readers may encounter that term in historical and educational sources. This document treats it as historical shorthand and explains the modern precision requirement.

Bitcoin Core implementation is primary evidence for Bitcoin Core behavior, but other compatible implementations may organize internal data structures differently. They must still converge on the same valid chain under consensus-compatible behavior.

Chainwork comparison assumes valid targets and valid Proof of Work. Invalid or unvalidated branches should not be counted as accepted history.

On-chain active-chain data alone does not reveal all stale blocks. Stale-block datasets depend on network observation, archival nodes, and measurement methodology.

Reorg interpretation is context-dependent. A shallow one-block reorg after near-simultaneous mining is different from a deep reorg with suspicious timing, but both require careful evidence.
