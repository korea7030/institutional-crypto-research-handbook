## 4. Definitions

### Coinbase Transaction

A coinbase transaction is the special first transaction in a Bitcoin block. It creates one or more outputs without spending a previous output. It is the transaction through which the block producer claims the permitted block subsidy and the transaction fees from the block's non-coinbase transactions.[^ref-btc-wp][^ref-btc-dev-transactions]

### Coinbase Input

The coinbase input is the input of the coinbase transaction. Unlike a normal input, it does not reference a previous spendable output. Bitcoin Developer documentation describes the coinbase input as using a 32-byte null hash and output index `0xffffffff` because it has no previous outpoint.[^ref-btc-dev-transactions]

### Non-Coinbase Input

A non-coinbase transaction input spends an outpoint from a previous transaction. The outpoint identifies a prior transaction hash and an output index. Bitcoin Core models this through `COutPoint` and `CTxIn`.[^ref-btc-core-transaction]

### Transaction Output

A transaction output specifies an amount and a locking script. Bitcoin Core models transaction outputs with `CTxOut`, including `nValue` and `scriptPubKey`.[^ref-btc-core-transaction]

### Block Subsidy

The block subsidy is newly issued bitcoin permitted by the consensus subsidy schedule at a block height. It is not chosen by the miner.

### Transaction Fee

A transaction fee is the difference between the value consumed by a non-coinbase transaction's inputs and the value created by its outputs:

```text
fee = input value - output value
```

Bitcoin Core's `CheckTxInputs` computes the fee as `nValueIn - value_out` after checking that input value is not below output value.[^ref-btc-core-tx-verify]

### Extra Nonce

Extra nonce is miner-controlled data, commonly placed in the coinbase transaction, that changes the coinbase transaction identifier, the transaction Merkle root, and therefore the block header being hashed. It is a mining convention, not a distinct consensus field named `extra_nonce`.

## 5. Historical Context

The Bitcoin whitepaper introduced the special first transaction as part of the incentive system. It states that the first transaction in a block starts a new coin owned by the block creator, giving nodes an incentive to support the network and providing a way to initially distribute coins.[^ref-btc-wp]

In the original design, this special transaction is primarily an incentive mechanism. In modern Bitcoin, the coinbase transaction is also a mining commitment surface. It contributes the first leaf of the transaction Merkle tree, can contain miner-controlled script data, and can carry later soft-fork commitments such as witness-related commitments.

The important historical transition is:

```text
Whitepaper role:
    miner reward and coin distribution

Modern operational role:
    miner reward
    transaction-fee claim
    block-height commitment
    Merkle-root input
    extra-nonce search-space expansion
    metadata surface
```

This expanded role should not obscure the consensus boundary. Miners can construct the coinbase transaction, but full nodes independently verify whether the block reward and block structure are valid.

## 6. Technical Foundations

### Transaction Shape

Bitcoin Developer documentation describes a raw transaction as containing:

- a version;
- an input count;
- one or more transaction inputs;
- an output count;
- one or more transaction outputs;
- a lock time.[^ref-btc-dev-transactions]

Bitcoin Core's `CTransaction` similarly contains `vin`, `vout`, `version`, and `nLockTime` fields.[^ref-btc-core-transaction]

The coinbase transaction uses the same broad transaction container but has a special input. Normal transactions consume existing UTXOs. Coinbase transactions create permitted outputs without spending existing UTXOs.

### Required Coinbase Position

Bitcoin Core's block validation checks coinbase placement. A valid block must have a coinbase transaction first, and later transactions must not be coinbase. If the first transaction is not coinbase, validation returns `bad-cb-missing`; if more than one coinbase is present, validation returns `bad-cb-multiple`.[^ref-btc-core-validation]

This rule matters because the coinbase transaction is how the block's subsidy and fees are claimed. It is not merely a wallet convention or block explorer display format.

### Basic Transaction Checks

Bitcoin Core's `CheckTransaction` performs context-independent checks. It rejects transactions with empty input vectors, empty output vectors, excessive serialized size, negative outputs, too-large outputs, too-large output totals, duplicate inputs, non-coinbase transactions with null previous outpoints, and coinbase scripts outside the permitted size range.[^ref-btc-core-tx-check]

These checks show that transaction validity is not defined by proof of work alone. A block can have a valid header hash but still be invalid if its transactions fail consensus checks.

### UTXO-Dependent Checks

Bitcoin Core's `CheckTxInputs` checks whether all inputs are available in the UTXO view, enforces coinbase maturity for spent coinbase outputs, sums input values, checks amount ranges, rejects transactions whose input value is below output value, and computes the transaction fee as input value minus output value.[^ref-btc-core-tx-verify]

This is the UTXO accounting basis for fees:

```text
sum(previous outputs spent by transaction)
-
sum(new outputs created by transaction)
=
transaction fee
```

The fee is not an explicit output. It is value left unassigned by the transaction and later claimable by the block's coinbase transaction.

## 7. Coinbase Reward Mechanics

### Reward Formula

For a block at height `h`:

```text
maximum coinbase value =
    GetBlockSubsidy(h, consensus parameters)
    +
    sum(fees of included non-coinbase transactions)
```

Bitcoin Core uses this logic when connecting a block. It computes the permitted block reward and rejects the block with `bad-cb-amount` if the coinbase transaction pays more than the allowed subsidy plus fees.[^ref-btc-core-validation]

### Underclaiming

A miner may claim less than the maximum permitted reward. The consensus failure condition is overclaiming, not underclaiming.

Example:

```text
subsidy:           3.125 BTC
included fees:     0.080 BTC
maximum coinbase:  3.205 BTC
coinbase outputs:  3.204 BTC
```

This underclaims by `0.001 BTC`. The reward amount rule is satisfied.

### Overclaiming

Example:

```text
subsidy:           3.125 BTC
included fees:     0.080 BTC
maximum coinbase:  3.205 BTC
coinbase outputs:  3.206 BTC
```

This overclaims by `0.001 BTC`. A fully validating node rejects the block even if the block header satisfies proof of work.

### Amount Bounds

Bitcoin Core defines `CAmount` in satoshis, `COIN = 100000000`, `MAX_MONEY = 21000000 * COIN`, and `MoneyRange` for checking that values are within the valid monetary range.[^ref-btc-core-amount]

These amount bounds are general monetary validity constraints. They do not replace the per-block reward rule. A coinbase output can be below `MAX_MONEY` and still be invalid if it exceeds subsidy plus fees.

## 8. Mining Commitments

### The Coinbase as a Merkle Leaf

The coinbase transaction is the first transaction in the block. Its transaction identifier is one of the leaves of the transaction Merkle tree. Because the block header contains the Merkle root, the coinbase transaction is indirectly committed into the proof-of-work input.

The commitment path is:

```text
coinbase transaction bytes
    -> coinbase txid
    -> transaction Merkle tree
    -> Merkle root
    -> block header
    -> proof-of-work hash
```

Changing the coinbase transaction changes the Merkle root unless the change somehow leaves the same transaction identifier and tree root, which would require breaking the relevant hash assumptions or recreating the same serialized transaction.

### Extra Nonce Search Space

The block header contains a 32-bit nonce. Large miners can exhaust assigned nonce ranges quickly. Mining software therefore changes other header-affecting data to create new candidate headers.

A common method is changing miner-controlled bytes in the coinbase transaction. That changes:

```text
coinbase script or output data
    -> coinbase txid
    -> Merkle root
    -> block header
    -> hash-search input
```

This is why extra nonce belongs in the mining-commitment discussion. It is not a separate consensus field in the block header. It is a convention for creating additional header families.

### Transaction Selection Commitment

The Merkle root also commits to the selected non-coinbase transactions and their order. Adding, removing, or reordering transactions generally changes the Merkle root.

This creates an important analytical connection:

```text
miner transaction selection
    -> transaction list
    -> fee total
    -> coinbase reward limit
    -> Merkle root
    -> proof-of-work search input
```

Mining is therefore not only nonce iteration. It is repeated construction of candidate block commitments.

Bitcoin Core's mining code reflects this construction pipeline. `BlockAssembler::CreateNewBlock` builds a candidate block, creates the coinbase transaction, accounts for fees and subsidy, and assigns the transaction Merkle root before proof-of-work search can be performed on the resulting header.[^ref-btc-core-miner]

## 9. Consensus, Policy, Implementation, and Convention

### Consensus Rules

The following are consensus-level constraints:

| Rule | Evidence |
|---|---|
| A valid block must have a coinbase transaction first. | Bitcoin Core validation |
| A valid block must not contain multiple coinbase transactions. | Bitcoin Core validation |
| Coinbase script size is constrained. | Bitcoin Core `CheckTransaction` |
| Non-coinbase transactions must not use null previous outpoints. | Bitcoin Core `CheckTransaction` |
| Duplicate inputs are invalid. | Bitcoin Core `CheckTransaction` |
| Output values must not be negative or out of range. | Bitcoin Core `CheckTransaction` and `MoneyRange` |
| Input value must be at least output value. | Bitcoin Core `CheckTxInputs` |
| Coinbase reward must not exceed subsidy plus fees. | Bitcoin Core block connection |
| Coinbase outputs must mature before spending. | Bitcoin Core `CheckTxInputs` |

### Policy Rules

Policy rules affect relay and mempool acceptance but are not the same as consensus. Examples include standardness, dust policy, minimum relay fee, and mempool package behavior. A transaction can be non-standard for relay policy but still valid if mined in a block that satisfies consensus.

This document does not define all policy rules. It only uses the distinction to prevent category errors.

### Implementation Details

Bitcoin Core function and file names are implementation evidence:

| File | Relevant Role |
|---|---|
| `src/primitives/transaction.h` | Transaction, input, output, and outpoint structures |
| `src/consensus/tx_check.cpp` | Context-free transaction checks |
| `src/consensus/tx_verify.cpp` | UTXO-dependent input and fee checks |
| `src/validation.cpp` | Block validation, coinbase placement, reward checks |
| `src/node/miner.cpp` | Candidate block and coinbase construction |
| `src/consensus/amount.h` | Amount unit and range constants |

### Mining Conventions

The following are mining conventions or operational practices, not direct consensus rules:

- pool tags in coinbase script data;
- extra nonce layout;
- payout address attribution;
- pool worker identifiers;
- pool reward distribution;
- transaction-selection strategy;
- whether the miner underclaims reward;
- the precise template-refresh policy.

Analysts should avoid treating mining conventions as protocol-authenticated facts.

## 10. Institutional Thinking

### Why Coinbase Analysis Matters

Coinbase data is useful because it links:

- block production;
- miner compensation;
- fee capture;
- reward destination scripts;
- block-template construction;
- possible pool metadata;
- proof-of-work search-space expansion.

For an institutional analyst, this makes the coinbase transaction a high-value evidence object. It is directly observable, consensus-relevant, and economically meaningful.

### What Coinbase Data Can Support

Coinbase data can support:

- fee and subsidy accounting;
- block reward verification;
- reward underclaim detection;
- payout script clustering;
- mining-pool attribution hypotheses;
- block construction analysis;
- extra-nonce pattern analysis;
- historical miner behavior studies.

### What Coinbase Data Cannot Prove Alone

Coinbase data alone cannot prove:

- real-world miner identity;
- physical hash hardware ownership;
- pool participant distribution;
- electricity cost;
- profitability;
- off-chain payout terms;
- whether a pool tag is authentic;
- whether an entity controlled transaction selection.

Coinbase tags are especially risky. They prove that certain bytes appear in a coinbase transaction. They do not prove identity without corroborating evidence.

### Institutional Controls

Research systems should:

- compute permitted coinbase value from full UTXO context;
- separate subsidy from fees;
- preserve raw coinbase data;
- avoid relying on one pool-label source;
- mark miner attribution as heuristic unless independently verified;
- track reward underclaims and overclaim invalidity separately;
- document whether analysis uses full-node data, indexed data, or third-party API data.

## 12. Common Misconceptions

### Misconception 1: The coinbase transaction comes from the Coinbase exchange.

Incorrect. In Bitcoin, coinbase is a protocol term for the special first transaction in a block. It is unrelated to the company named Coinbase.

### Misconception 2: Miners can create arbitrary bitcoin.

Incorrect. Miners construct the coinbase transaction, but full nodes reject blocks whose coinbase output value exceeds subsidy plus included fees.[^ref-btc-core-validation]

### Misconception 3: Fees are explicit outputs in each transaction.

Incorrect. A fee is the difference between input value and output value. It is claimed in aggregate by the block's coinbase transaction.

### Misconception 4: Extra nonce is a block-header field.

Incorrect. The block header has a 32-bit nonce field. Extra nonce is a mining convention usually placed in coinbase-controlled data that changes the Merkle root and therefore the header.

### Misconception 5: A valid proof-of-work hash validates the coinbase amount.

Incorrect. Proof of work validates only the header's work claim. The block still needs transaction, UTXO, script, Merkle-root, and reward validation.

### Misconception 6: Coinbase tags prove pool identity.

Incorrect. Tags are data in the transaction. Attribution requires corroborating evidence.

## 14. Challenge Section

### Exercise 1: Reward Limit

Given:

```text
subsidy = 3.125 BTC
included fees = 0.042 BTC
coinbase outputs = 3.167 BTC
```

Question:

```text
Is the coinbase reward amount valid?
```

Answer:

```text
maximum permitted = 3.125 + 0.042 = 3.167 BTC
```

The amount is valid if all other consensus rules also pass.

### Exercise 2: Fee Calculation

Given a non-coinbase transaction:

```text
input values:  0.80 BTC + 0.30 BTC
output values: 0.60 BTC + 0.49 BTC
```

Question:

```text
What is the transaction fee?
```

Answer:

```text
inputs = 1.10 BTC
outputs = 1.09 BTC
fee = 0.01 BTC
```

### Exercise 3: Extra Nonce

Question:

```text
Why can changing coinbase script data create new proof-of-work search space?
```

Answer:

Changing coinbase script data changes the coinbase transaction identifier. That changes the Merkle root in the block header. A new Merkle root creates a new family of candidate headers for nonce iteration.

### Exercise 4: Attribution

Question:

```text
A coinbase script contains a pool name. What evidence level should be assigned to real-world miner identity?
```

Answer:

The byte presence is FACT — ECL-A. Real-world miner identity is an attribution hypothesis and should receive lower confidence unless supported by payout patterns, pool statements, or independent datasets.

## 15. Summary

The coinbase transaction is the special first transaction in a Bitcoin block. It is the mechanism through which the miner claims the block subsidy and the included transaction fees.

The coinbase transaction is constrained by consensus. It cannot create arbitrary bitcoin. Its output value must not exceed the permitted subsidy plus fees, and fully validating nodes enforce this during block validation.

The coinbase transaction also matters for proof-of-work mechanics. Because it is part of the transaction Merkle tree, changing coinbase data changes the Merkle root and therefore the block header being hashed. This allows miners to expand search space beyond the header nonce.

For analysts, coinbase data is powerful but limited evidence. It supports reward accounting, fee analysis, and attribution hypotheses. It does not prove miner identity, profitability, pool ownership, or off-chain payout rules by itself.
